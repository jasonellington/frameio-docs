## Che cos'è un webhook? {#what’s-a-webhook}

Un **webhook** è un callback HTTP di tipo push che Frame.io attiva **non appena accade qualcosa di rilevante** nel tuo account (ad esempio, un nuovo file completa la transcodifica, viene aggiunto un commento, viene creato un progetto).
Invece di interrogare periodicamente l'API, fornisci un URL HTTPS pubblico; Frame.io invia un payload JSON a quell'URL in tempo reale, così puoi:

## Panoramica degli endpoint {#endpoint-overview}

| **Operazione** | **Endpoint** | **Dettagli** |
| --- | --- | --- |
| **Creare** un webhook | POST /v4/accounts/\{account_id\}/workspaces/\{workspace_id\}/webhooks | Corpo con `name`, `url`, `events[]` |
| **Elencare** tutti i webhook di uno spazio di lavoro | GET /v4/accounts/\{account_id\}/workspaces/\{workspace_id\}/webhooks | Supporta la paginazione |
| **Mostrare** un webhook | GET /v4/webhooks/\{webhook_id\} | Restituisce il segreto di firma solo al momento della creazione |
| **Aggiornare** un webhook | PATCH /v4/webhooks/\{webhook_id\} | Modifica `url`, `events` o `is_active` |
| **Eliminare** un webhook | DELETE /v4/webhooks/\{webhook_id\} | Interrompe immediatamente le consegne |

<Warning>

**Autenticazione**: tutti gli endpoint V4 richiedono un token di accesso OAuth 2.0 ottenuto tramite l'Adobe Developer Console. I token sviluppatore legacy e i JWT **non** sono accettati.

</Warning>

## Modifiche e aggiornamenti in Frame V4 {#changes-and-updates-in-frame-v4}

<Info>

I webhook creati in Legacy vengono trasferiti a V4 con le seguenti modifiche:

1. **Struttura del payload**: è stato aggiunto l'ID account al payload
2. **Modifiche agli endpoint**: il `team_id` non viene più fornito nel payload JSON, ma si trova invece nel parametro di percorso dell'URL: `https://api.frame.io/v4/accounts/:account_id/workspaces/:workspace_id/webhooks`
3. **Integrazione API**: a causa delle modifiche alla struttura dell'API, agli endpoint e ai metodi di autenticazione, qualsiasi codice esistente per i webhook in entrata che effettua chiamate successive all'API Frame.io per arricchire e cercare risorse deve essere aggiornato
4. **Tipi di evento**: i webhook degli asset sono stati suddivisi in eventi separati per File e Folder; tutti i webhook provenienti da Legacy con eventi asset devono essere aggiornati per utilizzare gli eventi File e Folder appropriati

</Info>

<Warning>

**Stato dei webhook dopo la migrazione**: quando il tuo account viene migrato a Frame.io V4, i webhook esistenti delle versioni precedenti vengono disattivati automaticamente. In questo modo puoi modificare gli endpoint dei webhook e la logica di integrazione per adattarli agli aggiornamenti di V4 prima di riattivarli. I webhook non aggiornati per la compatibilità con V4 genereranno errori se attivati senza le modifiche necessarie. Prima di riattivarli, puoi verificare quali webhook sono inattivi esaminando il campo `is_active` tramite l'API oppure controllando le [impostazioni dei webhook](https://next.frame.io/settings/webhooks).

</Warning>

## Sottoscrizioni agli eventi dei webhook {#webhook-event-subscriptions}

Quando crei e aggiorni i webhook, indica gli eventi che ti interessano. Puoi sceglierne quanti vuoi, ma tieni presente che l'esperienza è migliore se ti iscrivi a un numero ridotto di eventi, suddividendo i webhook in modo logico con schemi di denominazione ed endpoint diversi, così da poter modellare la logica di business sul lato ricevente riducendo il filtraggio e l'instradamento nelle funzioni condivise.

<Note>

Ambito degli eventi: tutti gli eventi sono limitati allo spazio di lavoro (Workspace) specificato durante la creazione del webhook. Ciò significa che gli eventi verranno inviati per le azioni eseguite in tutti i progetti di quel Workspace.

</Note>

## Payload dei messaggi webhook {#webhook-message-payload}

Tutti i payload dei webhook contengono un campo `type`, che indica l'evento che si è verificato, e un oggetto `resource`. L'oggetto `resource` contiene il `type` e l'`ID` della risorsa Frame.io correlata all'evento.

### Esempio di payload {#example-payload}

```json
{
  "account": {
    "id": "6f70f1bd-7e89-4a7e-b4d3-7e576585a181"
  },
  "project": {
    "id": "7e46e495-4444-4555-8649-bee4d391a997"
  },
  "resource": {
    "id": "d3075547-4e64-45f0-ad12-d075660eddd2",
    "type": "file"
  },
  "type": "file.ready",
  "user": {
    "id": "56556a3f-859f-4b38-b6c6-e8625b5da8a5"
  },
  "workspace": {
    "id": "378fcbf7-6f88-4224-8139-6a743ed940b2"
  }
}
```

Nell'esempio precedente di un evento `file.created`, `resource.id` indica l'`ID` del file appena creato. Sono inoltre inclusi gli oggetti `workspace`, `project` e `user`, che contengono i relativi `workspace.id`, `project.id` e `user.id`. Questi valori possono essere usati per ridurre le chiamate API filtrando gli eventi in entrata o cercando dati memorizzati nella cache locale.

<Warning>

**Oltre all'ID della risorsa, non includiamo alcuna informazione aggiuntiva sulla risorsa sottoscritta**.

Se la tua applicazione richiede ulteriori informazioni o contesto, ti consigliamo di effettuare una chiamata API per recuperare maggiori informazioni sulle risorse a cui si fa riferimento.

</Warning>

## Sicurezza {#security}

Per impostazione predefinita, tutti i webhook dispongono di una chiave di firma. Questo segreto di firma non configurabile può essere utilizzato per verificare che la richiesta provenga da Frame.io.

Il payload di risposta del webhook che hai configurato include il segreto di firma specifico di questo webhook. Questo segreto viene **fornito solo in questa risposta iniziale di creazione del webhook**, quindi conservalo in un luogo sicuro, nel tuo archivio di segreti o nelle variabili d'ambiente. Usalo in seguito per verificare che il webhook provenga direttamente dai nostri server e che non sia stato intercettato o manipolato in alcun modo.

### Verificare le firme dei webhook {#verifying-webhook-signatures}

Per proteggere un'integrazione da attacchi man-in-the-middle e di replay, è essenziale verificare la firma del payload del webhook. La verifica garantisce che i payload dei webhook siano stati effettivamente inviati da Frame.io e che il loro contenuto non sia stato modificato durante il trasporto.

La richiesta `POST` include i seguenti header HTTP:

| Nome dell'header | Descrizione | Esempio |
| --- | --- | --- |
| `X-Frameio-Request-Timestamp` | Il timestamp di invio della richiesta | `1604004499` |
| `X-Frameio-Signature` | La firma calcolata del webhook | `v0=a77ce6856e609c884575c2fd211d07a9ad1c3f72e19c06ff710e8f086ffca883` |
| `user-agent: "Frame.io V4 API"` | User agent nell'header per v4 |  |
| `user-agent: "Frame.io Legacy API"` | User agent nell'header per Legacy |  |

```python title="Python"
import hmac
import hashlib

def verify_signature(curr_time, req_time, signature, body, secret):
    """
    Verify Webhook signature
    :Args:
        curr_time (float): Current epoch time
        req_time (float): Request epoch time
        signature (str): Signature provided by the Frame.io API for the given request
        body (str): Webhook body from the received POST
        secret (str): The secret for this Webhook that you saved when you first created it
    """
    if int(curr_time) - int(req_time) < 500:
        message = 'v0:{}:{}'.format(req_time, body)
        calculated_signature = 'v0={}'.format(hmac.new(
            bytes(secret, 'latin-1'),
            msg=bytes(message, 'latin-1'),
            digestmod=hashlib.sha256).hexdigest())
        if calculated_signature == signature:
            return True
    return False
```

**Il timestamp** è l'ora di sistema dei sistemi di Frame.io al momento dell'invio del webhook in uscita. Può essere utilizzato per prevenire attacchi di [replay](https://en.wikipedia.org/wiki/Replay_attack). Ti consigliamo di verificare che questo orario non si discosti di più di 5 minuti dall'ora locale.

**La firma** è un hash HMAC SHA256 calcolato con la chiave di firma fornita al momento della creazione del webhook.

**Segui questi passaggi per verificare la firma:**

<Steps>

<Step title="Estrai la firma">

Estrai la firma dagli header HTTP.

</Step>

<Step title="Crea il messaggio da firmare">

Crea un messaggio da firmare combinando la versione, l'ora di consegna e il corpo della richiesta: `v0:timestamp:body.`

</Step>

<Step title="Calcola l'HMAC SHA256">

Calcola la firma HMAC SHA256 utilizzando il tuo segreto di firma.

</Step>

<Step title="Confronta le firme">

Confronta la firma che hai calcolato con quella fornita!

</Step>

</Steps>

<Note>

La firma fornita ha il prefisso `v0=`. Attualmente Frame.io dispone solo di questa versione per la firma delle richieste. Assicurati di anteporre questo prefisso alla firma che hai calcolato.

</Note>

## Limiti di frequenza dei webhook {#webhook-rate-limits}

Gli eventi dei webhook e delle Custom Action condividono i seguenti limiti per account:

| Intervallo di tempo | Limite per account |
| --- | --- |
| 1 minuto | 1.000 eventi |
| 1 ora | 20.000 eventi |

Entrambi i limiti si applicano al volume combinato degli eventi dei webhook e delle Custom Action. Rispettare il limite al minuto non esonera un account dal limite orario. Questi limiti si applicano a livello di account, non separatamente a ciascuna sottoscrizione webhook o Custom Action.

Si tratta di limiti sul volume degli eventi, non di limiti sulle richieste API per creare, elencare, aggiornare o eliminare sottoscrizioni webhook o Custom Action.

<Warning>

Quando viene raggiunto uno dei due limiti a livello di account, gli ulteriori eventi dei webhook e delle Custom Action vengono **scartati**, non messi in coda per una consegna successiva. Gli eventi scartati non vengono automaticamente ritentati o riprodotti quando torna disponibile capacità. La policy di nuovi tentativi di consegna descritta di seguito non si applica agli eventi scartati a causa dei limiti di frequenza.

</Warning>

### Rispettare i limiti {#working-within-the-limits}

Per rispettare i limiti dei webhook, ti consigliamo di sottoscrivere solo gli **[eventi](#webhook-event-subscriptions)** di cui la tua integrazione ha bisogno. Ad esempio, se il tuo flusso di lavoro inizia quando un file termina il caricamento, sottoscrivi `file.upload.completed` anziché tutti gli eventi relativi ai file. Controlla regolarmente le sottoscrizioni del tuo account e rimuovi quelle non più in uso.

Se la tua integrazione carica molti file o esegue una serie di aggiornamenti, distribuisci queste operazioni nel tempo, ove possibile, per rimanere entro entrambi i limiti e lasciare capacità per le altre attività dell'account. In questo modo eviterai la perdita di eventi, che non vengono ritentati.

## Nuovi tentativi e registrazione {#retries-and-logging}

<CardGroup cols={2}>

<Card title="Policy di nuovi tentativi di consegna" icon="arrows-rotate" iconType="solid">

- Tre tentativi in totale (iniziale + 2 nuovi tentativi)
- Back-off esponenziale a partire da 15 s (+ jitter)
- Una risposta HTTP `5xx`, un errore di connessione o un timeout superiore a 5 secondi attivano un nuovo tentativo
- Le risposte HTTP `4xx`, incluso `429`, non vengono ritentate

</Card>

Frame.io conserva un **registro degli errori** con: `webhook_id`, `account_id`, `event_type`, `resource_id`, `user_id`.

</Card>

## Tutorial sui webhook {#webhook-tutorial}

### Passaggio 1: configura il lato ricevente (da fare per primo, così saprai quale sarà il tuo URL) {#step-1-setup-receiving-end-done-first-so-that-you-know-what-your-url-will-be}

Quando visiti per la prima volta [https://webhook.site](https://webhook.site/), viene creato per te un endpoint webhook univoco che puoi copiare e utilizzare subito.

Questo URL è univoco per la tua sessione.

### Passaggio 2: scegli gli eventi da sottoscrivere {#step-2-choose-the-events-you-want-to-subscribe-to}

Per questo tutorial manterremo le cose semplici e configureremo il webhook per sottoscrivere solo gli eventi `file.created`. Il payload JSON che useremo per creare il webhook sarà il seguente.

```json
{
    "data": {
        "name": "asset.created sample webhook",
        "events": ["file.created"],
        "url": "https://webhook.site/c05f2216-9558-4816-bc09-f77ee7b9de40"
    }
}
```

### Passaggio 3: crea una risorsa webhook con Postman {#step-3-create-a-webhook-resource-using-postman}

Con Postman, effettua una chiamata API per creare la risorsa webhook, specificando l'endpoint di [webhook.site](http://webhook.site/) nel payload.

### Passaggio 4: prova! {#step-4-test}

Ora che hai creato la sottoscrizione al webhook e hai configurato un endpoint per riceverlo, è il momento di provarlo attivando il primo webhook tramite l'azione che ne provoca l'invio!

Poiché il nostro esempio è stato configurato per attivarsi con il trigger `file.created`, caricheremo un nuovo asset in un qualsiasi progetto all'interno dell'account e dello spazio di lavoro in cui è stato configurato il webhook.
