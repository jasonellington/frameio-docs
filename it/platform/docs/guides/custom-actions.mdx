Le Actions di Frame.io offrono un accesso rapido alle operazioni più comuni sui contenuti multimediali, come scaricare, rinominare e duplicare elementi, e consentono inoltre di integrare strumenti e servizi di terze parti direttamente nell’interfaccia utente di [Frame.io](https://next.frame.io/).

## Informazioni sulle Actions {#about-actions}

Con l’introduzione delle Custom Actions, gli sviluppatori possono configurare e gestire le proprie Actions in Frame.io V4. Sfruttando lo stesso sistema di eventi sottostante dei [Webhook](https://developer.adobe.com/frameio/guides/Webhooks/), le Custom Actions rappresentano un meccanismo alternativo con cui gli sviluppatori possono collegare i propri asset agli strumenti più importanti per gli utenti del loro Account Frame.io.

Le Actions possono essere eseguite da qualsiasi utente che sia Member del Workspace Frame.io in cui l’Action è abilitata. Quando viene eseguita un’Action, Frame.io invia un payload a un URL da te fornito. L’applicazione ricevente risponde con un codice di stato HTTP per confermare la ricezione oppure con un callback personalizzato per visualizzare campi di modulo aggiuntivi nell’interfaccia di Frame.io. L’applicazione ricevente può essere un tuo programma ospitato, un servizio o persino uno strumento IPaaS low-code/no-code come Workfront Fusion o Zapier.

Usa le Custom Actions per creare integrazioni direttamente in [Frame.io](https://next.frame.io/) sotto forma di componenti dell’interfaccia programmabili. Ciò abilita workflow che possono essere attivati dagli utenti all’interno dell’app, sfruttando lo stesso instradamento degli eventi dei webhook. Puoi creare moduli a passaggio singolo o multiplo attivati dagli utenti, che tornano a Frame.io come un altro modulo o come una semplice risposta. Inoltre, quando un utente fa clic su una Custom Action su un Asset, Frame.io invia un payload a un URL da te fornito. L’applicazione ricevente risponde con un codice di stato HTTP per confermare la ricezione oppure con un callback personalizzato in grado di visualizzare elementi di interfaccia aggiuntivi in Frame.io.

## Limiti di frequenza {#rate-limits}

Gli eventi delle Custom Actions rientrano negli stessi limiti a livello di account degli eventi webhook: **1.000 eventi al minuto** e **20.000 eventi all’ora**. Entrambi i limiti si applicano al volume combinato dell’intero account, non separatamente a ciascuna Custom Action o sottoscrizione webhook.

Quando viene raggiunto uno dei due limiti, gli ulteriori eventi delle Custom Actions vengono **scartati**, non messi in coda né ritentati automaticamente.

Si tratta di limiti sul volume degli eventi, non di limiti sulle richieste API per la gestione delle Custom Actions. Consulta [Limiti di frequenza dei webhook](/it/platform/docs/guides/webhooks#webhook-rate-limits) per i dettagli.

## Actions migrate {#migrated-actions}

Ci sono alcuni aspetti da tenere presenti durante la migrazione a un Account Frame.io V4 che contiene Custom Actions create in precedenza nella versione legacy di Frame.io.

### Stato delle Actions {#action-status}

Al momento della migrazione dell’Account a Frame.io V4, tutte le Custom Actions create nelle versioni precedenti avranno lo stato ‘null’ e verranno disabilitate automaticamente. Ciò offre agli utenti l’opportunità di aggiornare prima le proprie Actions per utilizzare l’API V4 e solo dopo abilitarle, poiché le Actions non aggiornate non funzioneranno. Per individuare le Actions in questo stato, visita la pagina Actions Settings e consulta la colonna “Status” oppure, se utilizzi l’API, controlla il campo is_active.

### Risorse su cui agire: file, cartelle e Version Stack {#actionable-resources-files-folders-&-version-stacks}

Dato che nell’API Frame.io V4 i tipi di asset sono separati in risorse distinte, potrebbe essere necessario considerare alcuni comportamenti nell’interpretare l’ID della risorsa ricevuto nel payload della tua Action. Il comportamento per i singoli File è semplice, poiché l’ID corrisponde al File specifico su cui è stata eseguita l’Action. Analogamente, per le Folder riceverai l’ID della Folder su cui è stata eseguita l’Action; tuttavia, a seconda del tuo caso d’uso, hai più opzioni per definire il comportamento della tua Action. Usa l’ID della Folder per effettuare chiamate successive all’API di Frame.io se vuoi interagire con la risorsa Folder stessa. In alternativa, potresti voler ottenere gli elementi figli di quella Folder per elaborare ulteriormente gli asset al suo interno. Quando un’Action viene eseguita su un Version Stack, il payload conterrà l’ID dell’‘Head Asset’, ovvero il File in cima allo Stack, che è quello mostrato nell’interfaccia di Frame.io.

Per saperne di più sulle differenze tra l’API Legacy di Frame.io e la V4, consulta la nostra [Guida alla migrazione](/it/platform/docs/resources/migration).

## Configurare la Custom Action {#configure-your-custom-action}

Quando un utente attiva una Custom Action, Frame.io invia un payload a un URL da te fornito. L’applicazione ricevente può rispondere con un codice di stato HTTP per confermare la ricezione oppure con un callback personalizzato che visualizza elementi di interfaccia aggiuntivi in [Frame.io](https://next.frame.io/).

<Warning>

</Warning>

### Configurazione multi-asset {#multi-asset-configuration}

Il supporto multi-asset dipende dalla configurazione e deve essere abilitato esplicitamente dalla finestra modale di configurazione dell’Action [sul Web](https://next.frame.io/settings/actions). Puoi farlo durante la creazione di una nuova Action o durante l’aggiornamento di un’Action esistente.

Quando il supporto multi-asset è abilitato, il formato del payload cambia immediatamente. Il payload legacy e quello con supporto multi-asset si escludono a vicenda.

### Migrazione dal payload legacy {#migrating-from-the-legacy-payload}

<Warning>

**Deprecazione prevista per il payload legacy**

È prevista la deprecazione del payload legacy e si consiglia vivamente agli utenti di migrare i propri servizi per elaborare il nuovo payload.

Abilitando il flag di configurazione e aggiornando la gestione del payload, un’Action può passare senza problemi al supporto del payload multi-asset.

1. Sostituisci l’utilizzo dell’oggetto singolare `resource` con l’elenco `resources`
2. Aggiorna il codice per iterare sull’elenco `resources`
3. Abilita il flag Multi-asset nella configurazione delle Actions

</Warning>

## Interazioni, nuovi tentativi e timeout {#interactions-retries-and-timeouts}

L’`interaction_id` è un identificatore univoco per tenere traccia dell’interazione man mano che si evolve nel tempo. Se non hai bisogno di rispondere all’utente, restituisci un codice di stato 200 e il gioco è fatto. Sebbene sia facoltativo, consigliamo di includere informazioni sul risultato dell’azione, come un messaggio di successo o un avviso di errore. Le Custom Actions supportano i message callback.

<Note>

Frame.io si aspetta una risposta entro 10 secondi e tenta fino a 5 volte in attesa di una risposta positiva. Idealmente la risposta è immediata e le azioni asincrone avvengono dopo l’attivazione tramite una Custom Action.

</Note>

## Creare un Message Callback {#create-a-message-callback}

Nella risposta HTTP all’evento webhook, puoi restituire un oggetto JSON che descrive un messaggio che verrà mostrato all’utente che ha avviato l’azione nell’interfaccia di Frame.io.

```json
{
  "title": "Success!",
  "description": "The thing worked! Nice."
}
```

I messaggi ti consentono di fornire un riscontro all’utente direttamente nell’interfaccia di Frame.io. Se devi raccogliere informazioni aggiuntive dall’utente, usa invece i **Form Callback**.

## Creare un Form Callback {#create-a-form-callback}

Supponiamo che tu abbia bisogno di più informazioni prima di avviare il tuo processo. Ad esempio, potresti caricare contenuti in un sistema che richiede dettagli aggiuntivi. Puoi descrivere un modulo nella tua risposta, che l’utente compila e ti rinvia. Ecco un esempio:

```json
{
  "title": "Need some more info!",
  "description": "Getting ready to submit this file!",
  "fields": [
    {
      "type": "text",
      "label": "Title",
      "name": "title",
      "value": "MyVideo.mp4"
    },
    {
      "type": "select",
      "label": "Captions",
      "name": "captions",
      "options": [
        {
          "name": "Off",
          "value": "off"
        },
        {
          "name": "On",
          "value": "on"
        }
      ]
    }
  ]
}
```

Quando l’utente invia il modulo, riceverai un evento sullo stesso URL della POST iniziale:

```json
POST /your/url
{
  "type": "your-specified-event-name",
  "interaction_id": "the-same-id-as-before",
  "action_id": "unique-id-for-this-custom-action",
  "data":{
    "title": "MyVideo.mp4",
    "captions": "off"
  }
}
```

Tutti i campi personalizzati aggiunti a un modulo compaiono nella sezione `data` del payload JSON inviato da Frame.io. Usa l’`interaction_id` per associare la richiesta iniziale a questi nuovi dati del modulo. Puoi rispondere con un messaggio oppure concatenare un altro modulo. Concatenando Actions, moduli e messaggi, puoi di fatto programmare workflow in più passaggi in Frame.io con la logica di business di un sistema esterno.

## Sicurezza e verifica {#security-and-verification}

Per impostazione predefinita, a tutte le Custom Actions viene associata una chiave di firma generata al momento della creazione. Questa impostazione non è configurabile. La chiave può essere utilizzata per verificare che la richiesta provenga da Frame.io. La richiesta `POST` include quanto segue:

| Nome | Descrizione |
| --- | --- |
| `X-Frameio-Request-Timestamp` | L’ora in cui è stata attivata la tua Custom Action. |
| `X-Frameio-Signature` | La firma calcolata. |

<CardGroup cols={2}>

<Card title="Verifica del timestamp" icon="clock" iconType="solid">

**Il timestamp** è l’ora in cui la richiesta è stata firmata in uscita dalla rete di Frame.io. Può essere utilizzato per prevenire attacchi di tipo replay. Consigliamo di verificare che questo orario rientri nei 5 minuti rispetto all’ora locale.

</Card>

<Card title="Verifica della firma" icon="shield" iconType="solid">

**La firma** è un hash HMAC SHA-256 calcolato con la chiave di firma fornita al momento della prima creazione della Custom Action.

</Card>

</CardGroup>

### Verificare la firma {#verifying-the-signature}

<Steps>

<Step title="Estrai la firma">

Estrai la firma dagli header HTTP.

</Step>

<Step title="Crea il messaggio da firmare">

Crea un messaggio da firmare combinando la versione, l’ora di consegna e il corpo della richiesta `v0:timestamp:body`.

</Step>

<Step title="Calcola l’HMAC SHA256">

Calcola la firma HMAC SHA256 utilizzando il tuo signing secret.

</Step>

<Step title="Confronta le firme">

Confronta la firma calcolata con quella fornita.

</Step>

</Steps>

<Note>

La firma fornita ha il prefisso `v0=`. Attualmente Frame.io dispone solo di questa versione per la firma delle richieste. Dovrai aggiungere questo prefisso alla firma calcolata.

</Note>

```python title="Python"
import hmac
import hashlib

def verify_signature(curr_time, req_time, signature, body, secret):
    """
    Verify webhook/custom action signature
    :Args:
        curr_time (float): Current epoch time
        req_time (float): Request epoch time
        signature (str): Signature provided by the frame.io API for the given request
        body (str): Custom Action body from the received POST
        secret (str): The secret for this Custom Action that you saved when you first created it
    """
    if int(curr_time) - int(req_time) < 500:
        message = 'v0:{}:{}'.format(req_time, body)
        calculated_signature = 'v0={}'.format(hmac.new(
            bytes(secret, 'latin-1'),
            msg=bytes(message, 'latin-1'),
            digestmod=hashlib.sha256).hexdigest())
        if calculated_signature == signature:
            return True
    return False
```
