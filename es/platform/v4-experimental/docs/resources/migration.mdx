## Introducción {#introduction}

La API de Frame.io V4 es un rediseño de la API Legacy, a menudo denominada *endpoints V2* o *API de Frame.io V3*. El rediseño aprovecha al máximo las nuevas capacidades y funciones de Frame V4 y, al mismo tiempo, mantiene toda la funcionalidad relevante de la API Legacy. Esta guía describe las diferencias clave entre la API Legacy y la API V4, y ofrece instrucciones paso a paso para ayudarte a migrar sin problemas.

## Lista de comprobación de la migración {#migration-checklist}

<Steps>

<Step title="Autenticación">

Para las <Tooltip tip="Cuentas que usaban la API Legacy con un token de desarrollador generado y que se migraron automáticamente a V4. No se incluyen las cuentas creadas en V4 ni las migradas manualmente">**cuentas migradas automáticamente a V4**</Tooltip> que todavía no se administran mediante Adobe Admin Console, puedes seguir usando los tokens de desarrollador Legacy gestionados en el [sitio para desarrolladores de Frame.io](/es/platform/v4-experimental/welcome), pero tendrás que añadir a tus solicitudes a la API un encabezado con la clave `x-frameio-legacy-token-auth` y el valor `true`. De lo contrario, debes seguir los pasos de la sección [Autenticación](#adobe-developer-console-managed-authentication) que aparece más abajo.

</Step>

<Step title="Actualiza las llamadas a la API existentes">

Todas las rutas de la API Legacy deberán asignarse a las nuevas rutas y payloads JSON de la API V4. Más abajo encontrarás una tabla de [correspondencias](#endpoint-mappings-legacy-api-to-v4) bastante completa para ayudarte en este proceso.

</Step>

<Step title="Se recomienda encarecidamente realizar pruebas">

**Haz pruebas exhaustivas.** Como la API tiene muchos cambios, se recomienda probar con una cuenta V4 para asegurarte de que la nueva API funciona como se espera.

</Step>

<Step title="Implementa un inicio de sesión dedicado">

Implementa un método de inicio de sesión dedicado para V4, ya que las URL de autenticación son distintas. La URL de autenticación de V4 es diferente de la de la API Legacy: no devolverá en la respuesta las cuentas que aún no se hayan actualizado a V4 y debe tratarse como una integración independiente.

</Step>

</Steps>

<Note>

Si tienes preguntas sobre algún endpoint que no aparezca en la tabla de correspondencias siguiente, ponte en contacto con nuestro equipo de soporte en [support@frame.io](mailto:support@frame.io).

</Note>

## Autenticación gestionada mediante Adobe Developer Console {#adobe-developer-console-managed-authentication}

Para las cuentas migradas a V4 que se gestionan a través de [Adobe Developer Console](https://developer.adobe.com/developer-console/), tendrás que usar la API V4 con OAuth2.0. Sigue los pasos que se indican a continuación.

<Steps>

<Step title="Crea un proyecto de Adobe">

**Crea un proyecto en Adobe Developer Console** y añade Frame.io como producto.

</Step>

<Step title="Elige el tipo de autenticación">

**Autentícate.** Consulta la [guía de autenticación](https://developer.adobe.com/frameio/guides/Authentication/) para obtener más información. Si tu cuenta V4 todavía no se gestiona mediante Adobe Admin Console, puedes omitir este paso.

- **Autenticación de usuario**: se conecta a Frame mediante un Client ID y/o un Client Secret, y requiere que un usuario inicie sesión con su nombre de usuario y contraseña.
- **Autenticación de servidor a servidor**: se conecta a Frame mediante un Client ID y un Client Secret, pero no requiere que un usuario intervenga para iniciar sesión a través de un navegador.

</Step>

<Step title="Implementa la autenticación Bearer">

**Autenticación JWT Bearer**: en cada solicitud a la API, envía el token de autenticación mediante un encabezado con la clave `Authorization` y el valor `Bearer <IMS_ACCESS_TOKEN>`.

</Step>

</Steps>

## Correspondencias de endpoints (de la API Legacy a V4) {#endpoint-mappings-legacy-api-to-v4}

<Note>

Si usas la autenticación con token de desarrollador Legacy, tendrás que añadir a tus solicitudes a la API un encabezado con la clave x-frameio-legacy-token-auth y el valor true.

</Note>

Notas generales para ayudarte con la migración:

<Steps>

<Step title="Payloads">

Los payloads de solicitud y respuesta pueden ser diferentes.

</Step>

<Step title="Teams → Workspaces">

Los “Teams” de la API Legacy equivalen a los “Workspaces” (espacios de trabajo) de V4.

</Step>

<Step title="Assets">

Los “Assets” de la API Legacy ahora se dividen en “Files” (archivos), “Folders” (carpetas) y “Version Stacks” (pilas de versiones) en V4.

</Step>

<Step title="Permisos">

Los permisos y roles son diferentes en V4, lo que cambia la estructura de los endpoints. En V4 hay roles de usuario de espacio de trabajo y de proyecto. Para obtener más información, consulta [Gestión de permisos de usuario](/es/platform/docs/guides/managing-user-permissions).

</Step>

</Steps>

### 9. Webhooks {#9-webhooks}

Los webhooks que usabas en V3 se migrarán y, en general, funcionarán igual. Tras la migración estarán deshabilitados y habrá que habilitarlos para que funcionen. Será necesario hacer algunos cambios en los eventos de assets, que ahora se dividen en archivos y carpetas. Hay algunos eventos nuevos específicos de V4 que conviene tener en cuenta: metadata.value.updated, los eventos relacionados con colecciones y los eventos relacionados con recursos compartidos.

Antes de volver a habilitar los webhooks migrados, revisa los [límites de frecuencia de los webhooks](/es/platform/docs/guides/webhooks#webhook-rate-limits). Los eventos de webhooks y de acciones personalizadas de V4 comparten límites de **1000 eventos por minuto** y **20 000 eventos por hora**, por cuenta. Ambos límites se aplican a su volumen combinado en toda la cuenta.

### 10. Acciones personalizadas {#10-custom-actions}

Las acciones personalizadas que usabas en V3 se migrarán, pero será necesario modificar las solicitudes y el tratamiento de las respuestas. Tras la migración estarán deshabilitadas y habrá que habilitarlas para que funcionen. Para obtener más información, consulta este [(documento)](/es/platform/docs/guides/custom-actions#migrated-actions)

Nota: los endpoints de acciones personalizadas se encuentran actualmente en la API experimental y requieren el encabezado “api-version: experimental”.

## Pasos de la migración {#migration-steps}

<Steps>

<Step title="Ajusta los endpoints V2 no admitidos">

**Ajusta** cualquier endpoint Legacy V2 no admitido.

</Step>

<Step title="Actualiza las URL base">

**Actualiza las URL base** de `api.frame.io/v2/...` a `api.frame.io/v4/...`.

</Step>

<Step title="Actualiza las solicitudes a la API">

**Actualiza las solicitudes a la API** en tu código para que hagan referencia al nuevo esquema de endpoints.

</Step>

<Step title="Actualiza los payloads JSON">

**Actualiza los payloads JSON** de los esquemas de solicitud y respuesta para asegurarte de que generas y consumes los campos correctos.

</Step>

<Step title="Actualiza la terminología">

Actualiza la terminología: “teams” → “workspaces”; “assets” → “files/folders”; “review links” o “presentation links” → “shares” en tu código y en tu front-end.

</Step>

<Step title="Prueba los endpoints">

**Prueba** todos los endpoints recién actualizados. Si recibes un error 403, 404 o 422, verifica los endpoints, la estructura del payload de la solicitud, etc.

</Step>

<Step title="Analiza las respuestas de error">

**Analiza** las nuevas respuestas de error detalladas y busca el problema en la respuesta JSON `{"errors": [...]}` si tu llamada a la API falla.

</Step>

<Step title="Despliega en producción">

**Despliega** en producción una vez validado con una cuenta V4 de [Frame.io](http://frame.io/).

</Step>

</Steps>

## Gestión de errores y problemas comunes {#error-handling-&-common-issues}

<Note>

Algunas rutas devuelven errores con descripciones personalizadas que pueden diferir ligeramente de los ejemplos siguientes.

</Note>

<CardGroup cols={2}>

<Card title="Errores del cliente (4xx)" icon="triangle-exclamation" iconType="solid">

- **400** Bad Request: comprueba la exactitud del payload.
- **401** Unauthorized: token de autorización no válido o ausente.
- **403** Forbidden: falta un scope o el usuario no tiene acceso.
- **404** Not Found: verifica el endpoint, la versión de la API o los IDs.
- **422** Unprocessable Entity: valida los datos de la solicitud
- **429** Too Many Requests: implementa reintentos con backoff.

</Card>

<Card title="Errores del servidor (5xx)" icon="server" iconType="solid">

- **500** Internal Server Error: vuelve a intentarlo tras una breve espera.

</Card>

</CardGroup>
