## Descripción general {#overview}

Esta guía describe los procedimientos para gestionar los tokens de autorización de dispositivos en Frame.io, incluidas la actualización y la revocación de tokens y las prácticas de almacenamiento seguro.

## Requisitos previos {#prerequisites}

Revisa la guía [Implementar C2C: configuración](/es/camera-to-cloud/implementing-c2c-setting-up) para asegurarte de que la configuración es correcta.

Componentes esenciales necesarios:

- Un `client_secret` válido emitido por Frame.io
- El `client_id` que se te ha asignado, tal como se detalla en la [guía de autenticación y autorización](/es/camera-to-cloud/implementing-c2c-authentication-and-authorization)
- Credenciales `access_token` y `refresh_token` válidas

## Comprender los tokens de autorización {#understanding-authorization-tokens}

Nuestra guía anterior sobre la [autenticación de dispositivos](/es/camera-to-cloud/implementing-c2c-authentication-and-authorization) describía el proceso para obtener los tokens de autorización iniciales mediante la autenticación del usuario.

Los tokens de acceso siguen funcionando durante aproximadamente 8 horas. Para evitar tener que emparejar el dispositivo con frecuencia, utilizamos el ámbito `offline` para obtener un token de actualización junto con la autorización. Este token de actualización permite generar nuevos tokens de acceso cuando caducan.

Los tokens de actualización son válidos durante 14 días. Esta limitación deliberada de la duración de los tokens de acceso mejora la seguridad al minimizar las posibles vulnerabilidades derivadas de tokens comprometidos. Ten en cuenta que, si la autorización no se renueva antes de que caduque el token de actualización, el usuario tendrá que volver a autenticarse.

## Proceso de renovación del token de acceso {#access-token-renewal-process}

Cuando el token de acceso caduque, las solicitudes a la API recibirán esta respuesta:

```json
{
    "code": 401,
    "errors": [
        {
            "code": 401,
            "detail": "You are not allowed to access that resource",
            "status": 401,
            "title": "Not Authorized"
        }
    ],
    "message": "Not Authorized"
}
```

Ejecuta el siguiente comando para obtener un nuevo token:

```shell
curl -X POST https://api.frame.io/v2/auth/token \
    --header 'x-client-version: 2.0.0' \
    --form 'client_id=[client_id]' \
    --form 'client_secret=[client_secret]' \
    --form 'grant_type=refresh_token' \
    --form 'refresh_token=[refresh_token]' \
    | python -m json.tool
```

<Info>

**Especificación del endpoint de la API**

La documentación detallada de `/v2/auth/token` está disponible [aquí](/es/camera-to-cloud/api-reference/authentication/auth-device-token)

</Info>

Esta implementación requiere varios factores de autenticación para mejorar la seguridad. Un tercero no autorizado necesitaría obtener tanto el `refresh_token` como el `client_secret` para suplantar con éxito tu integración.

Una renovación correcta genera esta respuesta:

```json
{
    "access_token": "[access_token]",
    "expires_in": 28800,
    "refresh_token": "[refresh_token]",
    "token_type": "bearer"
}
```

Tras actualizar correctamente el token, tus credenciales anteriores dejan de ser válidas. Asegúrate de almacenar correctamente los nuevos tokens de autorización.

Si intentas reutilizar un token de actualización caducado, obtendrás:

```json
{
    "error": "invalid_request"
}
```

Esto indica que el token ya se ha procesado anteriormente y ya no es válido.

<Danger>

**Recibir un 401 durante una actualización**

Recibir una respuesta `401 Not Authorized` durante la actualización del token indica que las credenciales se han invalidado, por lo que es necesario un nuevo proceso de autorización.

</Danger>

## Gestionar respuestas de actualización fallidas {#handling-failed-refresh-responses}

Dado que los valores de `refresh_token` son de un solo uso, no recibir la respuesta de actualización (ya sea por una interrupción de la red o por el apagado del sistema) obliga a reiniciar toda la secuencia de autenticación y autorización.

Este protocolo de seguridad, aunque pueda resultar incómodo, es esencial para mantener la integridad del sistema.

## Proceso de revocación de tokens {#token-revocation-process}

Determinadas circunstancias pueden requerir que se ponga fin al acceso a Frame.io, como la finalización de un proyecto o el restablecimiento de la aplicación. Implementa procedimientos de revocación adecuados al retirar la autorización actual.

Ejecuta el siguiente comando para revocar la autorización:

<Info>

**Volver a autorizar**

Tras la revocación, debes reiniciar el proceso de autenticación y autorización tal como se describe en la [guía de autenticación y autorización](/es/camera-to-cloud/implementing-c2c-authentication-and-authorization).

</Info>

```shell
curl -X POST https://api.frame.io/v2/auth/revoke \
    --include \
    --header 'x-client-version: 2.0.0' \
    --form 'client_id=[client_id]' \
    --form 'client_secret=[client_secret]' \
    --form 'token=[refresh_token]'
```

<Info>

**Especificación del endpoint de la API**

La documentación completa de `/v2/auth/revoke` está disponible [aquí](/es/camera-to-cloud/api-reference/authentication/auth-device-revoke-token)

</Info>

El sistema devuelve encabezados sin carga útil. Un código de estado `200` indica que la operación se ha realizado correctamente:

```text
HTTP/2 200
...
```

Tras la revocación, las operaciones de Frame.io que requieren autenticación con `access_token` devolverán `Not Authorized`. Para restablecer el acceso, es necesario volver a emparejar el dispositivo con el proyecto.

## Implementación del almacenamiento de tokens {#token-storage-implementation}

Mantener una autorización persistente entre reinicios del sistema requiere un almacenamiento seguro de los tokens. Sigue estas pautas esenciales:

**Implementa controles de acceso de usuario:** restringe la visibilidad y el acceso a los tokens exclusivamente a los procesos de la aplicación.

**Habilita el cifrado del almacenamiento:** cifra los tokens almacenados, incluidos el `client_secret` y las credenciales de autorización. Nunca guardes las claves de autorización en texto sin formato.

**Mantén las credenciales separadas:** aunque nuestra aplicación de demostración en Python centraliza el almacenamiento, en los entornos de producción los tokens de autorización deben separarse del `client_secret`. Ten en cuenta estos factores:

- `client_secret` y `client_id` son credenciales permanentes del dispositivo: su pérdida provoca un fallo permanente del dispositivo
- Los tokens de autorización se actualizan con regularidad durante el funcionamiento del dispositivo
- El almacenamiento separado garantiza que, si se daña el almacenamiento de tokens, solo sea necesario volver a emparejar el dispositivo en lugar de restablecer por completo la autenticación

Aunque SQLite ofrece capacidades óptimas para almacenar tokens, como mínimo implementa un almacenamiento separado para los datos de autorización y las credenciales principales.
