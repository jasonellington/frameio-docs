## はじめに {#introduction}

Frame.io V4 API は、*V2 エンドポイント*や *Frame.io V3 API* とも呼ばれる Legacy API を再設計したものです。この再設計では、Legacy API の関連機能をすべて維持しながら、Frame V4 の新しい機能を最大限に活用しています。このガイドでは、Legacy API と V4 API の主な違いを概説し、スムーズに移行するためのステップバイステップのガイダンスを提供します。

## 移行チェックリスト {#migration-checklist}

<Steps>

<Step title="認証">

Adobe Admin Console でまだ管理されていない <Tooltip tip="生成した開発者トークンで Legacy API を使用しており、V4 に自動移行されたアカウント。V4 で作成されたアカウントや手動で移行されたアカウントは含まれません">**V4 自動移行アカウント**</Tooltip>の場合、[Frame.io 開発者サイト](/ja/platform/welcome)で管理されている Legacy Developer トークンを引き続き使用できますが、API リクエストにキー `x-frameio-legacy-token-auth`、値 `true` のヘッダーを追加する必要があります。それ以外の場合は、以下の[認証](#adobe-developer-console-managed-authentication)セクションの手順に従ってください。

</Step>

<Step title="既存の API 呼び出しを更新する">

すべてのレガシー API ルートを、新しい V4 API のルートと JSON ペイロードにマッピングする必要があります。このプロセスを支援するため、以下にかなり網羅的な[マッピング](#endpoint-mappings-legacy-api-to-v4)表を用意しています。

</Step>

<Step title="テストを強く推奨">

**十分にテストしてください。** API には多くの変更があるため、V4 アカウントでテストして、新しい API が期待どおりに動作することを確認することをお勧めします。

</Step>

<Step title="専用のログインを実装する">

認証 URL が別であるため、V4 専用のログイン方法を実装してください。V4 の認証 URL は Legacy API とは異なり、まだ V4 にアップグレードされていないアカウントはレスポンスに含まれないため、別のインテグレーションとして扱う必要があります。

</Step>

</Steps>

<Note>

以下のマッピング表に記載されていないエンドポイントについてご質問がある場合は、サポートチーム（[support@frame.io](mailto:support@frame.io)）までお問い合わせください。

</Note>

## Adobe Developer Console で管理される認証 {#adobe-developer-console-managed-authentication}

[Adobe Developer Console](https://developer.adobe.com/developer-console/) で管理されている V4 移行済みアカウントの場合は、OAuth 2.0 で V4 API を使用する必要があります。以下の手順に従ってください。

<Steps>

<Step title="Adobe プロジェクトを作成する">

**Adobe Developer Console でプロジェクトを作成**し、製品として Frame.io を追加します。

</Step>

<Step title="認証タイプを選択する">

**認証します。** 詳しくは、[認証ガイド](https://developer.adobe.com/frameio/guides/Authentication/)をご覧ください。V4 アカウントがまだ Adobe Admin Console で管理されていない場合は、この手順をスキップできます。

- **ユーザー認証**：Client ID と Client Secret（またはそのいずれか）を使用して Frame に接続し、ユーザーがユーザー名とパスワードでログインする必要があります。
- **サーバー間認証**：Client ID と Client Secret を使用して Frame に接続しますが、ユーザーがブラウザ経由でログインする必要はありません。

</Step>

<Step title="Bearer 認証を実装する">

**JWT Bearer 認証**：すべての API リクエストで、キー `Authorization`、値 `Bearer <IMS_ACCESS_TOKEN>` のヘッダーを使用して認証トークンを渡します。

</Step>

</Steps>

## エンドポイントのマッピング（Legacy API から V4） {#endpoint-mappings-legacy-api-to-v4}

<Note>

レガシーの開発者トークン認証を使用している場合は、API リクエストにキー x-frameio-legacy-token-auth、値 true のヘッダーを追加する必要があります。

</Note>

移行に役立つ一般的な注意事項：

<Steps>

<Step title="ペイロード">

リクエストとレスポンスのペイロードが異なる場合があります。

</Step>

<Step title="Teams → Workspaces">

Legacy API の「Teams」は、V4 の「Workspaces」に相当します。

</Step>

<Step title="Assets">

Legacy API の「Assets」は、V4 では「Files」、「Folders」、「Version Stacks」に分割されました。

</Step>

<Step title="権限">

V4 では権限とロールが異なるため、エンドポイントの構造が変わります。V4 には、ワークスペースとプロジェクトのユーザーロールがあります。詳しくは、[ユーザー権限の管理](/ja/platform/docs/guides/managing-user-permissions)をご覧ください。

</Step>

</Steps>

### 9. Webhook {#9-webhooks}

V3 で使用していた Webhook は移行され、ほとんどの場合同じように機能します。移行時には無効化されるため、機能させるには有効にする必要があります。アセットのイベントはファイルとフォルダーに分割されたため、いくつかの変更が必要になります。また、注意すべき V4 固有の新しいイベントとして、metadata.value.updated、コレクション関連のイベント、共有関連のイベントがあります。

移行された Webhook を再度有効にする前に、[Webhook のレート制限](/ja/platform/docs/guides/webhooks#webhook-rate-limits)を確認してください。V4 の Webhook と Custom Action のイベントは、アカウントごとに **1 分あたり 1,000 イベント**、**1 時間あたり 20,000 イベント**の制限を共有します。どちらの制限も、アカウント全体での合計量に適用されます。

## 移行手順 {#migration-steps}

<Steps>

<Step title="サポートされていない V2 エンドポイントを調整する">

サポートされていない Legacy V2 エンドポイントを**調整**します。

</Step>

<Step title="ベース URL を更新する">

**ベース URL を** `api.frame.io/v2/...` から `api.frame.io/v4/...` に**更新**します。

</Step>

<Step title="API リクエストを更新する">

コード内の **API リクエストを更新**して、新しいエンドポイントのスキーマを参照するようにします。

</Step>

<Step title="JSON ペイロードを更新する">

リクエスト/レスポンススキーマの **JSON ペイロードを更新**して、正しいフィールドを生成、使用していることを確認します。

</Step>

<Step title="用語を更新する">

コードとフロントエンドの用語を更新します：「teams」→「workspaces」、「assets」→「files/folders」、「review links」または「presentation links」→「shares」。

</Step>

<Step title="エンドポイントをテストする">

新たに更新したすべてのエンドポイントを**テスト**します。403、404、422 が返される場合は、エンドポイントやリクエストペイロードの形式などを確認してください。

</Step>

<Step title="エラーレスポンスを解析する">

API 呼び出しが失敗した場合は、新しい詳細なエラーレスポンスを**解析**し、`{"errors": [...]}` JSON レスポンスで問題を確認します。

</Step>

<Step title="本番環境にデプロイする">

V4 の [Frame.io](http://frame.io/) アカウントで検証が完了したら、本番環境に**デプロイ**します。

</Step>

</Steps>

## エラー処理とよくある問題 {#error-handling-&-common-issues}

<Note>

一部のルートでは、以下の例とは若干異なるカスタムの説明を含むエラーが返される場合があります。

</Note>

<CardGroup cols={2}>

<Card title="クライアントエラー（4xx）" icon="triangle-exclamation" iconType="solid">

- **400** Bad Request：ペイロードが正しいか確認してください。
- **401** Unauthorized：認可トークンが無効か、指定されていません。
- **403** Forbidden：スコープが不足しているか、ユーザーにアクセス権がありません。
- **404** Not Found：エンドポイント、API バージョン、ID を確認してください。
- **422** Unprocessable Entity：リクエストデータを検証してください
- **429** Too Many Requests：バックオフ付きのリトライを実装してください。

</Card>

<Card title="サーバーエラー（5xx）" icon="server" iconType="solid">

- **500** Internal Server Error：少し時間をおいてからリトライしてください。

</Card>

</CardGroup>
