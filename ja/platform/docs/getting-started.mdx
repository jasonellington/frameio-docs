## Adobe Developer Console {#adobe-developer-console}

Adobe API を使用する最初のステップは、Adobe Developer Console で**プロジェクト**を作成することです。Developer Console のプロジェクトは、Frame.io Developer API を利用するために構築するアプリケーションに対応します。これは Frame.io 内のプロジェクトとは別のものです。

## Frame.io V4 Developer API の新機能 {#what’s-new-in-the-frame-io-v4-developer-api}

Frame.io アプリケーションがバージョン 4 で全面的に刷新されたのと同様に、V4 API も一から再設計されました。いくつかの主要な概念はレガシーバージョンと似ていますが、より強力なコラボレーションワークフローや連携をサポートするために、多くの概念が置き換えられたり再設計されたりしています。また、まったく新しい API の導入は、運用を大幅に簡素化し、お客様にとって重要なワークフローを優先する機会にもなりました。

<Info>

Frame.io V4 とレガシーバージョンの比較は[こちら](https://help.frame.io/en/articles/9084073-frame-io-v4-legacy-feature-comparison)をご覧ください。

</Info>

V4 API では、ワークスペース（Frame.io のレガシーバージョンではチームと呼ばれていたもの）など一部のリソースは Frame.io バージョン 4 に合わせて名前が変更されました。また、レガシーバージョンのアセットのように、開発者の混乱を減らすため、特定のストレージエンティティ（ファイル、フォルダー、バージョンスタック）を指す名前に変更されたものもあります。さらに、カスタムフィールドや共有のように、まったく新しいリソースもあります。その他の大きな変更として、リソースのリクエストに対してデフォルトで返されるデータ量を大幅に削減し、API 全体でより正確かつ一貫性のあるものにするためにレスポンス内の一部のプロパティ名を変更し、新しいカーソルベースのページネーションの仕組みに切り替えました。そのため、Camera to Cloud（C2C）API を除き、レガシー API と連携するクライアントは V4 API と互換性がないことを理解しておくことが重要です。

さらに、一部の機能はまだ開発中であり、実際のお客様のユースケースやフィードバックに応じて迅速に追加・進化していく予定です。たとえば、カスタムアクションやバージョンスタックを作成する機能などがあります。以前のレガシー API で利用できた機能が見当たらない場合は、代替手段があるか、近日中に利用可能になる可能性が高いですが、ぜひご意見をお寄せください。

V4 API について詳しく学ぶ前に、まず Frame.io バージョン 4 アプリケーションで表現されている中核的な概念を理解しておくと役立ちます。最初のステップとしては、[Frame.io V4 ナレッジベース](https://help.frame.io/en/)がおすすめです。アカウント、ユーザー、ワークスペース、プロジェクト、コレクション、共有、カスタムフィールド（メタデータ）といった概念は、V4 API ではそれぞれ別個のリソースとしてモデル化されています。アプリケーションにおけるそれらの関係や機能を理解しておくと、V4 API でそれらがどのように動作するかを理解しやすくなります。

## API の概要 {#api-overview}

Frame.io V4 API は RESTful なアーキテクチャの原則に従うように設計されており、標準の HTTP メソッドとレスポンスコードを、リソースごとに固有の URL と組み合わせて使用します。Frame.io は V4 API の [OpenAPI 3.0 仕様](https://api.frame.io/v4/openapi.json)を公開しており、エンドポイント、リクエストパラメーター、レスポンスに関する詳細な情報を提供しています。OpenAPI 仕様はさまざまなサードパーティ製のコード生成ツールで利用でき、クライアントアプリケーションを迅速に開発するのに役立ちます。

### URL とパスの規則 {#url-and-path-conventions}

OpenAPI 仕様で公開されている URL パスは、一般にリソースの所有関係と包含関係を反映しています。そのため、一部のリクエストパラメーター（アカウント ID、フォルダー ID など）はリソースパスに埋め込まれています。これらのパスは予測しやすく理解しやすいことを意図していますが、API リクエストによって返される一部の URL（署名付きアップロード URL や表示リンクなど）の構造は変更される可能性があるため、クライアントアプリケーションで直接組み立てることは決してしないでください。

### リクエストのクエリパラメーター {#request-query-parameters}

ページネーションの動作や、レスポンスオブジェクトに関連リソースを任意で含めるかどうかを制御するリクエストパラメーターは、`include`、`page_size`、`include_total_count` という標準のクエリパラメーターのセットとして定義されています。リクエストによっては、そのリソースや操作に固有の追加のクエリパラメーターをサポートしている場合があります。

```html
GET https://api.frame.io/v4/accounts/{account_id}/folders/{folder_id}/children?&include=project&page_size=5&include_total_count=true
```

### リクエストとレスポンスのペイロード {#request-and-response-payloads}

リクエストとレスポンスのペイロードはどちらも JSON オブジェクトとして構成されるため、HTTP の POST、PUT、PATCH リクエストの content-type ヘッダーには `application/json` メディアタイプを指定する必要があります。リソースを作成または更新する場合、リクエストの `data` プロパティにリソースオブジェクトを含める必要があります。作成または更新するリソースの属性は、このオブジェクト内に含めます。同様に、リソースを含む成功レスポンスでは、レスポンスの `data` プロパティ内にリソースが返されます。

### ページネーション {#pagination}

大量のリソースオブジェクトを返す可能性のあるレスポンス（フォルダーやコメントの一覧など）は、結果セットが大きくなった際のリクエストのレイテンシーを抑えるためにページネーションされます。つまり、リクエストに対するレスポンスには、結果の 1「ページ」分しか含まれない場合があります。前述のとおり、クライアントはリクエスト時に `page_size` クエリパラメーターを使って、最大 100 要素までの特定のページサイズを選択できます。指定しない場合、ページサイズはデフォルトで 50 要素になります。V4 API は*カーソルベースのページネーション*と呼ばれる形式のページネーションを使用しており、レスポンスオブジェクトの `links` プロパティに相対リンクを含めます（以下の例を参照）。このリンクの `after` クエリパラメーターには不透明なカーソル文字列（クライアントがこの文字列を自分で組み立てようとしてはいけません）が含まれており、クライアントは後続のリクエストを行うことで次のページの結果を取得できます（以下のレスポンス例を参照）。現時点では、V4 API は一方向のページネーションのみをサポートしています。

```json
{
    "data": [
        {
            "created_at": "2024-10-02T00:22:44.887775Z",
            "creator_id": "8ea72912-d40d-4b88-8d31-3762e055a2aa",
            "file_size": 102432,
            "id": "df171f3e-c95f-4454-9071-825cd924b572",
            "media_type": "application/pdf",
            "name": "sample.pdf",
            "parent_id": "e183c7ba-07d9-425a-9467-ebdf0223d9ce",
            "project": {
                "created_at": "2024-08-21T17:45:41.881596Z",
                "description": "For demonstration purposes",
                "id": "976dd413-a92b-4af6-b465-98aded0174a8",
                "name": "Demo Project",
                "owner_id": "8ea72912-d40d-4b88-8d31-3762e055a2aa",
                "root_folder_id": "e183c7ba-07d9-425a-9467-ebdf0223d9ce",
                "storage": 20881946,
                "updated_at": "2024-10-02T00:22:47.168489Z",
                "workspace_id": "378fcbf7-6f88-4224-8139-6a743ed940b2"
            },
            "project_id": "976dd413-a92b-4af6-b465-98aded0174a8",
            "status": "created",
            "type": "file",
            "updated_at": "2024-10-02T00:22:44.927993Z"
        }

    "links": {
        "next": "/v4/accounts/6f70f1bd-7e89-4a7e-b4d3-7e576585a181/folders/e183c7ba-07d9-425a-9467-ebdf0223d9ce/children?after=g3QAAAACZAAGb2Zmc2V0YQVkAAR0eXBlZAANb2Zmc2V0X2N1cnNvcg%3D%3D"
```

### エラー {#errors}

エラーが発生した場合、レスポンスオブジェクトの `errors` プロパティには、発生したエラーの詳細を示す 1 つ以上のエラーオブジェクトの配列が含まれます。現時点では V4 API はバッチ操作をサポートしていないため、部分的な成功とエラーをクライアントが処理しなければならないケースはありません。

```json
{
    "errors": [
        {
            "detail": "Unexpected field: foo",
            "source": {
                "pointer": "/data/foo"
            },
            "title": "Invalid value"
        }
    ]
}
```

次の表は、V4 API で使用される一般的なステータスコードの一覧です。

| ステータスコード | **ステータス** | 説明 |
| --- | --- | --- |
| 200 | OK | リクエストが成功しました。 |
| 201 | Created | リソースが作成されました。 |
| 204 | No Content | リソースが削除されました。レスポンスペイロードはありません。 |
| 400 | Bad Request | リクエストが無効です。多くの場合、パラメーターやペイロードの形式が不正であるか、欠落していることが原因です。 |
| 401 | Unauthorized | Authorization トークンが欠落しているか、無効です。 |
| 403 | Forbidden | Authorization トークンに、このリクエストに必要な権限がありません。 |
| 404 | Not Found | リクエストされたリソースは存在しません。 |
| 422 | Unprocessable Entity | リクエストのペイロードやパラメーターの形式は正しいものの、その他の理由で無効なため、リクエストを実行できません（400 Bad Request とほぼ同じ意味で使われます）。 |
| 429 | Too Many Requests | リクエストがこのアカウントの API レート制限を超えました。詳細については、スタートガイドのレート制限のセクションを参照してください。 |
| 5xx | Server Errors | サーバーで予期しないエラーが報告されました。クライアントは、再試行する前に最低 30 秒待機する必要があります。また、自動再試行は回数を制限し、連続するリクエストで指数バックオフを使用することに加えて、ランダムな間隔を含める必要があります。 |

### 認証と認可 {#authentication-and-authorization}

V4 API は、OAuth 2.0 と [Adobe Identity Management Server（IMS）](https://experienceleague.adobe.com/en/docs/commerce-admin/start/admin/ims/adobe-ims-integration-overview)を使用してユーザーを認証（AuthN）し、そのユーザーに代わってアクセストークンを生成します。アクセストークンは、すべての API リクエストで HTTP Authorization ヘッダー（つまり Bearer トークン認証）を通じて提供する必要があります。

<Note>

IMS によって生成される[トークンスコープ](https://developer.adobe.com/developer-console/docs/guides/authentication/UserAuthentication/ims#scopes)は静的です。ユーザーが何を行えるか（およびそのユーザーに代わって API がどの操作を実行できるか）を決定する認可（AuthZ）は、Frame.io 内でユーザーに付与されたロールと権限によって決まります。アクセストークンの生成とリクエストについて詳しくは、「Developer Console の使用を開始する」セクションと、「Postman で開発を始める」の「認証のセットアップ」セクションを参照してください。

</Note>

### バージョンと後方互換性 {#versions-and-backward-compatibility}

Frame.io V4 API は、以前のバージョンの Frame.io API と後方互換性が*ありません*。また、V4 の概念とデータモデルには大幅な変更が加えられているため、一般にレガシーアカウント内のリソースへのアクセスや更新には使用できません。そのため、V4 API に関連付けられた URI にはすべて `/v4` というパスプレフィックスが含まれています。ただし、V4 API は現在も急速に進化しており、新機能によって破壊的変更が必要になる場合もあります。より一般的には、Frame.io は一定期間試験的なものと位置付けた新しい*追加機能*を API にリリースし、お客様のフィードバックや利用状況の指標を受け取って対応できるようにします。高い稼働率が求められる本番品質の連携を管理しているお客様にとって、後方互換性が大きな懸念事項であることを認識しています。そこで、クライアントが試験的なエンドポイントの使用をオプトインし、破壊的変更を回避し、V4 名前空間内で後方互換性の保証を得られるよう、カスタム HTTP ヘッダーによる追加のバージョニングをサポートするように V4 API を設計しています。詳細は今後お知らせしますが、現時点では、V4 API の初期リリースは安定版とみなされており、破壊的変更の導入を検討するのはしばらく先になると考えて問題ありません。

### レート制限 {#rate-limiting}

すべての V4 API 呼び出しにはレート制限があり、API のリソースと操作ごとに独自の制限が設定されています。制限の範囲は、少ないもので 1 分あたり 10 リクエスト、多いもので 1 秒あたり 100 リクエストです。現時点では各制限は*ユーザー*ごとに適用されますが、ポリシーや制限自体は変更される可能性があります。

V4 API は、割り当てられた時間枠の中で制限が徐々に回復する、段階的なレート制限である「[リーキーバケット](https://wikipedia.org/wiki/Leaky_bucket)」アルゴリズムを使用しています。つまり、特定のリソースの制限がリセットされる明確な区切り（「固定ウィンドウ」や「スライディングウィンドウ」による適用方式など）という概念はありません。代わりに、残りの制限は、リソースの制限と時間枠に応じたペースで常に回復し続けます。特定のエンドポイントのレート制限を超えたリクエストは、429 HTTP エラーで失敗します。

429 エラーへの対応として推奨する方法は、一般に「指数バックオフ」と呼ばれるものです。
要約すると次のとおりです。

- `429` を受け取ったら、リクエストを再試行する前に一定期間（少なくとも 1 秒）待機します
- 再び `429` を受け取った場合は、通常の動作が再開するまで、前回の待機時間を指数関数的に（少なくとも 2 倍に）増やします

特定のリクエストに適用されるレート制限を確認するには、クライアントはレスポンスで返される次の HTTP ヘッダーを調べることができます。

| ヘッダー | 値の説明 |
| --- | --- |
| `x-ratelimit-limit` | このリソースパスのレート制限（リクエスト数）。 |
| `x-ratelimit-remaining` | 現在の時間枠で残っているリクエスト数。 |
| `x-ratelimit-window` | このリソースパスの制限の時間枠（ミリ秒（ms））。 |

## API の詳細 {#api-details}

V4 API の決定版ドキュメントは [API リファレンスガイド](/ja/platform/api-reference/account-permissions/account-user-roles-update)ですが、最初のリクエストを送信する前に、V4 API でモデル化されているリソースの階層を理解しておくと役立ちます。

### リソースの階層 {#resource-hierarchy}

[アカウント](https://help.frame.io/en/collections/8779087-account-settings)は通常、組織に関連付けられており、サブスクリプションプラン、コンテンツの所有権、ユーザーのロール／権限、ワークスペースの構成を決定する基本的なリソースです。そのため、V4 API のほぼすべてのエンドポイントの URL パスには、リソースが存在するアカウントを識別するプレフィックスが含まれています。

ワークスペース（Frame.io のレガシーバージョンではチームと呼ばれていたもの）と[プロジェクト](https://help.frame.io/en/articles/9101006-project-settings)は、コンテンツとユーザーの両方を整理するために使用され、誰がどのコンテンツにアクセスできるかも含めて管理します。

Frame.io 内のコンテンツリソースの基本的な階層は次のとおりです。

<CardGroup cols={2}>

<Card title="リソースの階層" icon="sitemap" iconType="solid">

**アカウント → ワークスペース → プロジェクト → フォルダー → フォルダー／バージョンスタック／ファイル**

</Card>

</CardGroup>

Frame.io にアップロードされたすべてのアセットは、最終的に[ファイル](https://help.frame.io/en/articles/9436564-supported-file-types-on-frame-io)として表されます。一方、[フォルダー](https://help.frame.io/en/articles/9101044-creating-folders)と[バージョンスタック](https://help.frame.io/en/articles/9101068-version-stacking)はコンテナとして機能するストレージリソースであり、バージョン管理されたアセットをサポートする階層型ストレージモデルの基盤となります。ほとんどのユーザーは、Frame.io におけるフォルダーの基本的な概念をすでにご存じでしょう。フォルダーは、他のストレージリソース（`children` としてモデル化されます）の順序のないコンテナとして機能し、フォルダーツリー内のノードを表します。すべてのプロジェクトには固有のルートフォルダー（`root_folder_id` キーで識別されます）があり、プロジェクトのすべてのアセットが格納されるフォルダーツリーのルートとして機能します。

バージョンスタックは、ファイルの順序付きコンテナです。その順序は厳密に線形で、各子要素のバージョン番号を決定しますが、クライアントはバージョンスタック内のファイルを自由に並べ替えることができます。ファイルは常に、ある時点でちょうど 1 つのフォルダー*または*バージョンスタックの子要素となります（その中に含まれます）。同様に、フォルダーやバージョンスタックは常に、ちょうど 1 つのフォルダーの子要素となります（プロジェクトのルートフォルダーを除く）。

Frame.io に保存されたファイルとフォルダーに対する基本的な CRUD 操作の実行について詳しくは、[API リファレンスガイド](https://developer.frame.io/platform/api/current)を参照してください。現時点では、V4 API がバージョンスタックをサポートしているのはフォルダーの内容を一覧表示する場合のみですが、バージョンスタックを作成・更新するためのエンドポイントも近日中に提供される予定です。

TypeScript と Python 向けの SDK が利用できます。以下のコマンドを使用してインストールできます。ドキュメントの SDK リファレンスセクションには、[Python](/ja/platform/docs/sdk-reference/python-sdk-reference) SDK と [TypeScript](/ja/platform/docs/sdk-reference/type-script-sdk-reference) SDK の完全なリファレンスがあります。

```bash
npm i -s frameio
```

```bash
pip install frameio
```
