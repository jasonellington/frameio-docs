## Webhookとは? {#what’s-a-webhook}

**Webhook** は、アカウント内で **注目すべきことが起きるとすぐに** Frame.ioが送信するプッシュ型のHTTPコールバックです(例: 新しいファイルのトランスコードが完了した、コメントが追加された、プロジェクトが作成された、など)。
APIをポーリングする代わりに公開HTTPSのURLを指定すると、Frame.ioがそのURLにJSONペイロードをリアルタイムで送信するため、次のようなことが可能になります。

<CardGroup cols={2}>

<Card title="外部のDAM/MAMにメタデータを同期する" icon="arrows-rotate" iconType="solid" />

<Card title="Slackチャンネルやチケットシステムに情報を投稿する" icon="bell" iconType="solid" />

</CardGroup>

Webhookとは何か、何ができるのかについて詳しくは、[https://docs.webhook.site/](https://docs.webhook.site/)を参照してください。

## エンドポイントの概要 {#endpoint-overview}

| **操作** | **エンドポイント** | **詳細** |
| --- | --- | --- |
| Webhookを **作成** | POST /v4/accounts/\{account_id\}/workspaces/\{workspace_id\}/webhooks | `name`、`url`、`events[]`を含むボディ |
| ワークスペースのすべてのWebhookを **一覧表示** | GET /v4/accounts/\{account_id\}/workspaces/\{workspace_id\}/webhooks | ページネーションに対応 |
| 1つのWebhookを **表示** | GET /v4/webhooks/\{webhook_id\} | 署名シークレットは作成時にのみ返されます |
| Webhookを **更新** | PATCH /v4/webhooks/\{webhook_id\} | `url`、`events`、`is_active`を変更 |
| Webhookを **削除** | DELETE /v4/webhooks/\{webhook_id\} | 配信を即座に停止 |

<Warning>

**認証** — すべてのV4エンドポイントには、Adobe Developer Consoleで取得したOAuth 2.0アクセストークンが必要です。従来の開発者トークンやJWTは **使用できません**。

</Warning>

## Frame V4での変更点と更新点 {#changes-and-updates-in-frame-v4}

<Info>

Legacyで作成されたWebhookは、次の変更が加えられた状態でV4に移行されます。

1. **ペイロードの構造**: ペイロードにAccount IDが追加されました
2. **エンドポイントの変更**: `team_id`はJSONペイロードで提供されなくなり、代わりにURLのパスパラメーターに含まれます: `https://api.frame.io/v4/accounts/:account_id/workspaces/:workspace_id/webhooks`
3. **APIとの連携**: API構造、エンドポイント、認証方法の変更により、受信したWebhookを処理する既存のコードのうち、リソースの情報補完や検索のためにFrame.io APIを後続で呼び出しているものは更新が必要です
4. **イベントタイプ**: AssetのWebhookは、FileイベントとFolderイベントに分割されました。Legacyから移行された、Assetイベントを使用するWebhookは、適切なFileイベントとFolderイベントを使用するように更新する必要があります

</Info>

<Warning>

**移行後のWebhookのステータス** — アカウントがFrame.io V4に移行されると、以前のバージョンの既存のWebhookは自動的に無効になります。これにより、再度有効にする前に、WebhookのエンドポイントとインテグレーションのロジックをV4の更新内容に合わせて修正できます。V4との互換性のための更新が行われていないWebhookを、適切な修正なしに有効にするとエラーが発生します。どのWebhookが無効になっているかは、APIで`is_active`フィールドを確認するか、再度有効にする前に[Webhookの設定](https://next.frame.io/settings/webhooks)を確認することで把握できます。

</Warning>

## Webhookのイベントサブスクリプション {#webhook-event-subscriptions}

Webhookを作成または更新する際は、関心のあるイベントを指定します。イベントはいくつでも選択できますが、購読するイベントは少ないほうが扱いやすくなります。異なる命名規則と異なるエンドポイントを使ってWebhookを論理的に分割しておくと、受信側でビジネスロジックを構成しやすくなり、共有関数でのフィルタリングやルーティングを減らせます。

<Note>

イベントのスコープ — すべてのイベントは、Webhookの作成時に指定したWorkspaceにスコープされます。つまり、そのWorkspace内のすべてのプロジェクトで行われた操作についてイベントが送信されます。

</Note>

## Webhookメッセージのペイロード {#webhook-message-payload}

すべてのWebhookペイロードには、発生したイベントを示す`type`フィールドと、`resource`オブジェクトが含まれます。`resource`オブジェクトには、イベントに関連するFrame.ioリソースの`type`と`ID`が含まれます。

### ペイロードの例 {#example-payload}

```json
{
  "account": {
    "id": "6f70f1bd-7e89-4a7e-b4d3-7e576585a181"
  },
  "project": {
    "id": "7e46e495-4444-4555-8649-bee4d391a997"
  },
  "resource": {
    "id": "d3075547-4e64-45f0-ad12-d075660eddd2",
    "type": "file"
  },
  "type": "file.ready",
  "user": {
    "id": "56556a3f-859f-4b38-b6c6-e8625b5da8a5"
  },
  "workspace": {
    "id": "378fcbf7-6f88-4224-8139-6a743ed940b2"
  }
}
```

上記の`file.created`イベントの例では、`resource.id`が新しく作成されたFileの`ID`を示しています。さらに、`workspace`、`project`、`user`の各オブジェクトが含まれており、関連する`workspace.id`、`project.id`、`user.id`が格納されています。これらの値を使って受信したイベントをフィルタリングしたり、ローカルにキャッシュしたデータを参照したりすることで、API呼び出しを減らせます。

<Warning>

**購読しているリソースについて、リソースID以外の追加情報は含まれません**。

アプリケーションで追加の情報やコンテキストが必要な場合は、APIを呼び出して、参照されているリソースの詳細情報を取得することを推奨します。

</Warning>

## セキュリティ {#security}

デフォルトで、すべてのWebhookには署名キーがあります。この設定変更できない署名シークレットを使用して、リクエストがFrame.ioから送信されたものであることを検証できます。

設定したWebhookのレスポンスペイロードには、そのWebhook固有の署名シークレットが含まれます。このシークレットは **Webhookを作成したときの最初のレスポンスでのみ提供される** ため、シークレットストレージや環境変数など安全な場所に保存してください。後でこれを使用して、Webhookが当社のサーバーから直接送信されたものであり、傍受や改ざんを受けていないことを検証します。

### Webhook署名の検証 {#verifying-webhook-signatures}

中間者攻撃やリプレイ攻撃からインテグレーションを保護するには、Webhookペイロードの署名を検証することが不可欠です。検証により、Webhookペイロードが実際にFrame.ioから送信されたものであり、転送中にペイロードの内容が変更されていないことを確認できます。

`POST`リクエストには、次のHTTPヘッダーが含まれます。

| ヘッダー名 | 説明 | 例 |
| --- | --- | --- |
| `X-Frameio-Request-Timestamp` | リクエストが送信されたタイムスタンプ | `1604004499` |
| `X-Frameio-Signature` | 計算されたWebhook署名 | `v0=a77ce6856e609c884575c2fd211d07a9ad1c3f72e19c06ff710e8f086ffca883` |
| `user-agent: "Frame.io V4 API"` | V4のヘッダーに含まれるユーザーエージェント |  |
| `user-agent: "Frame.io Legacy API"` | Legacyのヘッダーに含まれるユーザーエージェント |  |

```python title="Python"
import hmac
import hashlib

def verify_signature(curr_time, req_time, signature, body, secret):
    """
    Verify Webhook signature
    :Args:
        curr_time (float): Current epoch time
        req_time (float): Request epoch time
        signature (str): Signature provided by the Frame.io API for the given request
        body (str): Webhook body from the received POST
        secret (str): The secret for this Webhook that you saved when you first created it
    """
    if int(curr_time) - int(req_time) < 500:
        message = 'v0:{}:{}'.format(req_time, body)
        calculated_signature = 'v0={}'.format(hmac.new(
            bytes(secret, 'latin-1'),
            msg=bytes(message, 'latin-1'),
            digestmod=hashlib.sha256).hexdigest())
        if calculated_signature == signature:
            return True
    return False
```

**タイムスタンプ** は、送信Webhookが送られた時点のFrame.ioのシステム時刻です。これを使用して[リプレイ](https://en.wikipedia.org/wiki/Replay_attack)攻撃を防止できます。この時刻がローカル時刻から5分以内であることを確認することを推奨します。

**署名** は、Webhookの初回作成時に提供された署名キーを使用したHMAC SHA256ハッシュです。

**署名を検証するには、次の手順に従います。**

<Steps>

<Step title="署名を抽出する">

HTTPヘッダーから署名を抽出します。

</Step>

<Step title="署名対象のメッセージを作成する">

バージョン、配信時刻、リクエストボディを組み合わせて、署名対象のメッセージを作成します: `v0:timestamp:body.`

</Step>

<Step title="HMAC SHA256を計算する">

署名シークレットを使用して、HMAC SHA256署名を計算します。

</Step>

<Step title="署名を比較する">

計算した署名と、提供された署名を比較します。

</Step>

</Steps>

<Note>

提供される署名には`v0=`というプレフィックスが付いています。現在、Frame.ioでリクエストの署名に使用しているバージョンはこの1つだけです。計算した署名の先頭にこのプレフィックスを付けるようにしてください。

</Note>

## Webhookのレート制限 {#webhook-rate-limits}

WebhookイベントとCustom Actionイベントは、アカウントごとに次の制限を共有します。

| 期間 | アカウントごとの上限 |
| --- | --- |
| 1分 | 1,000イベント |
| 1時間 | 20,000イベント |

どちらの制限も、WebhookイベントとCustom Actionイベントを合算した量に適用されます。1分あたりの制限内に収まっていても、1時間あたりの制限が免除されるわけではありません。これらの制限はアカウントレベルで適用され、Webhookサブスクリプションや Custom Action ごとに個別に適用されるものではありません。

これらはイベント量に対する制限であり、WebhookサブスクリプションやCustom Actionの作成、一覧表示、更新、削除に関するAPIリクエストの制限ではありません。

<Warning>

いずれかのアカウントレベルの制限に達すると、それ以降のWebhookイベントとCustom Actionイベントは後で配信するためにキューに入れられるのではなく、**破棄** されます。破棄されたイベントは、処理能力に余裕ができても自動的にリトライまたは再送されません。以下の配信リトライポリシーは、レート制限によって破棄されたイベントには適用されません。

</Warning>

### 制限内で運用する {#working-within-the-limits}

Webhookの制限内で運用するには、インテグレーションに必要な **[イベント](#webhook-event-subscriptions)** のみを購読することを推奨します。たとえば、ファイルのアップロード完了時にワークフローを開始する場合は、すべてのファイルイベントではなく`file.upload.completed`を購読します。アカウントのサブスクリプションを定期的に見直し、使用されなくなったものは削除してください。

インテグレーションで多数のファイルをアップロードしたり、一連の更新を行ったりする場合は、可能な範囲で処理を分散させて両方の制限内に収め、他のアカウントアクティビティのための余裕を残してください。これにより、リトライされないイベントの破棄を回避しやすくなります。

## Webhookチュートリアル {#webhook-tutorial}

### ステップ1: 受信側をセットアップする(URLを把握するために最初に行います) {#step-1-setup-receiving-end-done-first-so-that-you-know-what-your-url-will-be}

ここでは[webhook.site](http://webhook.site/)を使用します。webhook.siteを使うと、ペイロードの確認や、実際のビジネスロジックを伴わない基本的なレスポンスの送信に使える使い捨てのWebhookレシーバーを簡単に立ち上げられます。初めて[https://webhook.site](https://webhook.site/)にアクセスすると、固有のWebhookエンドポイントが作成されるので、すぐにコピーして使用できます。

このURLはセッションごとに固有です。

<Frame>

![Step 1 Example](/images/platform/docs/guides/webhooks/webhook_site_example.gif)

</Frame>

### ステップ2: 購読するイベントを選択する {#step-2-choose-the-events-you-want-to-subscribe-to}

このチュートリアルではシンプルに、`file.created`イベントのみを購読するWebhookをセットアップします。Webhookの作成に使用するJSONペイロードは次のとおりです。

```json
{
    "data": {
        "name": "asset.created sample webhook",
        "events": ["file.created"],
        "url": "https://webhook.site/c05f2216-9558-4816-bc09-f77ee7b9de40"
    }
}
```

### ステップ3: Postmanを使ってWebhookリソースを作成する {#step-3-create-a-webhook-resource-using-postman}

Postmanを使用してAPIを呼び出し、ペイロードに[webhook.site](http://webhook.site/)のエンドポイントを指定してWebhookリソースを作成します。

### ステップ4: テストする {#step-4-test}

Webhookサブスクリプションを作成し、Webhookを受信するエンドポイントのセットアップも完了したので、Webhookが発火する操作を実際に行い、最初のWebhookをトリガーしてテストしてみましょう。

このサンプルは`file.created`トリガーで発火するように設定しているので、Webhookを設定したAccountとWorkspace内の任意のProjectに新しいアセットをアップロードします。
