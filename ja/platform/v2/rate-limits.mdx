# 概要 {#overview}

トークンが開発者ポータル、OAuth による付与、あるいは Frame.io 自身のアプリケーションを支える Accounts バックエンドのいずれから発行されたものであっても、**Frame.io へのすべての API 呼び出しにはレート制限が適用されます。**

レート制限は、個々のユーザーからのあらゆる API リクエストに対して(使用するトークンや認証方法に関係なく)適用され、段階的に消費・補充され、Frame.io API へのすべてのリクエストのレスポンスヘッダーに反映されます。各エンドポイントには独自の制限が設定されており、その範囲は低いもので `10` リクエスト/分、高いもので `100` リクエスト/秒です。

特定のエンドポイントのレート制限を超えたリクエストには、レスポンスとして `429` HTTP エラーが返されます。

## 消費と補充 {#depletion-and-refill}

Frame.io API は、段階的なレート制限の手法として [leaky bucket](https://wikipedia.org/wiki/Leaky_bucket) 方式を採用しており、制限は割り当てられた時間枠の中で徐々に回復します。言い換えると、特定のリソースについて、ある時点を境に制限がリセットされるという厳密な区切りの概念(つまり「固定ウィンドウ」や「スライディングウィンドウ」の適用方式)はありません。代わりに、残りの制限は、リソースの制限と時間枠に応じたペースで常に回復し続けます。

### 指数バックオフ {#exponential-backoff}

レート制限への対処として推奨される方法は、一般に「指数バックオフ」と呼ばれるものです。

簡単に言うと、次のとおりです。

- `429` を受け取ったら、一定時間(通常は 1 秒)待機します
- 再び `429`  を受け取った場合は、通常の動作が再開されるまで、待機時間を指数関数的に増やします

## ヘッダー {#headers}

API リクエストへのレスポンスには、送信するリクエストを制限するために活用すべき次の 3 つのヘッダーが常に含まれます。

| ヘッダー | 値 |
| --- | --- |
| `x-ratelimit-limit` | このリソースパスのレート制限で、リクエスト数で表されます。 |
| `x-ratelimit-remaining` | 現在の時間枠で残っているリクエスト数です。 |
| `x-ratelimit-window` | このリソースパスの制限の時間枠で、ミリ秒(ms)で表されます。 |

### 例 {#example}

次の例は、Project ルート、フォルダー、またはバージョンスタックの子 Asset を取得する `GET v2/assets/:id/children` のレスポンスからのものです。このパスの制限は 60,000 ms(1 分)あたり 40 リクエストで、1 回リクエストを行った後の残りは 39 リクエストです。

```
x-ratelimit-limit → 40
x-ratelimit-remaining → 39
x-ratelimit-window → 60000
```

## 詳細 {#details}

レート制限は、Frame.io API のリソースパスによって大きく異なります。以下に、読みやすさのためにリソースとアクションで表した(例: `PUT /assets/:id` ではなく「Assets — Update」)いくつかの詳細を示します。

一般的なルールとして、新しいデータを作成するリソースパスは 1 分あたり 100 回以下に制限され、Asset の一覧を取得するリソースパスは 1 分あたり 200 回に制限されます。

| リソース | アクション | 制限(リクエスト数) | 制限の時間枠(ms) |
| --- | --- | --- | --- |
| **Assets** | `create` | `5` | 1,000 |
| **Assets** | `update` | `10` | 1,000 |
| **Assets** | `read` | `5` | 1,000 |
| **Comments<br />Presentations<br />Projects<br />Review Links<br />Teams<br />Team Members** | `create` | `100` | 60,000 |
| **Search** | `read` | `200` | 60,000 |
