## Camera to Cloud API とは {#what-is-the-camera-to-cloud-api}

Camera to Cloud (C2C) API は、収録が完了した直後に、ユーザーによる追加の操作を必要とせずにメディアを Frame.io へ直接送信するための安全な手段を提供します。Frame.io では、収録が停止した時点、またはメタデータが入力された時点で、すぐにメディアをレビューやコラボレーションに利用できるようにすることを目指しています。

開発の過程で、インテグレーターとユーザーの双方に最高の体験を提供するには、C2C API を Frame.io のメインのエコシステムから切り離された、独自の専用バックエンドシステムとして機能させる必要があると判断しました。このアーキテクチャ上の決定は一見すると直感的ではないかもしれませんが、本ドキュメントでは C2C の背後にある指針を紹介しながら、その理由を説明します。

## カメラ映像だけではない {#beyond-camera-footage}

わかりやすさと認知度のために「Camera to Cloud」という名前が付けられていますが、この API の機能はカメラ映像にとどまりません。C2C API はさまざまな種類のデジタルコンテンツを扱えます。お使いのデバイスがオーディオ、ビデオ、PDF、その他どのような種類のファイルを生成する場合でも、Frame.io はそれらすべてに対応できます。この API は、あらゆるデジタルアセットを作成からクラウドストレージまで、最小限の手間で転送できるようにします。

## 書き込みのみ、読み取りはしない {#write-but-don’t-read}

Frame.io は高いセキュリティ基準を維持しており、デバイスの接続性を導入することには潜在的なセキュリティ上の考慮事項が伴います。多くのメディアキャプチャデバイスは、もともとネットワーク接続を前提に設計されていないため、パスワードや画面ロックといった従来のセキュリティ機能を備えていません。こうしたデバイスに Frame.io API へのフルアクセスを与えると、放置された場合にセキュリティ上の脆弱性を生む可能性があります。

さらに、デバイスのオペレーターは多くの場合、プロジェクト全体ではなく特定の要素へのアクセスだけを必要とします。その役割は、プロジェクト全体の管理ではなく、特定のメディアアセットの作成に限られることがあります。

このことから、私たちの中核となる設計原則が生まれました。収録デバイスは主にメディアを作成するために存在し、他のソースからのコンテンツをレビューしたりコメントしたりするためのものではない、という原則です。最善のセキュリティアプローチは、その本質的な機能、つまりクラウドへのデータのアップロードに特化して制限された API を開発することでした。読み取り機能を完全に排除することで、機密性の高いプロジェクト情報への不正アクセスを効果的に防止しました。

## インターフェースが限られたデバイス向けの設計 {#designing-for-devices-with-limited-interfaces}

Frame.io の既存の API は、グラフィカルユーザーインターフェースを備えたアプリケーションと連携することを前提に設計されていました。そうしたアプリケーションはユーザーに選択肢を表示でき、ユーザーが行った選択がサーバーに送信されます。

しかし C2C エコシステムには、GUI 機能が限られている、またはまったくない物理デバイスや、ユーザー入力の手段を持たない可能性のあるデバイスが含まれます。そのため、ユーザーとのインタラクションに対して根本的に異なるアプローチが必要でした。

C2C を設計するにあたり、インターフェース機能が限られたデバイス上でも効果的に機能するシステムを構築する必要がありました。つまり、多くの場合デバイス上での入力は不可能である可能性があるため、デバイス自体でのユーザー入力を必要としないインタラクションモデルを開発する必要がありました。

この制約により、Web ベースの認証フローとユーザーによるアップロード先フォルダーの選択に依存していた既存の API アーキテクチャを使用することはできなくなりました。デバイスが実行できるアクションだけでなく、それらのアクションを取り巻くユーザー体験全体を簡素化する必要があったのです。

## 断続的な接続への対応 {#accommodating-intermittent-connectivity}

インターフェースの制約に加えて、C2C エコシステムの多くのデバイスは、ネットワーク接続が予測できない環境で動作します。私たちは、バックエンドとの通信を最小限に抑えるよう API を設計し、動作中に必要な呼び出しの数を減らすことで、Wi-Fi やモバイル通信が限られたリモートの現場で作業するプロフェッショナルにも信頼性の高い体験を提供できるようにしました。

## 統合の簡素化 {#simplifying-integration}

私たちが優先したのは、統合をできる限りシンプルにすることでした。最小限のエンドポイント、限られたサーバーとのネゴシエーション要件、そして目的に沿って狭く定義されたスコープを持つ、焦点を絞った API を開発しました。インテグレーターによっては、サードパーティのネットワーク呼び出しを実装するのはこれが初めてという場合もあるでしょう。効率的な実装を求める経験豊富な開発者の方も、REST API が初めての方も、利用しやすくわかりやすい体験になるよう設計しています。
