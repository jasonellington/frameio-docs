## はじめに {#introduction}

API リクエストを始める前に、C2C 統合の基本的なアーキテクチャを理解しておく必要があります。(ご安心ください。次の記事ではターミナルで作業します。ここでは、まず重要な概念を説明します。)

統合の簡略化されたデータモデルは、おおよそ次のようになります。

```text
                                   ┌───────────────────┐    ┌─────────┐
                                   │ Project Device 01 │ -> │ Project │
┌───────────┐    ┌──────────────┐  └───────────────────┘    └─────────┘
│ Oauth App │ -> │ Device Model │ ──────────⭥
└───────────┘    └──────────────┘  ┌───────────────────┐    ┌─────────┐
                                   │ Project Device 02 │ -> │ Project │
                                   └───────────────────┘    └─────────┘
```

## OAuth アプリ {#oauth-apps}

統合は OAuth アプリによって定義されます。OAuth アプリは私たちのバックエンドに登録されるエンティティで、デバイスが [OAuth 2](https://oauth.net/2/) を使用して Frame.io で自身を認可できるようにします。OAuth アプリは、統合全体の認可戦略を定義します。ユーザーが Frame.io に接続するすべてのデバイスは、同じ OAuth アプリを通じて認可されます(ただし、複数のデバイスラインを持つインテグレーターは、ラインごとに OAuth アプリを用意したほうがよい場合もあります)。

C2C 統合では、UI 機能が限られたデバイス向けに特別に設計された専用の OAuth フローを使用します。

### C2C デバイス認証 {#c2c-device-authentication}

C2C API は、UI 機能が限られたデバイス向けに設計されています。これらのデバイスは 6 桁のコードを表示し、ユーザーがそのコードを自身のブラウザーで Frame.io の Web サイトに入力することで、デバイスを Frame.io に接続できます。

デバイスには `client_secret` が発行され、6 桁の認可コードを受け取るにはこれを私たちのバックエンドに提供する必要があります。この合理化されたアプローチにより、すべての C2C 統合で一貫性のある安全な認証体験が保証されます。

## デバイスモデル {#device-models}

デバイスモデルは、サポートする機能を含め、デバイスが C2C バックエンドとやり取りする際の動作を設定します。デバイスモデルでは次の設定を行います。

</Card>

<Card title="パス名" icon="folder" iconType="solid">

</Card>

<Card title="必須メタデータ" icon="list" iconType="solid">

アセットを Frame.io にアップロードする際に必須となるメタデータです。主にトークン化されたファイルパスをサポートするために使用されます。

</Card>

</CardGroup>

<CardGroup cols={2}>

<Card title="ソケットステータス" icon="plug" iconType="solid">

統合が現在のステータスを伝えるために、低レイテンシのソケットを使用するか、より高レイテンシの REST 呼び出しを使用するかを指定します。

デバイスがサポートする機能は、ファームウェアのバージョンによって変わることがあります。後方互換性とわかりやすいユーザー体験を実現するため、デバイスの設定は検出されたファームウェアバージョンに基づいて動的に選択されます。近い将来、1 つの統合で複数の DeviceModel を持てるようになる予定です。どのデバイスモデルが使用されるかは、デバイスのファームウェアバージョンと、特定のデバイスモデルが要求する最小ファームウェアバージョンを比較して決定されます。

## プロジェクトデバイスと識別 {#project-devices-and-identification}

`ProjectDevice` は、Frame.io に接続されたデバイスの物理的なインスタンスそれぞれを表します。

`ProjectDevice` は、`client_id` と呼ばれる一意の識別値を使用して自身を識別します。この値は、2 台のデバイス間で共有されないことが保証されたものである必要があります。デバイスのシリアル番号や、デバイスが一度生成して保存するランダムな文字列などを使用できます。`client_id` には、コンピューターの MAC アドレスなど、デバイスが所有していない値を使用してはいけません。

私たちのバックエンドは各プロジェクトデバイスを追跡し、現在のファームウェアバージョンなどの情報を保存します。

各 `ProjectDevice` には、特定の Frame.io `Project` が関連付けられます。また、デバイスにプロジェクトへのアクセスを許可する `OauthAuthorization` と、デバイスに許可されている操作を定める一連のスコープも関連付けられます。利用可能なスコープの詳細については、認証と認可の実装に関する詳細ガイドをご覧ください。

`/me` エンドポイントから返されるのは `ProjectDevice` です。1 つの `Device` が同時にアクティブにリンクできるのは 1 つの `ProjectDevice` のみであり、したがって同時にリンクできる `Project` も 1 つだけです。

## ファームウェアバージョン {#firmware-versions}

`https://api.frame.io` のエンドポイントを呼び出す際には、デバイスは常に `x-client-version` HTTP ヘッダーで現在のファームウェアバージョンを提供する必要があります。以降の API ガイドでは、各例にこのヘッダーを含めています。

場合によっては、私たちのバックエンドで複数のファームウェアバージョンを並べ替える必要があります。これをサポートするため、値は有効な[セマンティックバージョン](https://semver.org/)でなければなりません(MUST)。たとえば、`0.1.2`、`2.1.3-preview.01`、`2.1.3-preview.01+build_19770504.01` などの値が該当します。

ファームウェアバージョンの値が有効なセマンティックバージョンでない場合は、エラーが返されます。すべての統合がセマンティックバージョニングでファームウェアを管理しているわけではないことは理解しています。そのような場合は、作成する各内部バージョンに対応するセマンティックバージョンを管理し、それを私たちのバックエンドに提供してください。

このヘッダーを提供することで、ファームウェアのリリースごとに、Frame.io 内で異なる(場合によっては相反する)機能をサポートできます。

<Info>

**ヘッダーのホスト**

ファームウェアバージョンは [https://api.frame.io](https://api.frame.io) への呼び出しでのみ処理されます。[https://applications.frame.io](https://applications.frame.io) への呼び出しでは、このヘッダーは効果がありません。

</Info>

<Info>

**現在の要件**

`x-client-version` は現在必須の HTTP ヘッダーとなっており、Frame のサーバーによって強制されます。

</Info>
