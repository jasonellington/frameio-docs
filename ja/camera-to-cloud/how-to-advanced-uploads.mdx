## はじめに {#introduction}

信頼性の高いアセットのアップロードは、あらゆる C2C インテグレーションの中核となる機能です。このガイドでは、厳しい環境でも良好に動作する、堅牢で回復力があり効率的なアップロードシステムを構築するための応用テクニックとベストプラクティスを紹介します。

## 前提条件 {#prerequisites}

まだご覧になっていない場合は、先に進む前に [Implementing C2C: Setting Up](/ja/camera-to-cloud/implementing-c2c-setting-up) ガイドを確認してください。

[認証と認可のプロセス](/ja/camera-to-cloud/implementing-c2c-authentication-and-authorization)で取得した `access_token` が必要になります。

引き続き、[基本的なアップロードガイド](/ja/camera-to-cloud/how-to-basic-upload)と[同じテストアセット](https://f.io/Rq1q5CzB)を使用します。

## 高度なアセットパラメーター {#advanced-asset-parameters}

Frame.io でアセットを作成する際、いくつかの高度なパラメーターを使用してアップロードの動作をカスタマイズできます。適切なインテグレーションのためには、特に `offset` パラメーターが重要です。

### Offset - 一時停止中のデバイスへの対応 {#offset---handling-paused-devices}

正確な `offset` 値を指定することは非常に重要です。このパラメーターはメディアが作成された時点を指定し、共有すべきでないコンテンツをデバイスがアップロードしないようにします。Frame.io でデバイスが一時停止されている場合、ユーザーは一時停止中に作成されたメディアをアップロードすべきではないと示しています。詳しくは、[一時停止機能に関するガイド](/ja/camera-to-cloud/how-to-heartbeats-connection-info-and-status#managing-the-paused-status)を参照してください。

### offset パラメーターのその他の利点 {#additional-benefits-of-the-offset-parameter}

`offset` パラメーターには、Frame.io 内でメディアを整理するうえでもう 1 つの大きな利点があります。以前の日付に撮影されたコンテンツをアップロードする場合 (たとえば、ユーザーが再生中に前の週に撮影した写真を選択した場合)、`offset` パラメーターによって、このメディアは現在のアップロード日ではなく、元の撮影日に対応するフォルダーに表示されます。

この時系列に沿った整理により、Frame.io のプロジェクト構造で論理的なタイムラインが維持されます。`offset` パラメーターがないと、過去のメディアが今日のコンテンツと誤ってまとめて表示され、エディターや他のコラボレーターを混乱させる可能性があります。

インターフェースを通じて、この点についてユーザーに選択肢を提供することもできます。メディアの撮影時期にかかわらず、すべてのアップロードを現在の日付で整理したいユーザーには、`offset` パラメーターを省略するだけで対応できます。指定しない場合のデフォルトは `0` です。

当社の API 設計では、デバイスが一時停止状態を追跡する必要はありません。代わりに、ファイルをアップロードする際に、そのファイルが何秒前に作成されたかを指定します。当社のサーバーはこれを一時停止期間と照合し、一時停止中に作成されたものであればアップロードを拒否します。

この機能を試すには、C2C Connections タブの三点メニューからデバイスを一時停止します。

次に、アセットのアップロードを試みます。

```shell
{
curl -X POST https://api.frame.io/v2/devices/assets \
    --header 'Authorization: Bearer [access_token]' \
    --header 'Content-Type: application/json' \
    --header 'x-client-version: 2.0.0' \
    --data-binary @- <<'__JSON__' 
        {
            "name": "C2C_TEST_CLIP.mp4", 
            "filetype": "video/mp4", 
            "filesize": 21136250,
            "offset": 0
        }
__JSON__
} | python -m json.tool
```

<Info>

**API エンドポイントの仕様**

`/v2/devices/assets` のドキュメントは[こちら](/ja/camera-to-cloud/api-reference/device-asset-create)にあります。

</Info>

次のエラーが返されます。

```json
{
    "code": 409,
    "errors": [
        {
            "code": 409,
            "detail": "The channel you're uploading from is currently paused.",
            "status": 409,
            "title": "Channel Paused"
        }
    ],
    "message": "Channel Paused"
}
```

デバイスの一時停止を解除して同じリクエストを再試行すると、アセットが作成されます。

ただし、アセットが一時停止期間中に作成されたものである場合は、実際に作成された時点を反映するように `offset` を設定する必要があります。

```shell
{
curl -X POST https://api.frame.io/v2/devices/assets \
    --header 'Authorization: Bearer [access_token]' \
    --header 'Content-Type: application/json' \
    --header 'x-client-version: 2.0.0' \
    --data-binary @- <<'__JSON__' 
        {
            "name": "C2C_TEST_CLIP.mp4", 
            "filetype": "video/mp4", 
            "filesize": 21136250,
            "offset": 60
        }
__JSON__
} | python -m json.tool
```

これにより、アセットが 60 秒前 (一時停止中) に作成されたことが Frame.io に伝わり、正しく `Channel Paused` エラーが発生します。

保護された知的財産、機密性の高い映像、その他の制限された素材など、ユーザーの意に反して機密コンテンツがアップロードされるのを防ぐには、*正確な `offset` 値が不可欠です*。

<Danger>

**Offset と再試行**

失敗したアセット作成の呼び出しを再試行する際は、`offset` 値を更新することを忘れないでください。再試行の期間が長くなると、固定された offset が該当する一時停止期間から外れてしまい、本来ブロックされるべきアップロードが許可されてしまう可能性があります。

</Danger>

### 特定のチャンネルへのアップロード {#uploading-to-a-specific-channel}

デバイスに複数のチャンネルがある場合は、使用するチャンネルを指定できます。

```shell
{
curl -X POST https://api.frame.io/v2/devices/assets \
    --header 'Authorization: Bearer [access_token]' \
    --header 'Content-Type: application/json' \
    --header 'x-client-version: 2.0.0' \
    --data-binary @- <<'__JSON__' 
        {
            "name": "C2C_TEST_CLIP.mp4", 
            "filetype": "video/mp4", 
            "filesize": 21136250,
            "offset": -10,
            "channel": 2
        }
__JSON__
} | python -m json.tool
```

指定しない場合、デフォルトのチャンネルは `0` です。ほとんどのインテグレーションでは、この値を変更する必要はありません。

### カスタムのチャンク数をリクエストする {#requesting-a-custom-chunk-count}

デフォルトでは、Frame.io のバックエンドはファイルを約 25MB のチャンクに分割します。輻輳の激しいネットワークでは、より小さいチャンクのほうが望ましい場合があります。`parts` パラメーターを使用して、特定のチャンク数をリクエストできます。

```shell
{
curl -X POST https://api.frame.io/v2/devices/assets \
    --header 'Authorization: Bearer [access_token]' \
    --header 'Content-Type: application/json' \
    --header 'x-client-version: 2.0.0' \
    --data-binary @- <<'__JSON__'
        {
            "name": "C2C_TEST_CLIP.mp4",
            "filetype": "video/mp4",
            "filesize": 21136250,
            "offset": 0,
            "parts": 4
        }
__JSON__
} | python -m json.tool
```

レスポンスには 4 つのアップロード URL が含まれます。

```json
{
    ...
    "upload_urls": [
        "https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-01-path]",
        "https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-02-path]",
        "https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-03-path]",
        "https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-04-path]"
    ],
    ...
}
```

チャンクサイズは次のようになります。

```python title="Python"
math.ceiling(float(21136250) / float(4))
# 5284063 bytes
```

最後のチャンクは 5,284,061 バイトになります (`21136250 - 5284063 * 3` として計算)。

カスタムのチャンク数をリクエストする場合は、[AWS S3 マルチパートアップロードの制限](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)に注意してください。

- 最後のパートを除き、各パートは 5 MiB (5,242,880 バイト) 以上である必要があります
- パート数は 10,000 を超えることはできません

リクエストがこれらの制約に違反している場合、`500: INTERNAL SERVER ERROR` が返されます。

```
{
    "code": 500,
    "errors": [
        {
            "code": 500,
            "detail": "There was a problem with your request",
            "status": 500,
            "title": "Something went wrong"
        }
    ],
    "message": "Something went wrong"
}
```

カスタムのパート数が S3 の要件に準拠していることを必ず確認してください。

## 効率的なアップロード {#uploading-efficiently}

C2C デバイスは厳しいネットワーク環境で動作することが多いため、効率性が非常に重要です。スループットを最大化するための戦略を以下に紹介します。

### TCP 接続の再利用/プーリング {#tcp-connection-reuse/pooling}

暗号化された接続を確立するには、大きなネゴシエーションのオーバーヘッドが必要です。効率的に動作させるには、複数のリクエストを行う際に TCP 接続を再利用してください。ほとんどの HTTP ライブラリは、永続的な接続を維持する `Client` または `Session` の抽象化を提供しています。

新しい HTTPS 接続のネゴシエーションプロセスには、暗号化ハンドシェイクと証明書の検証が含まれます。接続を再利用することで、このオーバーヘッドはリクエストごとではなく一度だけで済みます。

<Info>

**TCP ハンドシェイクのリファレンス**

TLS ハンドシェイクプロセスの技術的な詳細については、[Cloudflare の解説](https://www.cloudflare.com/learning/ssl/what-happens-in-a-tls-handshake/)を参照してください。

</Info>

`curl` で接続の再利用を試すには、まず[基本的なアップロードガイド](/ja/camera-to-cloud/how-to-basic-upload#step-1-creating-an-asset)の説明に従って Frame.io に新しいアセットを作成します。

次に、テスト用にファイルを個別のチャンクに分割します。

```shell
head -c 10568125 ~/Downloads/C2C_TEST_CLIP.mp4 > "C2C_TEST_CLIP-Chunk01"
tail -c 10568125 ~/Downloads/C2C_TEST_CLIP.mp4 > "C2C_TEST_CLIP-Chunk02"
```

curl の `--next` パラメーターを使用して、単一の TCP 接続で両方のチャンクをアップロードします。

```shell
curl -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-1-path] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk01 \
--next -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-2-path] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk02
```

これを個別の接続を使う場合と比較してみましょう。

```shell
curl -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-1-path] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk01 \
&& curl -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-2-path] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk02
```

<Info>

**チャンク URL の再利用**

同じチャンク URL に何度でもアップロードできるため、例の間で URL を自由に再利用してかまいません。

</Info>

テストでは、接続の再利用により、連続したアップロードのパフォーマンスが通常 15〜20% 向上します。

### 並列アップロード {#parallel-uploads}

さらにスループットを高めるには、複数のチャンクを同時にアップロードします。

```shell
curl -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-1-path] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk01 \
& \
curl -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[part-2-path]\
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk02 \
&
```

十分な帯域幅があれば、並列アップロードは個々のアップロードのうち最も遅いものとほぼ同じ時間で完了します。

最適な並列性を得るための目安は、CPU コアあたり 2 つの同時アップロードです。この比率を超えると、リソースの競合が発生し、効果が逓減する可能性があります。

<Warning>

**並列アップロードの速度**

ネットワークの状況は、並列アップロードのパフォーマンスに大きく影響します。環境によっては、連続アップロードのほうが並列アップロードよりも高速な場合があります。高度な実装では、スループットを監視して並列度を動的に調整することもあります。例のタイミングに頼るのではなく、必ず実際の本番環境でパフォーマンスをプロファイリングしてください。

</Warning>

### 両方のアプローチを組み合わせる {#combining-both-approaches}

効率を最大化するには、接続プーリングと並列アップロードを組み合わせます。複数のプロセスを作成し、それぞれが独自の一連のアップロードに接続プーリングを使用するようにします。

```shell
curl -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[asset01-chunk01] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk01 \
--next -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[asset01-chunk02] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk02 \
& \
curl -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[asset02-chunk01] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk01 \
--next -X PUT https://frameio-uploads-production.s3-accelerate.amazonaws.com/parts/[asset02-chunk02] \
        --include \
        --header 'content-type: video/mp4' \
        --header 'x-amz-acl: private' \
        --data-binary @C2C_TEST_CLIP-Chunk02 \
&
```

<Info>

**HTTP ライブラリの機能**

ほとんどの HTTP ライブラリは、接続プーリングと並列リクエストのための抽象化を提供しています。お使いのライブラリのオプションを試して、環境に最適な設定を見つけてください。

</Info>

## アップロードの進捗状況の追跡 {#tracking-upload-progress}

インテグレーションでは、ユーザーに基本的な進捗表示を提供する必要があります。チャンク単位の粒度で問題ありません。3 つのチャンクのアップロードであれば、各チャンクが完了するたびに進捗が 0% → 33% → 66% → 100% と増加する形でかまいません。

より細かい粒度の進捗報告は、お使いの HTTP ライブラリの機能に依存します。より詳細な進捗追跡の実装についてガイダンスが必要な場合は、私たちのチームにお問い合わせください。

## 信頼性の高いアップロード {#uploading-reliably}

堅牢なエラー処理については、[エラーガイド](/ja/camera-to-cloud/how-to-handle-errors)を確認してください。以下のセクションは、そこで説明されているエラー処理戦略を実装済みであることを前提としています。

本番品質のアップローダーを作成するには、個々のリクエストのエラー処理以外にも考慮すべき点があります。

### アップロードキューの作成 {#creating-an-upload-queue}

実際のシナリオでは、デバイスがアップロードできる速度よりも速くメディアを生成したり、長時間の接続中断が発生したりすることがあります。キューイングシステムを実装することで、メディアの作成とアップロードの管理を分離できます。

2 つのキューを使ったアーキテクチャを検討してください。

1. ローカルファイルを Frame.io に登録するための**メディアキュー**
2. 個々のファイルチャンクをアップロードするための**チャンクキュー**

以下は簡略化した実装です。

```python title="Python"
# Where we are going to queue new files.
FILE_QUEUE = Queue()

# Where we are going to queue new chunks.
CHUNK_QUEUE = Queue()

# The http session that will handle TCP 
# connection pooling for us.
HTTP_SESSION = http.Session()

def take_picture():
    """Snaps a picture for the user."""

    image = MY_DEVICE.capture()
    file_path = MY_DEVICE.write_image(image)
    FILE_QUEUE.add(file_path)

def task_register_assets():
    """
    Pulls snapped pictures from the FILE_QUEUE, registers
    with Frame.io, and adds the chunks to the CHUNK_QUEUE.
    """
    while True:
        # Get the latest file added to the queue and register 
        # a C2C Asset for it.
        new_file = FILE_QUEUE.get()
        asset = c2c.crete_asset_for_file(HTTP_SESSION, new_file)

        # Calculate the size for each chunk
        chunk_size = c2c.calculate_chunk_size(asset, new_file)

        # Create a message for each chunk with it's parameters 
        # and add it to the 
        # queue.
        chunk_start = 0
        for chunk_url in asset.upload_urls:
            message = {
                "file_path": new_file,
                "chunk_url": chunk_url,
                "chunk_start": chunk_start,
                "chunk_size": chunk_size,
            }

            # Put the message in the queue and 
            CHUNK_QUEUE.put(message)
            chunk_start += chunk_size

def task_upload_chunk():
    """Takes a chunks and uploads them."""

    while True:
        info = CHUNK_QUEUE.get()
        c2c.upload_chunk(HTTP_SESSION, info)

def launch_upload_tasks():
    """Lauches our Frame.io upload tasks."""
    # Create a list to hold all of our tasks.
    tasks = list()

    # Create one task for registering assets.
    asset_task = run_task_in_thread(task_register_assets)
    tasks.append(asset_task)

    # Create 2 tasks per CPU core for uploading chunks.
    for _ in range(0, GET_CPU_COUNT() * 2):
        chunk_task = run_task_in_thread(task_upload_chunk)
        tasks.append(chunk_task)

    # Run these tasks until shutdown
    run_forever(tasks)
```

<Warning>

**エラー処理**

上記の例では、c2c の呼び出しで使用される関数が、[エラーガイド](/ja/camera-to-cloud/how-to-handle-errors)で説明されているとおりにエラーを処理していることを前提としています。

</Warning>

### 電源の再投入をまたぐ永続的なキューイング {#persistent-queuing-across-power-cycles}

メモリ内キューのアプローチは、デバイスの電源が入っている間はうまく機能しますが、アップロードが完了する前に電源が失われた場合はどうなるでしょうか。真に回復力のあるインテグレーションを作成するには、デバイスが再起動後に中断したところから再開できるようにする必要があります。

そのためには、電源の再投入の間でキューの状態をストレージに永続化する必要があります。[SQLite](https://www.sqlite.org/index.html) などの組み込みデータベースは、この機能の優れた基盤となります。

永続キューの実装は、次の主要な操作をサポートする必要があります。

- 新しく作成されたファイルをアップロードキューに追加する
- Frame.io でアセットが正常に作成されたことを追跡する
- エラーによりアセットの作成に失敗したことを記録する
- アップロードタスク用にファイルチャンクの情報を保存する
- 次にアップロードするチャンクを取得する
- チャンクを正常にアップロード済みとしてマークする
- チャンクのアップロードの失敗をログに記録する
- ユーザーに表示するためのファイルのステータス情報を提供する

以下は、前の例を永続ストレージシステムを使うように適応させた例です。

```python title="Python"
# Our persistence layer for queuing uploads, potentially using SQLite 
# or another embedded database
C2C_UPLOAD_STORE = NewC2CUploadStore()

# HTTP session for connection pooling
HTTP_SESSION = http.Session()

def take_picture():
    """Captures an image and adds it to the upload queue."""
    image = MY_DEVICE.capture()
    file_path = MY_DEVICE.write_image(image)

    # Register the file with our persistent store
    C2C_UPLOAD_STORE.add_file(file_path)

def task_register_assets():
    """
    Processes files from persistent storage and registers
    them with Frame.io for upload.
    """
    while True:
        # Get the next available file from our store
        file_record = C2C_UPLOAD_STORE.get_file()

        try:
            # Register the asset with Frame.io
            asset = c2c.create_asset_for_file(HTTP_SESSION, file_record)
            chunk_size = c2c.calculate_chunk_size(asset, file_record)

            # Create entries for each chunk in our persistent store
            chunk_start = 0
            for chunk_url in asset.upload_urls:
                message = {
                    "file_path": file_record,
                    "chunk_url": chunk_url,
                    "chunk_start": chunk_start,
                    "chunk_size": chunk_size,
                }
                
                C2C_UPLOAD_STORE.new_chunk(message)
                chunk_start += chunk_size
                
        except BaseException as error:
            # Record the error in our persistent store
            C2C_UPLOAD_STORE.file_asset_create_error(file_record, error)
        else:
            # Mark the asset as successfully created
            C2C_UPLOAD_STORE.file_asset_created(file_record)

def task_upload_chunk():
    """Uploads individual file chunks from the persistent queue."""
    while True:
        # Get the next chunk, marking it as "in progress" to prevent 
        # other tasks from processing it simultaneously
        chunk_record = C2C_UPLOAD_STORE.get_chunk()

        try:
            c2c.upload_chunk(HTTP_SESSION, chunk_record)
        except BaseException as error:
            # Record the error for potential retry
            C2C_UPLOAD_STORE.chunk_error(chunk_record, error)
        else:
            # Mark successful completion
            C2C_UPLOAD_STORE.chunk_success(chunk_record)

def launch_upload_tasks():
    """Launches Frame.io upload processing tasks."""
    tasks = []

    # Asset registration task
    asset_task = run_task_in_thread(task_register_assets)
    tasks.append(asset_task)

    # Multiple parallel chunk upload tasks
    worker_count = GET_CPU_COUNT() * 2
    for _ in range(worker_count):
        chunk_task = run_task_in_thread(task_upload_chunk)
        tasks.append(chunk_task)

    # Run indefinitely
    run_forever(tasks)
```

この永続ストレージのアプローチにより、インテグレーションは電源の中断に対して回復力を持つようになります。デバイスが再起動すると、最後に保存された状態から処理を続行するだけです。このアーキテクチャは、エラー追跡や停滞したアップロードの検出など、より高度な機能を実装するための基盤にもなります。

### アップロードエラーの追跡 {#tracking-upload-errors}

堅牢なアップロードシステムでは、エラーを注意深く追跡する必要があります。[エラーガイド](/ja/camera-to-cloud/how-to-handle-errors)の戦略に従って操作を再試行した後、これらの失敗を永続ストアに記録します。これにより、システムは次のことが可能になります。

1. 問題のあるアップロードの優先度を下げ、キュー全体がブロックされるのを防ぐ
2. ユーザーに正確なステータス情報を提供する
3. 継続的な問題に対して管理者が介入できるようにする

致命的なエラーが発生した場合は、その項目にマークを付けて不要な再試行を防ぎます。

### 停滞したアップロードの管理 {#managing-stalled-uploads}

アップロードが無期限に停滞しないよう、安全策を実装してください。最大時間 (例: 30 分) を設定し、それを超えたらチャンクのアップロードタスクを終了して再開するようにします。これにより、応答しない操作によってすべてのアップロードワーカーがブロックされる事態を防げます。

### サイレント障害からの回復 {#recovering-from-silent-failures}

システムのクラッシュ、電源喪失、プロセスの終了などにより、通常のエラー報告が行われないことがあります。キューから項目を取得する際は、取得時刻を記録してください。項目が成功も失敗も報告しないまま妥当なしきい値 (例: 30 分) を超えて「処理中」の状態にとどまっている場合は、自動的に利用可能なプールに戻し、別のワーカーが処理できるようにします。

### ポイズンアップロードの軽減 {#mitigating-poisoned-uploads}

「ポイズン」化したキュー項目は、データや環境に内在する問題のために常に失敗します。こうした項目が繰り返しキューに戻されると、アップロードシステム全体が事実上ブロックされる可能性があります。このようなケースに対処するには、次の戦略を検討してください。

- 複数回失敗した後は、その項目の優先度を下げて新しいコンテンツを先に処理できるようにする
- 明示的なエラーと処理の試行回数の両方を追跡する
- 接続と認可のベストプラクティスに従って、一時的な環境の問題とファイル固有の問題を区別する
- 段階的な再試行の上限を実装する (例: 3 回のジョブ試行それぞれで個々の操作を 10 回再試行し、合計 30 回試行する)
- 環境の問題が解決した後に、問題のあるアップロードを手動でリセットするためのユーザーインターフェースを提供する

ポイズンアップロードは、次のような原因で発生します。

- I/O エラーを引き起こす破損したファイルデータ
- エラー報告を妨げる致命的なプロセス障害
- 恒久的な根本原因によって引き起こされる、本来は再試行可能なエラー

### システム再起動後の再試行 {#retry-after-system-restart}

問題のあるアップロードを完全に破棄する前に、次回のシステム再起動後に最後の再試行を行うようフラグを立ててください。これにより、メモリ、ドライバー、リソース割り当てなどのシステム状態の一時的な問題が原因でアップロードが失敗したケースに対処できます。クリーンな再起動後もアップロードが失敗し続ける場合は、恒久的な問題があるものとしてより確信を持ってマークできます。

## キューのクリア {#clearing-your-queue}

利用できなくなったファイルをキューから削除することを忘れないでください。メディアが物理的に取り外されたり、ファイルが削除されたりした場合は、不要なエラーを防ぐために、アップロードキューから対応するエントリを削除します。

*重要: 新しいプロジェクトに接続する際は、アップロードキューをクリアする必要があります。* あるプロジェクト用にキューに入れられたメディアが、別のプロジェクトに表示されることがあってはなりません。ユーザーがデバイスを別のプロジェクトとペアリングした場合は、プロジェクトが変更されたかどうかを確認し、変更されていれば既存のキューを完全にクリアしてください。
