Frame.io Actions bieten schnellen Zugriff auf gängige Medienvorgänge wie das Herunterladen, Umbenennen und Duplizieren von Elementen – und ermöglichen es außerdem, Integrationen mit Tools und Diensten von Drittanbietern direkt in der Benutzeroberfläche von [Frame.io](https://next.frame.io/) bereitzustellen.

## Über Actions {#about-actions}

Mit der Einführung von Custom Actions können Entwicklerinnen und Entwickler ihre eigenen Actions in Frame.io V4 konfigurieren und verwalten. Custom Actions nutzen dasselbe zugrunde liegende Ereignissystem wie [Webhooks](https://developer.adobe.com/frameio/guides/Webhooks/) und bieten einen alternativen Mechanismus, um Assets mit den Tools zu verbinden, die für die User in ihrem Frame.io-Account am wichtigsten sind.

Actions können von jedem User ausgeführt werden, der Mitglied des Frame.io-Workspaces ist, in dem die Action aktiviert ist. Wenn eine Action ausgeführt wird, sendet Frame.io eine Payload an eine von Ihnen angegebene URL. Die empfangende Anwendung antwortet mit einem HTTP-Statuscode, um den Empfang zu bestätigen, oder mit einem benutzerdefinierten Callback, um zusätzliche Formularfelder in der Frame.io-Oberfläche darzustellen. Die empfangende Anwendung kann Ihr eigenes gehostetes Programm, ein Dienst oder sogar ein Low-Code-/No-Code-iPaaS-Tool wie Workfront Fusion oder Zapier sein.

Verwenden Sie Custom Actions, um Integrationen als programmierbare UI-Komponenten direkt in [Frame.io](https://next.frame.io/) zu integrieren. Dadurch werden Workflows möglich, die von Usern innerhalb der App ausgelöst werden können und dasselbe zugrunde liegende Ereignis-Routing wie Webhooks nutzen. Sie können von Usern ausgelöste ein- oder mehrstufige Formulare erstellen, die als weiteres Formular oder als einfache Antwort an Frame.io zurückgegeben werden. Und wenn ein User auf eine Custom Action für ein Asset klickt, sendet Frame.io eine Payload an eine von Ihnen angegebene URL. Die empfangende Anwendung antwortet mit einem HTTP-Statuscode, um den Empfang zu bestätigen, oder mit einem benutzerdefinierten Callback, der zusätzliche UI-Elemente in Frame.io darstellen kann.

## Rate Limits {#rate-limits}

Custom-Action-Ereignisse werden auf dieselben Limits auf Account-Ebene angerechnet wie Webhook-Ereignisse: **1.000 Ereignisse pro Minute** und **20.000 Ereignisse pro Stunde**. Beide Limits gelten für das kombinierte Volumen im gesamten Account, nicht separat für jede Custom Action oder jedes Webhook-Abonnement.

Wenn eines der Limits erreicht ist, werden weitere Custom-Action-Ereignisse **verworfen** – sie werden weder in eine Warteschlange gestellt noch automatisch erneut versucht.

Dabei handelt es sich um Limits für das Ereignisvolumen, nicht um API-Anfragelimits für die Verwaltung von Custom Actions. Details finden Sie unter [Webhook-Rate-Limits](/de/platform/docs/guides/webhooks#webhook-rate-limits).

## Migrierte Actions {#migrated-actions}

Bei der Migration zu einem Frame.io-V4-Account mit Custom Actions, die zuvor in der Legacy-Version von Frame.io erstellt wurden, sind einige Dinge zu beachten.

### Action-Status {#action-status}

Bei der Migration eines Accounts zu Frame.io V4 erhalten alle in früheren Versionen erstellten Custom Actions den Status „null“ und werden automatisch deaktiviert. So haben User die Möglichkeit, ihre Actions zunächst auf die V4-API umzustellen, bevor sie sie aktivieren, da alle nicht aktualisierten Actions fehlschlagen. Um Actions in diesem Zustand zu erkennen, rufen Sie die Seite mit den Action-Einstellungen auf und sehen Sie sich die Spalte „Status“ an oder prüfen Sie bei Verwendung der API das Feld is_active.

### Ressourcen für Actions: Files, Folders und Version Stacks {#actionable-resources-files-folders-&-version-stacks}

Da Asset-Typen in der Frame.io V4 API als separate Ressourcen geführt werden, gibt es bei der Auswertung der Ressourcen-ID in der Payload Ihrer Action einiges zu beachten. Bei einzelnen Files ist das Verhalten einfach: Die ID entspricht dem konkreten File, für das die Action ausgeführt wurde. Ebenso erhalten Sie bei Folders die ID des Folders, für den die Action ausgeführt wurde. Je nach Anwendungsfall haben Sie jedoch mehrere Möglichkeiten, das Verhalten Ihrer Action zu definieren. Verwenden Sie die Folder-ID für weitere Aufrufe der Frame.io API, wenn Sie mit der Folder-Ressource selbst interagieren möchten. Alternativ können Sie die untergeordneten Elemente dieses Folders abrufen, um die darin enthaltenen Assets weiterzuverarbeiten. Wird eine Action für einen Version Stack ausgeführt, enthält Ihre Payload die ID des „Head Asset“. Dies ist das oberste File im Stack, das auch in der Frame.io-Oberfläche angezeigt wird.

Weitere Informationen zu den Unterschieden zwischen der Frame.io Legacy API und V4 finden Sie in unserem [Migrationsleitfaden](/de/platform/v4-experimental/docs/resources/migration).

## Ihre Custom Action konfigurieren {#configure-your-custom-action}

Wenn ein User eine Custom Action auslöst, sendet Frame.io eine Payload an eine von Ihnen angegebene URL. Die empfangende Anwendung kann mit einem HTTP-Statuscode antworten, um den Empfang zu bestätigen, oder mit einem benutzerdefinierten Callback, der zusätzliche UI-Elemente in [Frame.io](https://next.frame.io/) darstellt.

<Warning>

Zum Erstellen von Custom Actions für einen Workspace sind Account-Admin-Berechtigungen erforderlich. Bitten Sie Ihren Admin, Ihre Berechtigungen anzupassen, falls Sie keinen Zugriff haben.

</Warning>

### Konfiguration für mehrere Assets {#multi-asset-configuration}

Die Unterstützung mehrerer Assets wird über die Konfiguration gesteuert und muss im Konfigurations-Modal der Action [im Web](https://next.frame.io/settings/actions) ausdrücklich aktiviert werden. Dies ist beim Erstellen einer neuen Action oder beim Aktualisieren einer bestehenden Action möglich.

Wenn die Unterstützung mehrerer Assets aktiviert ist, wird das Payload-Format sofort umgestellt. Die Legacy-Payload und die Payload mit Unterstützung mehrerer Assets schließen sich gegenseitig aus.

### Migration von der Legacy-Payload {#migrating-from-the-legacy-payload}

<Warning>

**Einstellung der Legacy-Payload geplant**

Die Legacy-Payload soll eingestellt werden, und wir empfehlen Usern dringend, ihre Dienste so umzustellen, dass sie die neue Payload verarbeiten.

Durch Aktivieren des Konfigurations-Flags und Anpassen Ihrer Payload-Verarbeitung kann eine Action nahtlos auf die Unterstützung einer Payload mit mehreren Assets umgestellt werden.

1. Ersetzen Sie die Verwendung des einzelnen `resource`-Objekts durch die `resources`-Liste
2. Passen Sie den Code so an, dass er über die `resources`-Liste iteriert
3. Aktivieren Sie das Flag für mehrere Assets in der Action-Konfiguration

</Warning>

## Interaktionen, Wiederholungsversuche und Timeouts {#interactions-retries-and-timeouts}

Die `interaction_id` ist eine eindeutige Kennung, mit der die Interaktion im Laufe der Zeit nachverfolgt wird. Wenn Sie dem User nicht antworten müssen, geben Sie den Statuscode 200 zurück, und Sie sind fertig. Auch wenn es optional ist, empfehlen wir, Informationen über das Ergebnis der Aktion mitzuliefern, z. B. eine Erfolgsmeldung oder einen Fehlerhinweis. Custom Actions unterstützen Message-Callbacks.

<Note>

Frame.io erwartet eine Antwort innerhalb von 10 Sekunden und unternimmt bis zu 5 Wiederholungsversuche, während auf eine erfolgreiche Antwort gewartet wird. Idealerweise erfolgt die Antwort sofort, und asynchrone Aktionen finden nach dem Auslösen über eine Custom Action statt.

</Note>

## Einen Message-Callback erstellen {#create-a-message-callback}

In Ihrer HTTP-Antwort auf das Webhook-Ereignis können Sie ein JSON-Objekt zurückgeben, das eine Nachricht beschreibt, die dem auslösenden User in der Frame.io-Oberfläche angezeigt wird.

```json
{
  "title": "Success!",
  "description": "The thing worked! Nice."
}
```

Mit Nachrichten können Sie dem User direkt in der Frame.io-Oberfläche Feedback geben. Wenn Sie zusätzliche Informationen vom User benötigen, verwenden Sie stattdessen **Form-Callbacks**.

## Einen Form-Callback erstellen {#create-a-form-callback}

Angenommen, Sie benötigen weitere Informationen, bevor Sie Ihren Prozess starten. Zum Beispiel laden Sie Inhalte in ein System hoch, das zusätzliche Angaben erfordert. Sie können in Ihrer Antwort ein Formular beschreiben, das der User ausfüllt und an Sie zurücksendet. Hier ist ein Beispiel:

```json
{
  "title": "Need some more info!",
  "description": "Getting ready to submit this file!",
  "fields": [
    {
      "type": "text",
      "label": "Title",
      "name": "title",
      "value": "MyVideo.mp4"
    },
    {
      "type": "select",
      "label": "Captions",
      "name": "captions",
      "options": [
        {
          "name": "Off",
          "value": "off"
        },
        {
          "name": "On",
          "value": "on"
        }
      ]
    }
  ]
}
```

Wenn der User das Formular absendet, erhalten Sie ein Ereignis an derselben URL wie beim ursprünglichen POST:

```json
POST /your/url
{
  "type": "your-specified-event-name",
  "interaction_id": "the-same-id-as-before",
  "action_id": "unique-id-for-this-custom-action",
  "data":{
    "title": "MyVideo.mp4",
    "captions": "off"
  }
}
```

Alle einem Formular hinzugefügten benutzerdefinierten Felder erscheinen im Abschnitt `data` der von Frame.io gesendeten JSON-Payload. Verwenden Sie die `interaction_id`, um die ursprüngliche Anfrage diesen neuen Formulardaten zuzuordnen. Sie können mit einer Nachricht antworten oder ein weiteres Formular anschließen. Durch die Verkettung von Actions, Formularen und Nachrichten können Sie in Frame.io effektiv mehrstufige Workflows mit Geschäftslogik aus einem externen System programmieren.

## Sicherheit und Verifizierung {#security-and-verification}

Standardmäßig wird für alle Custom Actions bei ihrer Erstellung ein Signaturschlüssel generiert. Dies ist nicht konfigurierbar. Mit diesem Schlüssel können Sie überprüfen, ob die Anfrage von Frame.io stammt. Die `POST`-Anfrage enthält Folgendes:

| Name | Beschreibung |
| --- | --- |
| `X-Frameio-Request-Timestamp` | Der Zeitpunkt, zu dem Ihre Custom Action ausgelöst wurde. |
| `X-Frameio-Signature` | Die berechnete Signatur. |

<CardGroup cols={2}>

<Card title="Überprüfung des Zeitstempels" icon="clock" iconType="solid">

**Der Zeitstempel** ist der Zeitpunkt, zu dem die Anfrage beim Verlassen des Frame.io-Netzwerks signiert wurde. Er kann verwendet werden, um Replay-Angriffe zu verhindern. Wir empfehlen zu überprüfen, ob dieser Zeitpunkt höchstens 5 Minuten von der lokalen Zeit abweicht.

</Card>

<Card title="Überprüfung der Signatur" icon="shield" iconType="solid">

**Die Signatur** ist ein HMAC-SHA-256-Hash, der mit dem Signaturschlüssel erstellt wird, der beim ersten Erstellen der Custom Action bereitgestellt wurde.

</Card>

</CardGroup>

### Die Signatur überprüfen {#verifying-the-signature}

<Steps>

<Step title="Signatur extrahieren">

Extrahieren Sie die Signatur aus den HTTP-Headern.

</Step>

<Step title="Zu signierende Nachricht erstellen">

Erstellen Sie eine zu signierende Nachricht, indem Sie Version, Zustellzeitpunkt und Request-Body kombinieren: `v0:timestamp:body`.

</Step>

<Step title="HMAC SHA256 berechnen">

Berechnen Sie die HMAC-SHA256-Signatur mit Ihrem Signatur-Secret.

</Step>

<Step title="Signaturen vergleichen">

Vergleichen Sie Ihre berechnete Signatur mit der bereitgestellten!

</Step>

</Steps>

<Note>

Der bereitgestellten Signatur ist `v0=` vorangestellt. Derzeit verwendet Frame.io nur diese eine Version zum Signieren von Anfragen. Sie müssen dieses Präfix Ihrer berechneten Signatur hinzufügen.

</Note>

```python title="Python"
import hmac
import hashlib

def verify_signature(curr_time, req_time, signature, body, secret):
    """
    Verify webhook/custom action signature
    :Args:
        curr_time (float): Current epoch time
        req_time (float): Request epoch time
        signature (str): Signature provided by the frame.io API for the given request
        body (str): Custom Action body from the received POST
        secret (str): The secret for this Custom Action that you saved when you first created it
    """
    if int(curr_time) - int(req_time) < 500:
        message = 'v0:{}:{}'.format(req_time, body)
        calculated_signature = 'v0={}'.format(hmac.new(
            bytes(secret, 'latin-1'),
            msg=bytes(message, 'latin-1'),
            digestmod=hashlib.sha256).hexdigest())
        if calculated_signature == signature:
            return True
    return False
```
