## Einführung {#introduction}

Die Frame.io V4 API ist eine Neugestaltung der Legacy API, die häufig als *V2-Endpunkte* oder *Frame.io V3 API* bezeichnet wird. Die Neugestaltung nutzt die neuen Möglichkeiten und Funktionen von Frame V4 voll aus und behält gleichzeitig alle relevanten Funktionen der Legacy API bei. Dieser Leitfaden beschreibt die wichtigsten Unterschiede zwischen der Legacy API und der V4 API und bietet eine Schritt-für-Schritt-Anleitung für eine reibungslose Migration.

## Migrations-Checkliste {#migration-checklist}

<Steps>

<Step title="Authentifizierung">

Für <Tooltip tip="Konten, die die Legacy API mit einem generierten Entwickler-Token verwendet haben und automatisch zu V4 migriert wurden. Konten, die in V4 erstellt oder manuell migriert wurden, sind nicht eingeschlossen">**automatisch zu V4 migrierte Konten**</Tooltip>, die noch nicht über die Adobe Admin Console verwaltet werden, können Sie weiterhin Legacy-Entwickler-Tokens verwenden, die auf der [Frame.io-Entwicklerwebsite](/de/platform/v4-experimental/welcome) verwaltet werden. Sie müssen Ihren API-Anfragen jedoch einen Header mit dem Schlüssel `x-frameio-legacy-token-auth` und dem Wert `true` hinzufügen. Andernfalls folgen Sie den Schritten im Abschnitt [Authentifizierung](#adobe-developer-console-managed-authentication) weiter unten.

</Step>

<Step title="Bestehende API-Aufrufe aktualisieren">

Alle Legacy-API-Routen müssen den neuen V4-API-Routen und JSON-Payloads zugeordnet werden. Weiter unten finden Sie eine recht umfassende [Zuordnungstabelle](#endpoint-mappings-legacy-api-to-v4), die Sie dabei unterstützt.

</Step>

<Step title="Tests werden dringend empfohlen">

**Testen Sie gründlich.** Da es viele Änderungen an der API gibt, empfehlen wir, mit einem V4-Konto zu testen, um sicherzustellen, dass die neue API wie erwartet funktioniert.

</Step>

<Step title="Dedizierte Anmeldung implementieren">

Implementieren Sie aufgrund der separaten Auth-URLs eine dedizierte Anmeldemethode für V4. Die V4-Auth-URL unterscheidet sich von der der Legacy API. Sie gibt in der Antwort keine Konten zurück, die noch nicht auf V4 umgestellt wurden, und sollte als separate Integration behandelt werden.

</Step>

</Steps>

<Note>

Wenn Sie Fragen zu einem Endpunkt haben, der in der Zuordnungstabelle unten nicht aufgeführt ist, wenden Sie sich bitte an unser Supportteam unter [support@frame.io](mailto:support@frame.io).

</Note>

## Über die Adobe Developer Console verwaltete Authentifizierung {#adobe-developer-console-managed-authentication}

Für zu V4 migrierte Konten, die über die [Adobe Developer Console](https://developer.adobe.com/developer-console/) verwaltet werden, müssen Sie die V4 API mit OAuth 2.0 verwenden. Folgen Sie dazu den unten stehenden Schritten.

<Steps>

<Step title="Adobe-Projekt erstellen">

**Erstellen Sie ein Projekt in der Adobe Developer Console** und fügen Sie Frame.io als Produkt hinzu.

</Step>

<Step title="Authentifizierungstyp auswählen">

**Authentifizieren Sie sich.** Weitere Informationen finden Sie im [Authentifizierungsleitfaden](https://developer.adobe.com/frameio/guides/Authentication/). Wenn Ihr V4-Konto noch nicht über die Adobe Admin Console verwaltet wird, können Sie diesen Schritt überspringen.

- **Benutzerauthentifizierung**: Stellt die Verbindung zu Frame über eine Client-ID und/oder ein Client-Secret her und erfordert, dass sich ein Benutzer mit Benutzername und Passwort anmeldet.
- **Server-zu-Server-Authentifizierung**: Stellt die Verbindung zu Frame über Client-ID und Client-Secret her, erfordert jedoch keine Anmeldung eines Benutzers über einen Browser.

</Step>

<Step title="Bearer-Authentifizierung implementieren">

**JWT-Bearer-Authentifizierung**: Übergeben Sie bei jeder API-Anfrage das Auth-Token über einen Header mit dem Schlüssel `Authorization` und dem Wert `Bearer <IMS_ACCESS_TOKEN>`.

</Step>

</Steps>

## Endpunktzuordnungen (Legacy API zu V4) {#endpoint-mappings-legacy-api-to-v4}

<Note>

Wenn Sie die Legacy-Authentifizierung mit Entwickler-Token verwenden, müssen Sie Ihren API-Anfragen einen Header mit dem Schlüssel x-frameio-legacy-token-auth und dem Wert true hinzufügen.

</Note>

Allgemeine Hinweise zur Unterstützung bei der Migration:

<Steps>

<Step title="Payloads">

Die Anfrage- und Antwort-Payloads können sich unterscheiden.

</Step>

<Step title="Teams → Workspaces">

„Teams“ in der Legacy API entsprechen „Workspaces“ in V4.

</Step>

<Step title="Assets">

„Assets“ der Legacy API sind in V4 nun in „Files“, „Folders“ und „Version Stacks“ aufgeteilt.

</Step>

<Step title="Berechtigungen">

Berechtigungen und Rollen sind in V4 anders, was die Struktur der Endpunkte verändert. In V4 gibt es Benutzerrollen auf Workspace- und Projektebene. Weitere Details finden Sie unter [Benutzerberechtigungen verwalten](/de/platform/docs/guides/managing-user-permissions).

</Step>

</Steps>

### 8. Shares (Review-Links / Präsentationen) {#8-shares-review-links-/-presentations}

In Frame V4 wird bei Share-Links nicht mehr zwischen Review-Links und Präsentationslinks unterschieden. In V4 kann der Share-Link nun mit unterschiedlichen Stilen konfiguriert werden, um dem Review- oder Präsentationserlebnis zu entsprechen.

Hinweis: Die Interaktion mit Legacy-Review-Links und -Präsentationen über die V4 API wird nicht unterstützt.

### 9. Webhooks {#9-webhooks}

Die Webhooks, die Sie in V3 verwendet haben, werden migriert und funktionieren größtenteils unverändert. Bei der Migration werden sie deaktiviert und müssen wieder aktiviert werden, damit sie funktionieren. Für Asset-Events sind einige Änderungen erforderlich, da diese nun in Dateien und Ordner aufgeteilt sind. Beachten Sie außerdem einige neue V4-spezifische Events: metadata.value.updated, Collection-bezogene Events und Share-bezogene Events.

Bevor Sie migrierte Webhooks wieder aktivieren, prüfen Sie die [Rate Limits für Webhooks](/de/platform/docs/guides/webhooks#webhook-rate-limits). V4-Webhook- und Custom-Action-Events teilen sich pro Konto Limits von **1.000 Events pro Minute** und **20.000 Events pro Stunde**. Beide Limits gelten für das kombinierte Volumen im gesamten Konto.

## Migrationsschritte {#migration-steps}

<Steps>

<Step title="Nicht unterstützte V2-Endpunkte anpassen">

**Passen Sie** alle nicht unterstützten Legacy-V2-Endpunkte an.

</Step>

<Step title="Basis-URLs aktualisieren">

**Aktualisieren Sie die Basis-URLs** von `api.frame.io/v2/...` auf `api.frame.io/v4/...`.

</Step>

<Step title="API-Anfragen aktualisieren">

**Aktualisieren Sie die API-Anfragen** in Ihrem Code, sodass sie auf das neue Endpunktschema verweisen.

</Step>

<Step title="JSON-Payloads aktualisieren">

**Aktualisieren Sie die JSON-Payloads** der Anfrage- und Antwortschemas, um sicherzustellen, dass Sie die richtigen Felder erzeugen und verarbeiten.

</Step>

<Step title="Terminologie aktualisieren">

Aktualisieren Sie die Terminologie in Ihrem Code und Ihrem Frontend: „Teams“ → „Workspaces“; „Assets“ → „Dateien/Ordner“; „Review-Links“ oder „Präsentationslinks“ → „Shares“.

</Step>

<Step title="Endpunkte testen">

**Testen Sie** alle neu aktualisierten Endpunkte. Wenn Sie 403, 404 oder 422 erhalten, überprüfen Sie die Endpunkte, die Struktur der Anfrage-Payload usw.

</Step>

<Step title="Fehlerantworten auswerten">

**Werten Sie** die neuen, detaillierten Fehlerantworten aus, wenn Ihr API-Aufruf fehlschlägt, und suchen Sie in der JSON-Antwort `{"errors": [...]}` nach der Ursache.

</Step>

<Step title="In Produktion bereitstellen">

**Stellen Sie** die Integration in der Produktion bereit, sobald sie mit einem V4-Konto von [Frame.io](http://frame.io/) validiert wurde.

</Step>

</Steps>

## Fehlerbehandlung und häufige Probleme {#error-handling-&-common-issues}

<Note>

Einige Routen geben Fehler mit benutzerdefinierten Beschreibungen zurück, die leicht von den Beispielen unten abweichen können.

</Note>

<CardGroup cols={2}>

<Card title="Clientfehler (4xx)" icon="triangle-exclamation" iconType="solid">

- **400** Bad Request: Überprüfen Sie die Payload auf Richtigkeit.
- **401** Unauthorized: Ungültiges oder fehlendes Autorisierungstoken.
- **403** Forbidden: Fehlender Scope oder der Benutzer hat keinen Zugriff.
- **404** Not Found: Überprüfen Sie Endpunkt, API-Version oder IDs.
- **422** Unprocessable Entity: Validieren Sie die Anfragedaten
- **429** Too Many Requests: Implementieren Sie Wiederholungsversuche mit Backoff.

</Card>

<Card title="Serverfehler (5xx)" icon="server" iconType="solid">

- **500** Internal Server Error: Versuchen Sie es nach einer kurzen Wartezeit erneut.

</Card>

</CardGroup>
