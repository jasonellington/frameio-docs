## Adobe Developer Console {#adobe-developer-console}

Pierwszym krokiem w korzystaniu z API Adobe jest utworzenie **projektu** (Project) w Adobe Developer Console. Projekty w Developer Console odpowiadają aplikacji, którą tworzysz w celu korzystania z Frame.io Developer API. Nie należy ich mylić z projektami we Frame.io.

## Co nowego we Frame.io V4 Developer API? {#what’s-new-in-the-frame-io-v4-developer-api}

Tak jak aplikacja Frame.io została całkowicie przebudowana w wersji 4, tak również API V4 zaprojektowano od podstaw. Choć niektóre kluczowe pojęcia pozostają podobne do starszych wersji, wiele z nich zastąpiono lub przeprojektowano, aby obsługiwać bardziej zaawansowane przepływy pracy związane ze współpracą oraz integracje. Wprowadzenie zupełnie nowego API dało nam też okazję do radykalnego uproszczenia działania i nadania priorytetu ważnym przepływom pracy klientów.

<Info>

Porównanie Frame.io V4 ze starszą wersją znajdziesz [tutaj](https://help.frame.io/en/articles/9084073-frame-io-v4-legacy-feature-comparison).

</Info>

W API V4 nazwy niektórych zasobów, takich jak obszary robocze (Workspaces, w starszej wersji Frame.io nazywane zespołami — Teams), zostały zmienione, aby odpowiadały Frame.io w wersji 4, a inne, jak zasoby (Assets) ze starszej wersji, przemianowano tak, by odnosiły się do konkretnych jednostek przechowywania (plików — Files, folderów — Folders i stosów wersji — Version Stacks), co ma ograniczyć dezorientację programistów. Jeszcze inne, na przykład pola niestandardowe (Custom Fields) i udostępnienia (Shares), są zupełnie nowe. Wśród innych istotnych zmian znacznie ograniczyliśmy ilość danych zwracanych domyślnie w odpowiedzi na żądania zasobów, zmieniliśmy nazwy niektórych właściwości w odpowiedziach, aby były dokładniejsze i spójne w całym API, oraz przeszliśmy na nowy mechanizm paginacji oparty na kursorach. Należy więc pamiętać, że z wyjątkiem API Camera to Cloud (C2C) klienci zintegrowani ze starszym API nie są zgodni z API V4.

Ponadto niektóre funkcje są wciąż w trakcie opracowywania i oczekuje się, że będą szybko pojawiać się i rozwijać w odpowiedzi na rzeczywiste przypadki użycia i opinie klientów. Przykładem jest możliwość tworzenia akcji niestandardowych i stosów wersji. Jeśli wydaje się, że brakuje funkcji, która była dostępna w starszym API, najprawdopodobniej istnieje alternatywa lub funkcja ta wkrótce będzie dostępna — chętnie jednak poznamy Twoją opinię na ten temat.

Zanim zagłębisz się w API V4, warto najpierw zrozumieć podstawowe pojęcia wykorzystywane w aplikacji Frame.io w wersji 4. Dobrym punktem wyjścia jest [baza wiedzy Frame.io V4](https://help.frame.io/en/). Pojęcia takie jak konta (Accounts), użytkownicy (Users), obszary robocze (Workspaces), projekty (Projects), kolekcje (Collections), udostępnienia (Shares) i pola niestandardowe (Custom Fields, metadane) są modelowane w API V4 jako odrębne zasoby, a zrozumienie ich relacji i możliwości w aplikacji ułatwi zrozumienie, jak działają w API V4.

## Przegląd API {#api-overview}

Frame.io V4 API zaprojektowano zgodnie z zasadami architektury REST. Korzysta ono ze standardowych metod HTTP i kodów odpowiedzi w połączeniu z unikalnymi adresami URL przypisanymi do poszczególnych zasobów. Frame.io publikuje [specyfikację OpenAPI 3.0](https://api.frame.io/v4/openapi.json) dla API V4, która zawiera szczegółowe informacje o punktach końcowych, parametrach żądań i odpowiedziach. Specyfikację OpenAPI można wykorzystać w wielu zewnętrznych narzędziach do generowania kodu, aby przyspieszyć tworzenie aplikacji klienckich.

### Konwencje adresów URL i ścieżek {#url-and-path-conventions}

Ścieżki URL opublikowane w specyfikacji OpenAPI zasadniczo odzwierciedlają relacje własności i zawierania się zasobów. Dlatego niektóre parametry żądania (np. identyfikatory kont, folderów itp.) są osadzone w ścieżce zasobu. Choć ścieżki te mają być przewidywalne i łatwe do zrozumienia, struktura niektórych adresów URL zwracanych przez żądania API (np. wstępnie podpisanych adresów URL przesyłania lub linków do wyświetlania) może ulec zmianie i aplikacja kliencka nigdy nie powinna ich składać samodzielnie.

### Parametry zapytania żądania {#request-query-parameters}

Parametry żądania sterujące paginacją i opcjonalnym dołączaniem powiązanych zasobów do obiektów odpowiedzi są zdefiniowane jako standardowy zestaw parametrów zapytania: `include`, `page_size`, `include_total_count`. Niektóre żądania mogą obsługiwać dodatkowe parametry zapytania, specyficzne dla danego zasobu lub operacji.

```html
GET https://api.frame.io/v4/accounts/{account_id}/folders/{folder_id}/children?&include=project&page_size=5&include_total_count=true
```

### Ładunki żądań i odpowiedzi {#request-and-response-payloads}

Ładunki żądań i odpowiedzi są tworzone jako obiekty JSON, dlatego nagłówek content-type żądania HTTP POST, PUT lub PATCH musi określać typ multimediów `application/json`. Podczas tworzenia lub aktualizowania zasobów właściwość `data` żądania musi zawierać obiekt zasobu. Atrybuty tworzonego lub aktualizowanego zasobu znajdują się w tym obiekcie. Podobnie odpowiedzi zakończone powodzeniem, które zawierają zasoby, udostępniają je we właściwości `data` odpowiedzi.

### Paginacja {#pagination}

Odpowiedzi, które mogą zwracać dużą liczbę obiektów zasobów (np. listy folderów lub komentarzy), są dzielone na strony, aby ograniczyć opóźnienia żądań w miarę wzrostu zbioru wyników. Oznacza to, że odpowiedź na żądanie może zawierać tylko jedną „stronę” wyników. Jak wspomniano powyżej, klient może podczas wysyłania żądania wybrać określony rozmiar strony — maksymalnie 100 elementów — za pomocą parametru zapytania `page_size`. Jeśli go nie określono, rozmiar strony domyślnie wynosi 50 elementów. API V4 korzysta z formy paginacji nazywanej *paginacją opartą na kursorach* i umieszcza we właściwości `links` obiektu odpowiedzi (zob. przykład poniżej) link względny zawierający nieprzezroczysty ciąg kursora w parametrze zapytania `after` (klienci nie powinni próbować samodzielnie tworzyć tego ciągu), który pozwala klientowi pobrać kolejną stronę wyników (zob. przykładową odpowiedź poniżej) za pomocą kolejnych żądań. Obecnie API V4 obsługuje wyłącznie paginację jednokierunkową.

### Błędy {#errors}

W przypadku wystąpienia błędu właściwość `errors` w obiekcie odpowiedzi będzie zawierać tablicę z jednym lub większą liczbą obiektów błędów, które zawierają szczegóły dotyczące zaistniałych błędów. Obecnie API V4 nie obsługuje operacji wsadowych, więc nie ma przypadków, w których klient musiałby obsługiwać częściowe powodzenie i błędy jednocześnie.

```json
{
    "errors": [
        {
            "detail": "Unexpected field: foo",
            "source": {
                "pointer": "/data/foo"
            },
            "title": "Invalid value"
        }
    ]
}
```

Poniższa tabela zawiera typowe kody stanu używane przez API V4.

| Kod stanu | **Stan** | Opis |
| --- | --- | --- |
| 200 | OK | Żądanie zakończyło się powodzeniem. |
| 201 | Created | Zasób został utworzony. |
| 204 | No Content | Zasób został usunięty. Brak ładunku odpowiedzi. |
| 400 | Bad Request | Żądanie było nieprawidłowe, często z powodu błędnie sformułowanego lub brakującego parametru albo ładunku. |
| 401 | Unauthorized | Brak tokenu autoryzacji lub token jest nieprawidłowy. |
| 403 | Forbidden | Token autoryzacji nie ma wystarczających uprawnień do tego żądania. |
| 404 | Not Found | Żądany zasób nie istnieje. |
| 422 | Unprocessable Entity | Ładunek i/lub parametry żądania są poprawnie sformułowane, ale z innych względów nieprawidłowe, co uniemożliwia wykonanie żądania (w dużej mierze zamienny z 400 Bad Request). |
| 429 | Too Many Requests | Żądanie przekroczyło limit żądań API dla tego konta. Szczegóły znajdziesz w sekcji Ograniczanie liczby żądań w przewodniku dla początkujących. |
| 5xx | Server Errors | Nasz serwer zgłosił nieoczekiwany błąd. Klienci powinni odczekać co najmniej 30 sekund przed ponowieniem próby, a wszelkie automatyczne ponowienia powinny być ograniczone i uwzględniać losowy odstęp, a także wykładnicze wydłużanie odstępów (exponential back-off) między kolejnymi żądaniami. |

### Uwierzytelnianie i autoryzacja {#authentication-and-authorization}

API V4 korzysta z OAuth 2.0 i [Adobe Identity Management Server (IMS)](https://experienceleague.adobe.com/en/docs/commerce-admin/start/admin/ims/adobe-ims-integration-overview) do uwierzytelniania użytkownika (AuthN) i generowania tokenów dostępu w jego imieniu. Token dostępu musi być dołączany do każdego żądania API w nagłówku HTTP Authorization (tj. uwierzytelnianie tokenem Bearer).

<Note>

[Zakresy tokenów](https://developer.adobe.com/developer-console/docs/guides/authentication/UserAuthentication/ims#scopes) generowane przez IMS są statyczne, a autoryzacja (AuthZ), która określa, co użytkownik może robić (i jakie operacje API może wykonywać w jego imieniu), zależy od ról i uprawnień przyznanych użytkownikowi we Frame.io. Więcej informacji o generowaniu tokenów dostępu i wysyłaniu żądań o nie znajdziesz w sekcjach Getting Started with the Developer Console oraz Authentication Setup (w części Start Developing with Postman).

</Note>

### Wersje i zgodność wsteczna {#versions-and-backward-compatibility}

Frame.io V4 API *nie* jest wstecznie zgodne z wcześniejszymi wersjami API Frame.io i zasadniczo nie może być używane do uzyskiwania dostępu do zasobów w starszych kontach ani do ich aktualizowania, ponieważ pojęcia i model danych V4 uległy znacznym zmianom. Dlatego wszystkie identyfikatory URI powiązane z API V4 zawierają prefiks ścieżki `/v4`. API V4 wciąż jednak szybko się rozwija i możliwe jest, że nowe funkcje będą czasami wymagały zmian powodujących niezgodność. Częściej Frame.io będzie publikować w API nowe *dodatki*, które przez pewien czas uznajemy za eksperymentalne, co pozwala nam zbierać opinie klientów i dane o użyciu oraz na nie reagować. Zdając sobie sprawę, że zgodność wsteczna jest kluczowa dla klientów zarządzających integracjami produkcyjnymi o wysokich wymaganiach dotyczących dostępności, projektujemy API V4 tak, aby obsługiwało dodatkowy poziom wersjonowania za pomocą niestandardowego nagłówka HTTP. Pozwoli to klientom świadomie korzystać z eksperymentalnych punktów końcowych, unikać zmian powodujących niezgodność i zapewni gwarancje zgodności wstecznej w przestrzeni nazw V4. Więcej szczegółów wkrótce, ale na razie można bezpiecznie założyć, że pierwsze wydanie API V4 jest uznawane za stabilne i że minie trochę czasu, zanim rozważymy wprowadzenie zmian powodujących niezgodność.

### Ograniczanie liczby żądań {#rate-limiting}

Wszystkie wywołania API V4 podlegają limitom, a każdy zasób i operacja API mają własny skonfigurowany limit. Limity wahają się od zaledwie 10 żądań na minutę do nawet 100 żądań na sekundę. Obecnie każdy limit jest egzekwowany na poziomie *użytkownika*, ale same zasady i limity mogą ulec zmianie.

API V4 stosuje algorytm progresywnego ograniczania liczby żądań typu „[leaky bucket](https://wikipedia.org/wiki/Leaky_bucket)”, w którym limity odnawiają się stopniowo w przydzielonym oknie czasowym. Innymi słowy, nie istnieje sztywny punkt odcięcia, po którym limity dla danego zasobu się odnawiają (jak w strategiach „stałego” i „przesuwnego okna”). Zamiast tego pozostałe limity są stale odnawiane w tempie zależnym od limitu i okna czasowego zasobu. Żądania przekraczające limit dla danego punktu końcowego zakończą się błędem HTTP 429.

Zalecana przez nas strategia reagowania na błędy 429 jest zwykle nazywana „wykładniczym wydłużaniem odstępów” (exponential back-off).
W skrócie:

- Po otrzymaniu kodu `429` odczekaj pewien czas (co najmniej jedną sekundę) przed ponowieniem żądania
- Jeśli otrzymasz kolejny kod `429`, zwiększaj wykładniczo (lub co najmniej podwajaj) poprzedni czas oczekiwania, aż działanie wróci do normy

Aby ustalić limity mające zastosowanie do konkretnego żądania, klienci mogą sprawdzić następujące nagłówki HTTP zwracane w odpowiedzi:

| Nagłówek | Opis wartości |
| --- | --- |
| `x-ratelimit-limit` | Limit żądań dla tej ścieżki zasobu, mierzony liczbą żądań. |
| `x-ratelimit-remaining` | Liczba żądań pozostałych w bieżącym oknie czasowym. |
| `x-ratelimit-window` | Okno czasowe limitów dla tej ścieżki zasobu, mierzone w milisekundach (ms). |

## Szczegóły API {#api-details}

Ostatecznym źródłem dokumentacji API V4 jest nasz [przewodnik po API (API Reference)](/pl/platform/api-reference/account-permissions/account-user-roles-update), ale przed wysłaniem pierwszych żądań warto zrozumieć hierarchię zasobów modelowaną przez API V4.

### Hierarchia zasobów {#resource-hierarchy}

[Konto](https://help.frame.io/en/collections/8779087-account-settings) (Account) jest zwykle powiązane z organizacją i stanowi podstawowy zasób, który określa plan subskrypcji, własność treści, role i uprawnienia użytkowników oraz organizację obszarów roboczych. Dlatego ścieżka URL niemal wszystkich punktów końcowych API V4 zawiera prefiks identyfikujący konto, w którym znajduje się zasób.

Obszary robocze (Workspaces, w starszej wersji Frame.io nazywane zespołami — Teams) i [projekty](https://help.frame.io/en/articles/9101006-project-settings) (Projects) służą do organizowania zarówno treści, jak i użytkowników, w tym określania, kto ma dostęp do jakich treści.

Podstawowa hierarchia zasobów treści we Frame.io wygląda następująco:

<CardGroup cols={2}>

<Card title="Hierarchia zasobów" icon="sitemap" iconType="solid">

**Account → Workspace → Project → Folder → Folder / Version Stack / File**

</Card>

</CardGroup>

Każdy zasób przesłany do Frame.io jest ostatecznie reprezentowany jako [plik](https://help.frame.io/en/articles/9436564-supported-file-types-on-frame-io) (File), natomiast [foldery](https://help.frame.io/en/articles/9101044-creating-folders) (Folders) i [stosy wersji](https://help.frame.io/en/articles/9101068-version-stacking) (Version Stacks) to zasoby przechowywania, które pełnią funkcję kontenerów i stanowią podstawę hierarchicznego modelu przechowywania obsługującego wersjonowane zasoby. Większość użytkowników zna już podstawowe pojęcie folderu we Frame.io: jest to po prostu nieuporządkowany kontener innych zasobów przechowywania (modelowanych jako jego `children`), który stanowi węzeł w drzewie folderów. Każdy projekt ma unikalny folder główny (identyfikowany kluczem `root_folder_id`), który jest korzeniem drzewa folderów, w którym znajdują się wszystkie zasoby projektu.

Stos wersji to uporządkowany kontener plików. Jego kolejność jest ściśle liniowa i określa numer wersji każdego elementu podrzędnego, ale klienci mogą dowolnie zmieniać kolejność plików w stosie wersji. Plik zawsze jest w danym momencie elementem podrzędnym (zawartym w) dokładnie jednego folderu *lub* stosu wersji. Podobnie folder lub stos wersji zawsze jest elementem podrzędnym dokładnie jednego folderu (z wyjątkiem folderu głównego projektu).

Więcej informacji o wykonywaniu podstawowych operacji CRUD na plikach i folderach przechowywanych we Frame.io znajdziesz w [przewodniku po API (API Reference)](https://developer.frame.io/platform/v4-experimental/api/current). Obecnie API V4 obsługuje stosy wersji tylko podczas wyświetlania zawartości folderu, ale punkty końcowe do tworzenia i aktualizowania stosów wersji będą dostępne wkrótce.
