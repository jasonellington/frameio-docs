## Wprowadzenie {#introduction}

API Frame.io V4 to przeprojektowana wersja Legacy API, często nazywanego *endpointami V2* lub *API Frame.io V3*. Nowy projekt w pełni wykorzystuje nowe możliwości i funkcje Frame V4, zachowując jednocześnie całą istotną funkcjonalność Legacy API. Ten przewodnik przedstawia najważniejsze różnice między Legacy API a API V4 oraz zawiera instrukcje krok po kroku, które pomogą Ci przeprowadzić migrację bez problemów.

## Lista kontrolna migracji {#migration-checklist}

<Steps>

<Step title="Uwierzytelnianie">

W przypadku <Tooltip tip="Konta, które korzystały z Legacy API z wygenerowanym tokenem programisty i zostały automatycznie zmigrowane do V4. Nie dotyczy to kont utworzonych w V4 ani kont zmigrowanych ręcznie">**kont automatycznie zmigrowanych do V4**</Tooltip>, które nie są jeszcze administrowane za pomocą Adobe Admin Console, możesz nadal używać tokenów programisty Legacy zarządzanych w [witrynie dla programistów Frame.io](/pl/platform/v4-experimental/welcome), ale musisz dodać do żądań API nagłówek z kluczem `x-frameio-legacy-token-auth` i wartością `true`. W przeciwnym razie wykonaj kroki opisane w sekcji [Uwierzytelnianie](#adobe-developer-console-managed-authentication) poniżej.

</Step>

<Step title="Zaktualizuj istniejące wywołania API">

Wszystkie trasy Legacy API trzeba będzie odwzorować na nowe trasy i ładunki JSON API V4. Poniżej znajduje się dość obszerna tabela [odwzorowań](#endpoint-mappings-legacy-api-to-v4), która ułatwi ten proces.

</Step>

<Step title="Testowanie jest wysoce zalecane">

**Przeprowadź dokładne testy.** Ponieważ API zawiera wiele zmian, zalecamy testowanie na koncie V4, aby upewnić się, że nowe API działa zgodnie z oczekiwaniami.

</Step>

<Step title="Zaimplementuj dedykowane logowanie">

Zaimplementuj dedykowaną metodę logowania dla V4, ponieważ adresy URL uwierzytelniania są oddzielne. Adres URL uwierzytelniania V4 różni się od adresu Legacy API, nie zwraca w odpowiedzi kont, które nie zostały jeszcze uaktualnione do V4, i należy go traktować jako oddzielną integrację.

</Step>

</Steps>

<Note>

Jeśli masz pytania dotyczące endpointu, którego nie ma w poniższej tabeli odwzorowań, skontaktuj się z naszym zespołem pomocy technicznej pod adresem [support@frame.io](mailto:support@frame.io).

</Note>

## Uwierzytelnianie zarządzane przez Adobe Developer Console {#adobe-developer-console-managed-authentication}

W przypadku kont zmigrowanych do V4, które są zarządzane za pomocą [Adobe Developer Console](https://developer.adobe.com/developer-console/), musisz używać API V4 z OAuth2.0. Wykonaj poniższe kroki.

<Steps>

<Step title="Utwórz projekt Adobe">

**Utwórz projekt w Adobe Developer Console** i dodaj Frame.io jako produkt.

</Step>

<Step title="Wybierz typ uwierzytelniania">

**Uwierzytelnij się.** Więcej informacji znajdziesz w [przewodniku po uwierzytelnianiu](https://developer.adobe.com/frameio/guides/Authentication/). Jeśli Twoje konto V4 nie jest jeszcze zarządzane za pomocą Adobe Admin Console, możesz pominąć ten krok.

- **Uwierzytelnianie użytkownika**: łączy się z Frame za pomocą Client ID i/lub Client Secret i wymaga, aby użytkownik zalogował się, podając nazwę użytkownika i hasło.
- **Uwierzytelnianie typu serwer–serwer**: łączy się z Frame za pomocą Client ID i Client Secret, ale nie wymaga udziału użytkownika logującego się przez przeglądarkę.

</Step>

<Step title="Zaimplementuj uwierzytelnianie Bearer">

**Uwierzytelnianie JWT Bearer**: w każdym żądaniu API przekazuj token uwierzytelniający w nagłówku z kluczem `Authorization` i wartością `Bearer <IMS_ACCESS_TOKEN>`.

</Step>

</Steps>

## Odwzorowania endpointów (z Legacy API do V4) {#endpoint-mappings-legacy-api-to-v4}

<Note>

Jeśli korzystasz z uwierzytelniania za pomocą tokenu programisty Legacy, musisz dodać do żądań API nagłówek z kluczem x-frameio-legacy-token-auth i wartością true.

</Note>

Ogólne uwagi pomocne przy migracji:

<Steps>

<Step title="Ładunki">

Ładunki żądań i odpowiedzi mogą się różnić.

</Step>

<Step title="Zespoły → Obszary robocze">

„Zespoły” (Teams) w Legacy API są odpowiednikiem „obszarów roboczych” (Workspaces) w V4.

</Step>

<Step title="Zasoby">

„Zasoby” (Assets) z Legacy API są teraz w V4 podzielone na „pliki” (Files), „foldery” (Folders) i „stosy wersji” (Version Stacks).

</Step>

<Step title="Uprawnienia">

Uprawnienia i role w V4 są inne, co zmienia strukturę endpointów. W V4 istnieją role użytkowników na poziomie obszaru roboczego i projektu. Więcej informacji znajdziesz w artykule [Zarządzanie uprawnieniami użytkowników](/pl/platform/docs/guides/managing-user-permissions).

</Step>

</Steps>

### 7. Komentarze {#7-comments}

Większość funkcji komentarzy w API V4 jest obecnie obsługiwana.

<Info>

**Funkcje dostępne wkrótce:**

- Reakcje na komentarze, czyli emoji
- Wyświetlanie lub modyfikowanie statusu ukończenia komentarza
- Sprawdzanie, kto wyświetlił komentarz (wyświetlenia)

</Info>

<Note>

Pole "timestamp" oznacza numer klatki (framestamp), przy której pozostawiono komentarz (licząc od 1), a nie znacznik czasu

</Note>

### 9. Webhooki {#9-webhooks}

Webhooki używane w V3 zostaną zmigrowane i w większości będą działać tak samo. Po migracji będą wyłączone i trzeba je włączyć, aby działały. W przypadku zdarzeń dotyczących zasobów konieczne będą pewne zmiany, ponieważ są one teraz podzielone na pliki i foldery. Pojawiły się też nowe zdarzenia specyficzne dla V4, o których warto wiedzieć: metadata.value.updated, zdarzenia związane z kolekcjami oraz zdarzenia związane z udostępnieniami.

Przed ponownym włączeniem zmigrowanych webhooków zapoznaj się z [limitami szybkości webhooków](/pl/platform/docs/guides/webhooks#webhook-rate-limits). Zdarzenia webhooków V4 i akcji niestandardowych podlegają wspólnym limitom wynoszącym **1000 zdarzeń na minutę** i **20 000 zdarzeń na godzinę** na konto. Oba limity dotyczą łącznej liczby zdarzeń w całym koncie.

Uwaga: aby pobrać wszystkie webhooki konta, musisz pobrać wszystkie obszary robocze konta, a następnie wszystkie webhooki tych obszarów roboczych. |

## Kroki migracji {#migration-steps}

<Steps>

<Step title="Dostosuj nieobsługiwane endpointy V2">

**Dostosuj** wszystkie nieobsługiwane endpointy Legacy V2.

</Step>

<Step title="Zaktualizuj bazowe adresy URL">

**Zaktualizuj bazowe adresy URL** z `api.frame.io/v2/...` na `api.frame.io/v4/...`.

</Step>

<Step title="Zaktualizuj żądania API">

**Zaktualizuj żądania API** w swoim kodzie, aby odwoływały się do nowego schematu endpointów.

</Step>

<Step title="Zaktualizuj ładunki JSON">

**Zaktualizuj ładunki JSON** w schematach żądań i odpowiedzi, aby mieć pewność, że wysyłasz i odczytujesz właściwe pola.

</Step>

<Step title="Zaktualizuj terminologię">

Zaktualizuj terminologię w kodzie i interfejsie użytkownika: „zespoły” → „obszary robocze”; „zasoby” → „pliki/foldery”; „linki do recenzji” lub „linki do prezentacji” → „udostępnienia”.

</Step>

<Step title="Przetestuj endpointy">

**Przetestuj** wszystkie zaktualizowane endpointy. Jeśli otrzymasz błąd 403, 404 lub 422, sprawdź endpointy, strukturę ładunku żądania itp.

</Step>

<Step title="Analizuj odpowiedzi z błędami">

**Analizuj** nowe, szczegółowe odpowiedzi z błędami — jeśli wywołanie API się nie powiedzie, szukaj przyczyny w odpowiedzi JSON `{"errors": [...]}`.

</Step>

<Step title="Wdróż w środowisku produkcyjnym">

**Wdróż** rozwiązanie w środowisku produkcyjnym po jego zweryfikowaniu na koncie [Frame.io](http://frame.io/) V4.

</Step>

</Steps>

## Obsługa błędów i typowe problemy {#error-handling-&-common-issues}

<Note>

Niektóre trasy zwracają błędy z niestandardowymi opisami, które mogą się nieznacznie różnić od poniższych przykładów.

</Note>

<CardGroup cols={2}>

<Card title="Błędy klienta (4xx)" icon="triangle-exclamation" iconType="solid">

- **400** Bad Request: sprawdź poprawność ładunku.
- **401** Unauthorized: nieprawidłowy lub brakujący token autoryzacji.
- **403** Forbidden: brak zakresu lub użytkownik nie ma dostępu.
- **404** Not Found: sprawdź endpoint, wersję API lub identyfikatory.
- **422** Unprocessable Entity: zweryfikuj dane żądania.
- **429** Too Many Requests: zaimplementuj ponawianie prób z wycofywaniem (backoff).

</Card>

<Card title="Błędy serwera (5xx)" icon="server" iconType="solid">

- **500** Internal Server Error: ponów próbę po krótkiej przerwie.

</Card>

</CardGroup>
