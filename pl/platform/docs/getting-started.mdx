## Co nowego we Frame.io V4 Developer API? {#what’s-new-in-the-frame-io-v4-developer-api}

Tak jak aplikacja Frame.io została całkowicie przebudowana w wersji 4, tak również API V4 zostało zaprojektowane od podstaw. Chociaż niektóre kluczowe koncepcje pozostają podobne do starszych wersji, wiele z nich zastąpiono lub przeprojektowano, aby obsługiwały bardziej zaawansowane przepływy pracy związane ze współpracą oraz integracje. Wprowadzenie zupełnie nowego API dało nam też okazję do radykalnego uproszczenia operacji i nadania priorytetu ważnym przepływom pracy klientów.

<Info>

Porównanie Frame.io V4 ze starszą wersją znajdziesz [tutaj](https://help.frame.io/en/articles/9084073-frame-io-v4-legacy-feature-comparison).

</Info>

W API V4 nazwy niektórych zasobów, takich jak przestrzenie robocze (Workspaces, w starszej wersji Frame.io nazywane zespołami — Teams), zmieniono, aby odpowiadały Frame.io w wersji 4, a inne, jak zasoby (Assets) w starszej wersji, przemianowano tak, by odnosiły się do konkretnych jednostek przechowywania (plików, folderów i stosów wersji), co ma ograniczyć dezorientację programistów. Jeszcze inne, na przykład pola niestandardowe (Custom Fields) i udostępnienia (Shares), są zupełnie nowe. Wśród innych istotnych zmian znacznie ograniczyliśmy ilość danych zwracanych domyślnie w odpowiedzi na żądania zasobów, zmieniliśmy nazwy niektórych właściwości w odpowiedziach, aby były dokładniejsze i spójne w całym API, oraz przeszliśmy na nowy mechanizm stronicowania oparty na kursorach. Dlatego należy pamiętać, że — z wyjątkiem API Camera to Cloud (C2C) — klienci zintegrowani ze starszym API nie są zgodni z API V4.

Ponadto niektóre funkcje są nadal w trakcie opracowywania i mają szybko pojawiać się oraz rozwijać w odpowiedzi na rzeczywiste przypadki użycia i opinie klientów. Przykładem jest możliwość tworzenia akcji niestandardowych i stosów wersji. Jeśli wydaje się, że brakuje funkcji, która była wcześniej dostępna w starszym API, najprawdopodobniej istnieje alternatywa lub funkcja wkrótce będzie dostępna — chętnie jednak o tym usłyszymy.

Zanim zagłębisz się w API V4, warto najpierw zrozumieć podstawowe koncepcje aplikacji Frame.io w wersji 4. Dobrym punktem wyjścia jest [baza wiedzy Frame.io V4](https://help.frame.io/en/). Koncepcje takie jak konta, użytkownicy, przestrzenie robocze, projekty, kolekcje, udostępnienia i pola niestandardowe (metadane) są w API V4 modelowane jako odrębne zasoby, a zrozumienie ich relacji i możliwości w aplikacji ułatwi zrozumienie, jak działają w API V4.

## Przegląd API {#api-overview}

API Frame.io V4 zostało zaprojektowane zgodnie z zasadami architektury RESTful i wykorzystuje standardowe metody HTTP oraz kody odpowiedzi w połączeniu z unikalnymi adresami URL specyficznymi dla zasobów. Frame.io publikuje [specyfikację OpenAPI 3.0](https://api.frame.io/v4/openapi.json) dla API V4, która zawiera szczegółowe informacje o jego endpointach, parametrach żądań i odpowiedziach. Specyfikację OpenAPI mogą wykorzystywać różne narzędzia innych firm do generowania kodu, co ułatwia szybkie tworzenie aplikacji klienckich.

### Konwencje adresów URL i ścieżek {#url-and-path-conventions}

Ścieżki URL opublikowane w specyfikacji OpenAPI zasadniczo odzwierciedlają relacje własności i zawierania się zasobów. Dlatego niektóre parametry żądań (np. identyfikatory kont, identyfikatory folderów itp.) są osadzone w ścieżce zasobu. Chociaż ścieżki te mają być przewidywalne i łatwe do zrozumienia, struktura niektórych adresów URL zwracanych przez żądania API (np. wstępnie podpisanych adresów URL przesyłania lub linków do wyświetlania) może ulec zmianie i nigdy nie powinna być składana bezpośrednio przez aplikację kliencką.

### Parametry zapytania żądania {#request-query-parameters}

Parametry żądania, które sterują stronicowaniem oraz opcjonalnym dołączaniem powiązanych zasobów do obiektów odpowiedzi, są zdefiniowane jako standardowy zestaw parametrów zapytania: `include`, `page_size`, `include_total_count`. Niektóre żądania mogą obsługiwać dodatkowe parametry zapytania specyficzne dla danego zasobu lub operacji.

```html
GET https://api.frame.io/v4/accounts/{account_id}/folders/{folder_id}/children?&include=project&page_size=5&include_total_count=true
```

### Ładunki żądań i odpowiedzi {#request-and-response-payloads}

Zarówno ładunki żądań, jak i odpowiedzi mają postać obiektów JSON, dlatego nagłówek content-type żądania HTTP POST, PUT lub PATCH musi określać typ nośnika `application/json`. Podczas tworzenia lub aktualizowania zasobów właściwość `data` żądania musi zawierać obiekt zasobu. Atrybuty tworzonego lub aktualizowanego zasobu znajdują się w tym obiekcie. Podobnie pomyślne odpowiedzi zawierające zasoby udostępniają je we właściwości `data` odpowiedzi.

### Stronicowanie {#pagination}

Odpowiedzi, które mogą zwracać dużą liczbę obiektów zasobów (np. listy folderów lub komentarzy), są stronicowane, aby ograniczyć opóźnienie żądań w miarę wzrostu zbioru wyników. Oznacza to, że odpowiedź na żądanie może zawierać tylko jedną „stronę” wyników. Jak wspomniano powyżej, klient może podczas wysyłania żądania wybrać konkretny rozmiar strony, maksymalnie do 100 elementów, za pomocą parametru zapytania `page_size`. Jeśli nie zostanie on określony, domyślny rozmiar strony wynosi 50 elementów. API V4 korzysta z formy stronicowania zwanej *stronicowaniem opartym na kursorach* i umieszcza we właściwości `links` obiektu odpowiedzi (zobacz przykład poniżej) link względny, który zawiera nieprzezroczysty ciąg kursora (klienci nie powinni próbować samodzielnie tworzyć tego ciągu) w parametrze zapytania `after`, co pozwala klientowi pobrać następną stronę wyników (zobacz przykładową odpowiedź poniżej) za pomocą kolejnych żądań. Obecnie API V4 obsługuje wyłącznie stronicowanie jednokierunkowe.

### Błędy {#errors}

W przypadku wystąpienia błędu właściwość `errors` w obiekcie odpowiedzi będzie zawierać tablicę jednego lub więcej obiektów błędów, które dostarczają szczegółów na temat wystąpienia błędu (błędów). Obecnie API V4 nie obsługuje operacji wsadowych, więc nie ma przypadków, w których klient musiałby obsługiwać częściowe powodzenie i błędy.

```json
{
    "errors": [
        {
            "detail": "Unexpected field: foo",
            "source": {
                "pointer": "/data/foo"
            },
            "title": "Invalid value"
        }
    ]
}
```

Poniższa tabela zawiera typowe kody stanu używane przez API V4.

| Kod stanu | **Stan** | Opis |
| --- | --- | --- |
| 200 | OK | Żądanie zakończyło się powodzeniem. |
| 201 | Created | Zasób został utworzony. |
| 204 | No Content | Zasób został usunięty. Brak ładunku odpowiedzi. |
| 400 | Bad Request | Żądanie było nieprawidłowe, często z powodu źle sformułowanego lub brakującego parametru albo ładunku. |
| 401 | Unauthorized | Brak tokenu autoryzacji lub token jest nieprawidłowy. |
| 403 | Forbidden | Token autoryzacji nie ma wystarczających uprawnień do tego żądania. |
| 404 | Not Found | Żądany zasób nie istnieje. |
| 422 | Unprocessable Entity | Ładunek i/lub parametry żądania są poprawnie sformułowane, ale z innych względów nieprawidłowe, co uniemożliwia wykonanie żądania (w dużej mierze zamienne z 400 Bad Request). |
| 429 | Too Many Requests | Żądanie przekroczyło limit liczby żądań API dla tego konta. Szczegóły znajdziesz w sekcji Limity liczby żądań w przewodniku wprowadzającym. |
| 5xx | Server Errors | Nasz serwer zgłosił nieoczekiwany błąd. Klienci powinni odczekać co najmniej 30 sekund przed ponowieniem próby, a wszelkie automatyczne ponowienia powinny być ograniczone i uwzględniać losowy odstęp, a także stosować wykładnicze wycofywanie (exponential back-off) w kolejnych żądaniach. |

### Uwierzytelnianie i autoryzacja {#authentication-and-authorization}

API V4 wykorzystuje OAuth 2.0 oraz [Adobe Identity Management Server (IMS)](https://experienceleague.adobe.com/en/docs/commerce-admin/start/admin/ims/adobe-ims-integration-overview) do uwierzytelniania użytkownika (AuthN) i generowania tokenów dostępu w jego imieniu. Token dostępu musi być dołączany do każdego żądania API za pomocą nagłówka HTTP Authorization (tj. uwierzytelnianie tokenem typu Bearer).

<Note>

[Zakresy tokenów](https://developer.adobe.com/developer-console/docs/guides/authentication/UserAuthentication/ims#scopes) generowane przez IMS są statyczne, a autoryzacja (AuthZ), która określa, co użytkownik może robić (i jakie operacje API może wykonywać w jego imieniu), zależy od ról i uprawnień przyznanych użytkownikowi w Frame.io. Więcej informacji o generowaniu tokenów dostępu i wysyłaniu po nie żądań znajdziesz w sekcjach Getting Started with the Developer Console oraz Authentication Setup (w części Start Developing with Postman).

</Note>

### Wersje i zgodność wsteczna {#versions-and-backward-compatibility}

API Frame.io V4 *nie* jest wstecznie zgodne z wcześniejszymi wersjami API Frame.io i co do zasady nie może być używane do uzyskiwania dostępu do zasobów w starszych kontach ani do ich aktualizowania, ponieważ koncepcje i model danych V4 uległy znaczącym zmianom. Dlatego wszystkie identyfikatory URI powiązane z API V4 zawierają prefiks ścieżki `/v4`. API V4 wciąż jednak szybko się rozwija i możliwe, że nowe funkcje będą czasami wymagać zmian powodujących niezgodność. Częściej Frame.io będzie udostępniać nowe *dodatki* do API, które przez pewien czas uznajemy za eksperymentalne, co pozwala nam zbierać opinie klientów i metryki użycia oraz na nie reagować. Zdając sobie sprawę, że zgodność wsteczna jest bardzo ważna dla klientów utrzymujących integracje produkcyjne o wysokich wymaganiach dotyczących dostępności, projektujemy API V4 tak, aby obsługiwało dodatkowy poziom wersjonowania za pomocą niestandardowego nagłówka HTTP. Pozwoli to klientom dobrowolnie korzystać z eksperymentalnych endpointów, unikać zmian powodujących niezgodność i zapewni gwarancje zgodności wstecznej w przestrzeni nazw V4. Więcej szczegółów wkrótce, ale na razie można bezpiecznie założyć, że pierwsze wydanie API V4 jest uznawane za stabilne i że minie trochę czasu, zanim rozważymy wprowadzenie zmian powodujących niezgodność.

### Limity liczby żądań {#rate-limiting}

Wszystkie wywołania API V4 podlegają limitom liczby żądań, a każdy zasób i każda operacja API mają skonfigurowany własny limit. Limity wahają się od zaledwie 10 żądań na minutę do nawet 100 żądań na sekundę. Obecnie każdy limit jest egzekwowany *na użytkownika*, ale same zasady i limity mogą ulec zmianie.

API V4 stosuje algorytm progresywnego ograniczania liczby żądań typu „[leaky bucket](https://wikipedia.org/wiki/Leaky_bucket)”, w którym limity odnawiają się stopniowo w przydzielonym oknie czasowym. Innymi słowy, nie ma sztywnego punktu odcięcia, po którym limity dla danego zasobu się odnawiają (jak w strategiach „stałego” i „przesuwnego okna”). Zamiast tego pozostałe limity stale się odnawiają w tempie zależnym od limitu i okna czasowego zasobu. Żądania przekraczające limit dla danego endpointu kończą się błędem HTTP 429.

Zalecana przez nas strategia reagowania na błędy 429 jest zwykle nazywana „wykładniczym wycofywaniem” (exponential back-off).
W skrócie:

- Po otrzymaniu kodu `429` odczekaj pewien czas (co najmniej jedną sekundę) przed ponowieniem żądania
- Jeśli otrzymasz kolejny kod `429`, zwiększaj wykładniczo, a co najmniej podwajaj poprzedni czas oczekiwania, aż do przywrócenia normalnego działania

Aby ustalić limity liczby żądań dotyczące konkretnego żądania, klienci mogą sprawdzić następujące nagłówki HTTP zwracane w odpowiedzi:

| Nagłówek | Opis wartości |
| --- | --- |
| `x-ratelimit-limit` | Limit liczby żądań dla tej ścieżki zasobu, mierzony w żądaniach. |
| `x-ratelimit-remaining` | Liczba żądań pozostałych w bieżącym oknie czasowym. |
| `x-ratelimit-window` | Okno czasowe limitów dla tej ścieżki zasobu, mierzone w milisekundach (ms). |

## Szczegóły API {#api-details}

Najbardziej miarodajną dokumentacją API V4 jest nasz [przewodnik po API](/pl/platform/api-reference/account-permissions/account-user-roles-update), jednak przed wysłaniem pierwszych żądań warto zrozumieć hierarchię zasobów modelowaną przez API V4.

### Hierarchia zasobów {#resource-hierarchy}

[Konto](https://help.frame.io/en/collections/8779087-account-settings) jest zazwyczaj powiązane z organizacją i stanowi podstawowy zasób, który określa plan subskrypcji, własność treści, role i uprawnienia użytkowników oraz organizację przestrzeni roboczych. Dlatego ścieżka URL niemal wszystkich endpointów API V4 zawiera prefiks identyfikujący konto, w którym znajduje się zasób.

Przestrzenie robocze (w starszej wersji Frame.io nazywane zespołami) i [projekty](https://help.frame.io/en/articles/9101006-project-settings) służą do organizowania zarówno treści, jak i użytkowników, w tym określania, kto ma dostęp do jakich treści.

Podstawowa hierarchia zasobów treści we Frame.io wygląda następująco:

<CardGroup cols={2}>

<Card title="Hierarchia zasobów" icon="sitemap" iconType="solid">

**Konto → Przestrzeń robocza → Projekt → Folder → Folder / Stos wersji / Plik**

</Card>

</CardGroup>

Każdy zasób przesłany do Frame.io jest ostatecznie reprezentowany jako [plik](https://help.frame.io/en/articles/9436564-supported-file-types-on-frame-io), natomiast [foldery](https://help.frame.io/en/articles/9101044-creating-folders) i [stosy wersji](https://help.frame.io/en/articles/9101068-version-stacking) to zasoby przechowywania, które pełnią funkcję kontenerów i stanowią podstawę hierarchicznego modelu przechowywania obsługującego zasoby z wersjami. Większość użytkowników zna już podstawową koncepcję folderu we Frame.io: służy on po prostu jako nieuporządkowany kontener innych zasobów przechowywania (modelowanych jako jego `children`) i reprezentuje węzeł w drzewie folderów. Każdy projekt ma unikalny folder główny (identyfikowany kluczem `root_folder_id`), który stanowi korzeń drzewa folderów, w którym znajdują się wszystkie zasoby projektu.

Stos wersji to uporządkowany kontener plików. Jego kolejność jest ściśle liniowa i określa numer wersji każdego elementu podrzędnego, ale klienci mogą dowolnie zmieniać kolejność plików w stosie wersji. Plik jest w danym momencie zawsze elementem podrzędnym (zawartym w) dokładnie jednego folderu *lub* stosu wersji. Podobnie folder lub stos wersji jest zawsze elementem podrzędnym dokładnie jednego folderu (z wyjątkiem folderu głównego projektu).

Więcej informacji o wykonywaniu podstawowych operacji CRUD na plikach i folderach przechowywanych we Frame.io znajdziesz w [przewodniku po API](https://developer.frame.io/platform/api/current). Obecnie API V4 obsługuje stosy wersji tylko podczas wyświetlania zawartości folderu, ale endpointy do tworzenia i aktualizowania stosów wersji będą dostępne wkrótce.
