## Czym jest webhook? {#what’s-a-webhook}

**Webhook** to wywołanie zwrotne HTTP typu push, które Frame.io wysyła **natychmiast, gdy na Twoim koncie wydarzy się coś istotnego** (np. zakończy się transkodowanie nowego pliku, zostanie dodany komentarz lub utworzony projekt).
Zamiast odpytywać API, podajesz publiczny adres URL HTTPS, a Frame.io wysyła pod ten adres ładunek JSON w czasie rzeczywistym, dzięki czemu możesz:

<Card title="Zasilać kanały Slack lub systemy zgłoszeń" icon="bell" iconType="solid" />

</CardGroup>

Więcej informacji o tym, czym jest webhook i jak działa, znajdziesz na stronie [https://docs.webhook.site/](https://docs.webhook.site/).

## Przegląd endpointów {#endpoint-overview}

| **Operacja** | **Endpoint** | **Szczegóły** |
| --- | --- | --- |
| **Utworzenie** webhooka | POST /v4/accounts/\{account_id\}/workspaces/\{workspace_id\}/webhooks | Treść z polami `name`, `url`, `events[]` |
| **Wyświetlenie listy** wszystkich webhooków Workspace’u | GET /v4/accounts/\{account_id\}/workspaces/\{workspace_id\}/webhooks | Obsługuje paginację |
| **Wyświetlenie** jednego webhooka | GET /v4/webhooks/\{webhook_id\} | Sekret podpisywania jest zwracany tylko w momencie utworzenia |
| **Aktualizacja** webhooka | PATCH /v4/webhooks/\{webhook_id\} | Zmiana `url`, `events` lub `is_active` |
| **Usunięcie** webhooka | DELETE /v4/webhooks/\{webhook_id\} | Natychmiast wstrzymuje dostarczanie |

<Warning>

**Uwierzytelnianie** — Wszystkie endpointy V4 wymagają tokenu dostępu OAuth 2.0 uzyskanego przez Adobe Developer Console. Starsze tokeny deweloperskie i tokeny JWT **nie** są akceptowane.

</Warning>

## Zmiany i aktualizacje w Frame V4 {#changes-and-updates-in-frame-v4}

<Info>

Webhooki utworzone w wersji Legacy są przenoszone do V4 z następującymi zmianami:

1. **Struktura ładunku**: do ładunku dodano identyfikator konta (Account ID)
2. **Zmiany endpointów**: `team_id` nie jest już przekazywany w ładunku JSON, lecz w parametrze ścieżki adresu URL: `https://api.frame.io/v4/accounts/:account_id/workspaces/:workspace_id/webhooks`
3. **Integracja z API**: ze względu na zmiany w strukturze API, endpointach i metodach uwierzytelniania istniejący kod obsługujący przychodzące webhooki, który wykonuje kolejne wywołania Frame.io API w celu wzbogacenia danych i wyszukiwania zasobów, wymaga aktualizacji
4. **Typy zdarzeń**: webhooki zasobów (asset) zostały podzielone na osobne zdarzenia dla plików (File) i folderów (Folder) — wszelkie webhooki z wersji Legacy korzystające ze zdarzeń asset należy zaktualizować, aby używały odpowiednich zdarzeń File i Folder

</Info>

<Warning>

**Status webhooków po migracji** — Gdy Twoje konto zostanie zmigrowane do Frame.io V4, istniejące webhooki z poprzednich wersji są automatycznie wyłączane. Dzięki temu możesz dostosować endpointy webhooków i logikę integracji do zmian w V4, zanim ponownie je aktywujesz. Webhooki, które nie zostały zaktualizowane pod kątem zgodności z V4, będą powodować błędy, jeśli zostaną włączone bez odpowiednich modyfikacji. Możesz sprawdzić, które webhooki są nieaktywne, analizując pole `is_active` przez API lub przeglądając [ustawienia webhooków](https://next.frame.io/settings/webhooks) przed ich ponownym włączeniem.

</Warning>

## Subskrypcje zdarzeń webhooków {#webhook-event-subscriptions}

Podczas tworzenia i aktualizowania webhooków określ, które zdarzenia Cię interesują. Możesz wybrać dowolną ich liczbę, jednak lepiej sprawdza się subskrybowanie mniejszej liczby zdarzeń i logiczne rozdzielenie webhooków z użyciem różnych schematów nazewnictwa i różnych endpointów. Dzięki temu możesz modelować logikę biznesową po stronie odbiorczej tak, aby ograniczyć filtrowanie i routing we współdzielonych funkcjach.

<Note>

Zakres zdarzeń — Wszystkie zdarzenia są ograniczone do Workspace’u podanego podczas tworzenia webhooka. Oznacza to, że zdarzenia będą wysyłane dla działań wykonanych we wszystkich projektach w tym Workspace’ie.

</Note>

## Ładunek wiadomości webhooka {#webhook-message-payload}

Wszystkie ładunki webhooków zawierają pole `type`, wskazujące zdarzenie, które wystąpiło, oraz obiekt `resource`. Obiekt `resource` zawiera `type` i `ID` zasobu Frame.io powiązanego ze zdarzeniem.

### Przykładowy ładunek {#example-payload}

```json
{
  "account": {
    "id": "6f70f1bd-7e89-4a7e-b4d3-7e576585a181"
  },
  "project": {
    "id": "7e46e495-4444-4555-8649-bee4d391a997"
  },
  "resource": {
    "id": "d3075547-4e64-45f0-ad12-d075660eddd2",
    "type": "file"
  },
  "type": "file.ready",
  "user": {
    "id": "56556a3f-859f-4b38-b6c6-e8625b5da8a5"
  },
  "workspace": {
    "id": "378fcbf7-6f88-4224-8139-6a743ed940b2"
  }
}
```

W powyższym przykładzie zdarzenia `file.created` pole `resource.id` wskazuje `ID` nowo utworzonego pliku. Dodatkowo dołączone są obiekty `workspace`, `project` i `user`, które zawierają powiązane wartości `workspace.id`, `project.id` i `user.id`. Wartości te można wykorzystać do ograniczenia liczby wywołań API poprzez filtrowanie przychodzących zdarzeń lub wyszukiwanie danych zapisanych lokalnie w pamięci podręcznej.

<Warning>

**Poza identyfikatorem zasobu nie dołączamy żadnych dodatkowych informacji o subskrybowanym zasobie**.

Jeśli Twoja aplikacja potrzebuje dodatkowych informacji lub kontekstu, zalecamy wykonanie wywołania API w celu pobrania szczegółów dotyczących zasobów, do których odnosi się zdarzenie.

</Warning>

## Bezpieczeństwo {#security}

Domyślnie wszystkie webhooki mają klucz podpisywania. Tego niekonfigurowalnego sekretu podpisywania można użyć do sprawdzenia, czy żądanie pochodzi z Frame.io.

Ładunek odpowiedzi dla skonfigurowanego webhooka zawiera sekret podpisywania właściwy dla tego webhooka. Sekret ten jest **zwracany wyłącznie w tej początkowej odpowiedzi na utworzenie webhooka**, dlatego przechowuj go w bezpiecznym miejscu, w magazynie sekretów lub w zmiennych środowiskowych. Użyj go później, aby sprawdzić, czy webhook pochodzi bezpośrednio z naszych serwerów i nie został w żaden sposób przechwycony ani zmodyfikowany.

### Weryfikacja podpisów webhooków {#verifying-webhook-signatures}

Aby chronić integrację przed atakami typu man-in-the-middle i atakami powtórzeniowymi, niezbędna jest weryfikacja podpisu ładunku webhooka. Weryfikacja gwarantuje, że ładunki webhooków zostały faktycznie wysłane przez Frame.io, a ich zawartość nie została zmodyfikowana podczas przesyłania.

Wraz z żądaniem `POST` przesyłane są następujące nagłówki HTTP:

| Nazwa nagłówka | Opis | Przykład |
| --- | --- | --- |
| `X-Frameio-Request-Timestamp` | Znacznik czasu wysłania żądania | `1604004499` |
| `X-Frameio-Signature` | Obliczony podpis webhooka | `v0=a77ce6856e609c884575c2fd211d07a9ad1c3f72e19c06ff710e8f086ffca883` |
| `user-agent: "Frame.io V4 API"` | User agent w nagłówku dla V4 |  |
| `user-agent: "Frame.io Legacy API"` | User agent w nagłówku dla wersji Legacy |  |

```python title="Python"
import hmac
import hashlib

def verify_signature(curr_time, req_time, signature, body, secret):
    """
    Verify Webhook signature
    :Args:
        curr_time (float): Current epoch time
        req_time (float): Request epoch time
        signature (str): Signature provided by the Frame.io API for the given request
        body (str): Webhook body from the received POST
        secret (str): The secret for this Webhook that you saved when you first created it
    """
    if int(curr_time) - int(req_time) < 500:
        message = 'v0:{}:{}'.format(req_time, body)
        calculated_signature = 'v0={}'.format(hmac.new(
            bytes(secret, 'latin-1'),
            msg=bytes(message, 'latin-1'),
            digestmod=hashlib.sha256).hexdigest())
        if calculated_signature == signature:
            return True
    return False
```

**Znacznik czasu** to czas systemowy Frame.io w momencie wysłania webhooka. Można go użyć do zapobiegania atakom [powtórzeniowym](https://en.wikipedia.org/wiki/Replay_attack). Zalecamy sprawdzanie, czy ten czas mieści się w granicach 5 minut od czasu lokalnego.

**Podpis** to skrót HMAC SHA256 obliczony przy użyciu klucza podpisywania przekazanego podczas pierwszego tworzenia webhooka.

**Aby zweryfikować podpis, wykonaj następujące kroki:**

<Steps>

<Step title="Wyodrębnij podpis">

Wyodrębnij podpis z nagłówków HTTP.

</Step>

<Step title="Utwórz wiadomość do podpisania">

Utwórz wiadomość do podpisania, łącząc wersję, czas dostarczenia i treść żądania: `v0:timestamp:body.`

</Step>

<Step title="Oblicz HMAC SHA256">

Oblicz podpis HMAC SHA256 przy użyciu swojego sekretu podpisywania.

</Step>

<Step title="Porównaj podpisy">

Porównaj obliczony podpis z podpisem otrzymanym w żądaniu!

</Step>

</Steps>

<Note>

Otrzymany podpis ma prefiks `v0=`. Obecnie Frame.io stosuje tylko tę jedną wersję podpisywania żądań. Pamiętaj, aby dodać ten prefiks na początku obliczonego podpisu.

</Note>

## Limity szybkości webhooków {#webhook-rate-limits}

Zdarzenia webhooków i Custom Actions podlegają wspólnym limitom na konto:

| Okno czasowe | Limit na konto |
| --- | --- |
| 1 minuta | 1000 zdarzeń |
| 1 godzina | 20 000 zdarzeń |

Oba limity dotyczą łącznej liczby zdarzeń webhooków i Custom Actions. Mieszczenie się w limicie minutowym nie zwalnia konta z limitu godzinowego. Limity te obowiązują na poziomie konta, a nie osobno dla każdej subskrypcji webhooka czy Custom Action.

Są to limity liczby zdarzeń, a nie limity żądań API służących do tworzenia, wyświetlania, aktualizowania lub usuwania subskrypcji webhooków czy Custom Actions.

<Warning>

Po osiągnięciu któregokolwiek z limitów na poziomie konta kolejne zdarzenia webhooków i Custom Actions są **odrzucane**, a nie kolejkowane do późniejszego dostarczenia. Odrzucone zdarzenia nie są automatycznie ponawiane ani odtwarzane, gdy pojawi się wolna przepustowość. Opisana poniżej zasada ponawiania dostarczania nie dotyczy zdarzeń odrzuconych w wyniku ograniczenia szybkości.

</Warning>

### Praca w ramach limitów {#working-within-the-limits}

Aby zmieścić się w limitach webhooków, zalecamy subskrybowanie wyłącznie tych **[zdarzeń](#webhook-event-subscriptions)**, których potrzebuje Twoja integracja. Na przykład, jeśli Twój workflow rozpoczyna się po zakończeniu przesyłania pliku, subskrybuj `file.upload.completed` zamiast wszystkich zdarzeń dotyczących plików. Regularnie przeglądaj subskrypcje swojego konta i usuwaj te, które nie są już używane.

Jeśli Twoja integracja przesyła wiele plików lub wykonuje serię aktualizacji, w miarę możliwości rozłóż te operacje w czasie, aby zmieścić się w obu limitach i pozostawić zapas na inną aktywność na koncie. Pomaga to uniknąć odrzucania zdarzeń, które nie są ponawiane.

## Samouczek dotyczący webhooków {#webhook-tutorial}

### Krok 1: Skonfiguruj stronę odbiorczą (najpierw, aby znać swój adres URL) {#step-1-setup-receiving-end-done-first-so-that-you-know-what-your-url-will-be}

Po pierwszym wejściu na stronę [https://webhook.site](https://webhook.site/) zostanie dla Ciebie utworzony unikalny endpoint webhooka, który możesz od razu skopiować i używać.

Ten adres URL jest unikalny dla Twojej sesji.

### Krok 2: Wybierz zdarzenia, które chcesz subskrybować {#step-2-choose-the-events-you-want-to-subscribe-to}

W tym samouczku nie będziemy komplikować i skonfigurujemy webhooka tak, aby subskrybował tylko zdarzenia `file.created`. Ładunek JSON, którego użyjemy do utworzenia webhooka, wygląda następująco.

```json
{
    "data": {
        "name": "asset.created sample webhook",
        "events": ["file.created"],
        "url": "https://webhook.site/c05f2216-9558-4816-bc09-f77ee7b9de40"
    }
}
```

Po utworzeniu subskrypcji webhooka i skonfigurowaniu endpointu odbierającego webhooki pora to przetestować, wyzwalając pierwszy webhook przez wykonanie odpowiedniej akcji, która spowoduje jego wysłanie!

Ponieważ nasz przykład został skonfigurowany tak, aby reagował na zdarzenie `file.created`, prześlemy nowy zasób do dowolnego Projektu w ramach odpowiedniego konta i Workspace’u, w którym skonfigurowano webhooka.
