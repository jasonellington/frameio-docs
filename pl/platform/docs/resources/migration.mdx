## Wprowadzenie {#introduction}

API Frame.io V4 to przeprojektowana wersja starszego API (Legacy API), często określanego jako *endpointy V2* lub *API Frame.io V3*. Nowy projekt w pełni wykorzystuje nowe możliwości i funkcje Frame V4, zachowując przy tym całą istotną funkcjonalność starszego API. Ten przewodnik przedstawia kluczowe różnice między starszym API a API V4 i zawiera instrukcje krok po kroku, które pomogą Ci przeprowadzić migrację bez problemów.

## Lista kontrolna migracji {#migration-checklist}

<Steps>

<Step title="Uwierzytelnianie">

W przypadku <Tooltip tip="Konta, które korzystały ze starszego API z wygenerowanym tokenem deweloperskim i zostały automatycznie zmigrowane do V4. Nie obejmuje to kont utworzonych w V4 ani kont zmigrowanych ręcznie">**kont automatycznie zmigrowanych do V4**</Tooltip>, które nie są jeszcze administrowane przez Adobe Admin Console, możesz nadal używać starszych tokenów deweloperskich (Legacy Developer tokens) zarządzanych w [witrynie deweloperskiej Frame.io](/pl/platform/welcome), ale musisz dodać do żądań API nagłówek o kluczu `x-frameio-legacy-token-auth` i wartości `true`. W przeciwnym razie wykonaj kroki opisane w sekcji [Uwierzytelnianie](#adobe-developer-console-managed-authentication) poniżej.

</Step>

<Step title="Zaktualizuj istniejące wywołania API">

Wszystkie ścieżki starszego API trzeba będzie zmapować na nowe ścieżki i ładunki JSON API V4. Poniżej znajduje się dość obszerna tabela [mapowań](#endpoint-mappings-legacy-api-to-v4), która ułatwi ten proces.

</Step>

<Step title="Zdecydowanie zalecamy testowanie">

**Dokładnie przetestuj.** Ponieważ w API wprowadzono wiele zmian, zalecamy testowanie na koncie V4, aby upewnić się, że nowe API działa zgodnie z oczekiwaniami.

</Step>

<Step title="Zaimplementuj dedykowane logowanie">

Zaimplementuj dedykowaną metodę logowania dla V4 ze względu na odrębne adresy URL uwierzytelniania. Adres URL uwierzytelniania V4 różni się od adresu starszego API, nie zwraca w odpowiedzi kont, które nie zostały jeszcze zaktualizowane do V4, i należy go traktować jako odrębną integrację.

</Step>

</Steps>

<Note>

Jeśli masz pytania dotyczące endpointu, którego nie ma w poniższej tabeli mapowań, skontaktuj się z naszym zespołem wsparcia pod adresem [support@frame.io](mailto:support@frame.io).

</Note>

## Uwierzytelnianie zarządzane przez Adobe Developer Console {#adobe-developer-console-managed-authentication}

W przypadku kont zmigrowanych do V4, które są zarządzane przez [Adobe Developer Console](https://developer.adobe.com/developer-console/), musisz używać API V4 z OAuth 2.0. Wykonaj poniższe kroki.

<Steps>

<Step title="Utwórz projekt Adobe">

**Utwórz projekt w Adobe Developer Console** i dodaj Frame.io jako produkt.

</Step>

<Step title="Wybierz typ uwierzytelniania">

**Uwierzytelnij się.** Więcej informacji znajdziesz w [przewodniku po uwierzytelnianiu](https://developer.adobe.com/frameio/guides/Authentication/). Jeśli Twoje konto V4 nie jest jeszcze zarządzane przez Adobe Admin Console, możesz pominąć ten krok.

- **Uwierzytelnianie użytkownika**: łączy się z Frame przy użyciu Client ID i/lub Client Secret i wymaga zalogowania się użytkownika za pomocą nazwy użytkownika i hasła.
- **Uwierzytelnianie server-to-server**: łączy się z Frame przy użyciu Client ID i Client Secret, ale nie wymaga udziału użytkownika logującego się przez przeglądarkę.

</Step>

<Step title="Zaimplementuj uwierzytelnianie Bearer">

**JWT Bearer Auth**: w każdym żądaniu API przekazuj token uwierzytelniający w nagłówku o kluczu `Authorization` i wartości `Bearer <IMS_ACCESS_TOKEN>`.

</Step>

</Steps>

## Mapowania endpointów (starsze API do V4) {#endpoint-mappings-legacy-api-to-v4}

<Note>

Jeśli używasz uwierzytelniania starszym tokenem deweloperskim, musisz dodać do żądań API nagłówek o kluczu x-frameio-legacy-token-auth i wartości true.

</Note>

Ogólne uwagi pomocne przy migracji:

<Steps>

<Step title="Ładunki">

Ładunki żądań i odpowiedzi mogą się różnić.

</Step>

<Step title="Teams → Workspaces">

„Teams” w starszym API odpowiadają „Workspaces” w V4.

</Step>

<Step title="Assets">

„Assets” ze starszego API są teraz w V4 podzielone na „Files”, „Folders” i „Version Stacks”.

</Step>

<Step title="Uprawnienia">

Uprawnienia i role w V4 są inne, co zmienia strukturę endpointów. W V4 istnieją role użytkowników na poziomie obszaru roboczego i projektu. Więcej szczegółów znajdziesz w sekcji [Zarządzanie uprawnieniami użytkowników](/pl/platform/docs/guides/managing-user-permissions).

</Step>

</Steps>

### 8. Udostępnienia (Review Links / Presentations) {#8-shares-review-links-/-presentations}

We Frame V4 linki udostępniania nie są już dzielone na linki do recenzji i linki do prezentacji. W V4 link udostępniania można teraz skonfigurować z różnymi stylami, aby odpowiadał doświadczeniu recenzji lub prezentacji.

Uwaga: interakcja ze starszymi linkami do recenzji i prezentacjami za pośrednictwem API V4 nie jest obsługiwana.

| Metoda | Starszy endpoint | Metoda | Endpoint V4 | Uwagi |

### 9. Webhooki {#9-webhooks}

Webhooki używane w V3 zostaną przeniesione i w większości będą działać tak samo. Po migracji zostaną wyłączone i trzeba będzie je włączyć, aby działały. Konieczne będą pewne zmiany w przypadku zdarzeń dotyczących zasobów (assets), które są teraz podzielone na pliki i foldery. Należy też pamiętać o kilku nowych zdarzeniach specyficznych dla V4: metadata.value.updated, zdarzeniach związanych z kolekcjami i zdarzeniach związanych z udostępnieniami.

Przed ponownym włączeniem zmigrowanych webhooków zapoznaj się z [limitami liczby żądań dla webhooków](/pl/platform/docs/guides/webhooks#webhook-rate-limits). Zdarzenia webhooków i Custom Actions w V4 mają wspólne limity wynoszące **1000 zdarzeń na minutę** i **20 000 zdarzeń na godzinę** na konto. Oba limity dotyczą łącznej liczby zdarzeń w obrębie konta.

## Kroki migracji {#migration-steps}

<Steps>

<Step title="Dostosuj nieobsługiwane endpointy V2">

**Dostosuj** wszystkie nieobsługiwane starsze endpointy V2.

</Step>

<Step title="Zaktualizuj bazowe adresy URL">

**Zaktualizuj bazowe adresy URL** z `api.frame.io/v2/...` na `api.frame.io/v4/...`.

</Step>

<Step title="Zaktualizuj żądania API">

**Zaktualizuj żądania API** w swoim kodzie, aby odwoływały się do nowego schematu endpointów.

</Step>

<Step title="Zaktualizuj ładunki JSON">

**Zaktualizuj ładunki JSON** zgodnie ze schematami żądań/odpowiedzi, aby mieć pewność, że wysyłasz i odczytujesz właściwe pola.

</Step>

<Step title="Zaktualizuj terminologię">

Zaktualizuj terminologię w kodzie i interfejsie użytkownika: „teams” → „workspaces”; „assets” → „files/folders”; „review links” lub „presentation links” → „shares”.

</Step>

<Step title="Przetestuj endpointy">

**Przetestuj** wszystkie nowo zaktualizowane endpointy. Jeśli zobaczysz błąd 403, 404 lub 422, sprawdź endpointy, strukturę ładunku żądania itp.

</Step>

<Step title="Analizuj odpowiedzi z błędami">

**Analizuj** nowe, szczegółowe odpowiedzi z błędami — jeśli wywołanie API się nie powiedzie, szukaj przyczyny w odpowiedzi JSON `{"errors": [...]}`.

</Step>

<Step title="Wdróż na produkcję">

**Wdróż** na produkcję po zweryfikowaniu z kontem [Frame.io](http://frame.io/) V4.

</Step>

</Steps>

## Obsługa błędów i typowe problemy {#error-handling-&-common-issues}

<Note>

Niektóre ścieżki zwracają błędy z niestandardowymi opisami, które mogą nieco różnić się od poniższych przykładów.

</Note>

<CardGroup cols={2}>

<Card title="Błędy klienta (4xx)" icon="triangle-exclamation" iconType="solid">

- **400** Bad Request: sprawdź poprawność ładunku.
- **401** Unauthorized: nieprawidłowy lub brakujący token autoryzacyjny.
- **403** Forbidden: brak zakresu lub użytkownik nie ma dostępu.
- **404** Not Found: sprawdź endpoint, wersję API lub identyfikatory.
- **422** Unprocessable Entity: zweryfikuj dane żądania
- **429** Too Many Requests: zaimplementuj ponawianie z wycofywaniem (backoff).

</Card>

<Card title="Błędy serwera (5xx)" icon="server" iconType="solid">

- **500** Internal Server Error: ponów próbę po krótkim czasie.

</Card>

</CardGroup>
