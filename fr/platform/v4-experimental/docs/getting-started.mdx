## Quoi de neuf dans l’API développeur Frame.io V4 ? {#what’s-new-in-the-frame-io-v4-developer-api}

Tout comme l’application Frame.io a été entièrement transformée pour la version 4, l’API V4 a elle aussi été repensée de fond en comble. Bien que certains concepts clés restent similaires à ceux des versions héritées, beaucoup ont été remplacés ou repensés pour prendre en charge des workflows de collaboration et des intégrations plus puissants. L’introduction d’une API entièrement nouvelle nous a également permis de simplifier considérablement nos opérations et de donner la priorité aux workflows clients importants.

<Info>

Une comparaison entre Frame.io V4 et la version héritée est disponible [ici](https://help.frame.io/en/articles/9084073-frame-io-v4-legacy-feature-comparison).

</Info>

Dans l’API V4, certaines ressources, comme les Workspaces (auparavant appelés Teams dans la version héritée de Frame.io), ont été renommées pour correspondre à Frame.io Version 4, tandis que d’autres, comme les Assets de la version héritée, ont été renommées pour désigner des entités de stockage spécifiques (Files, Folders et Version Stacks) afin de réduire la confusion pour les développeurs. D’autres encore, par exemple les Custom Fields et les Shares, sont entièrement nouvelles. Parmi d’autres changements importants, nous avons considérablement réduit la quantité de données renvoyées par défaut pour les requêtes de ressources, renommé certaines propriétés de nos réponses pour qu’elles soient plus précises et cohérentes sur l’ensemble de l’API, et adopté un nouveau mécanisme de pagination basé sur des curseurs. Il est donc important de comprendre qu’à l’exception de l’API Camera to Cloud (C2C), les clients intégrés à l’API héritée ne sont pas compatibles avec l’API V4.

Par ailleurs, certaines fonctionnalités sont encore en cours de développement et devraient arriver et évoluer rapidement en fonction des cas d’usage réels et des retours des clients. Citons par exemple la possibilité de créer des custom actions et des version stacks. Si une fonctionnalité auparavant disponible dans notre API héritée semble manquer, il est fort probable qu’il existe une alternative ou qu’elle soit bientôt disponible, mais nous aimerions avoir votre avis à ce sujet.

Avant de vous plonger dans l’API V4, il est utile de comprendre d’abord les concepts fondamentaux de l’application Frame.io Version 4. La [base de connaissances Frame.io V4](https://help.frame.io/en/) est un bon point de départ. Des concepts comme les Accounts, Users, Workspaces, Projects, Collections, Shares et Custom Fields (métadonnées) sont modélisés comme des ressources distinctes dans l’API V4 ; comprendre leurs relations et leurs capacités dans l’application vous aidera à comprendre leur fonctionnement dans l’API V4.

## Vue d’ensemble de l’API {#api-overview}

L’API Frame.io V4 est conçue pour suivre les principes architecturaux RESTful et utilise les méthodes HTTP et codes de réponse standard, associés à des URL uniques propres à chaque ressource. Frame.io publie une [spécification OpenAPI 3.0](https://api.frame.io/v4/openapi.json) pour son API V4, qui fournit des informations détaillées sur ses endpoints, paramètres de requête et réponses. La spécification OpenAPI peut être utilisée par divers outils tiers de génération de code pour faciliter le développement rapide d’applications clientes.

### Conventions d’URL et de chemins {#url-and-path-conventions}

Les chemins d’URL publiés dans la spécification OpenAPI reflètent généralement les relations d’appartenance et de contenance entre les ressources. Ainsi, certains paramètres de requête (par exemple les identifiants de compte, de dossier, etc.) sont intégrés au chemin de la ressource. Bien que ces chemins soient conçus pour être prévisibles et faciles à comprendre, la structure de certaines URL renvoyées par les requêtes API (par exemple les URL d’envoi pré-signées ou les liens d’affichage) est susceptible de changer et ne doit jamais être composée directement par une application cliente.

### Paramètres de requête {#request-query-parameters}

Les paramètres de requête qui contrôlent la pagination et l’inclusion facultative de ressources associées dans les objets de réponse sont définis comme un ensemble standard de paramètres de requête : `include`, `page_size`, `include_total_count`. Certaines requêtes peuvent prendre en charge des paramètres de requête supplémentaires propres à cette ressource ou à cette opération.

```html
GET https://api.frame.io/v4/accounts/{account_id}/folders/{folder_id}/children?&include=project&page_size=5&include_total_count=true
```

### Payloads de requête et de réponse {#request-and-response-payloads}

Les payloads de requête et de réponse sont tous deux composés d’objets JSON ; par conséquent, l’en-tête content-type d’une requête HTTP POST, PUT ou PATCH doit spécifier le type de média `application/json`. Lors de la création ou de la mise à jour de ressources, la propriété `data` de la requête doit contenir l’objet ressource. Les attributs de la ressource créée ou mise à jour sont contenus dans cet objet. De même, les réponses réussies qui incluent des ressources les fournissent dans la propriété `data` de la réponse.

### Pagination {#pagination}

Les réponses susceptibles de renvoyer un grand nombre d’objets ressources (par exemple des listes de dossiers ou de commentaires) sont paginées afin de réduire la latence des requêtes à mesure que l’ensemble de résultats s’agrandit. Cela signifie que la réponse à une requête peut n’inclure qu’une seule « page » de résultats. Comme indiqué ci-dessus, un client peut choisir une taille de page spécifique, jusqu’à un maximum de 100 éléments, via le paramètre de requête `page_size` lors de l’envoi de la requête. S’il n’est pas spécifié, la taille de page est de 50 éléments par défaut. L’API V4 utilise une forme de pagination appelée *pagination basée sur des curseurs* et inclut, dans la propriété `links` de l’objet de réponse (voir l’exemple ci-dessous), un lien relatif contenant une chaîne de curseur opaque (les clients ne doivent pas tenter de construire eux-mêmes cette chaîne) dans le paramètre de requête `after`, ce qui permet au client de récupérer la page de résultats suivante (voir l’exemple de réponse ci-dessous) en effectuant des requêtes successives. Actuellement, l’API V4 ne prend en charge que la pagination unidirectionnelle.

```json
{
    "data": [
```

### Erreurs {#errors}

En cas d’erreur, la propriété `errors` de l’objet de réponse contient un tableau d’un ou plusieurs objets d’erreur fournissant des détails sur la ou les erreurs survenues. Actuellement, les opérations par lots ne sont pas prises en charge par l’API V4 ; il n’existe donc aucun cas où le client doit gérer à la fois une réussite partielle et des erreurs.

```json
{
    "errors": [
        {
            "detail": "Unexpected field: foo",
            "source": {
                "pointer": "/data/foo"
            },
            "title": "Invalid value"
        }
    ]
}
```

Le tableau suivant répertorie les codes de statut courants utilisés par l’API V4.

| Code de statut | **Statut** | Description |
| --- | --- | --- |
| 200 | OK | La requête a réussi. |
| 201 | Created | La ressource a été créée. |
| 204 | No Content | La ressource a été supprimée. Aucun payload de réponse. |
| 400 | Bad Request | La requête n’est pas valide, souvent en raison d’un paramètre ou d’un payload mal formé ou manquant. |
| 401 | Unauthorized | Le jeton d’autorisation est manquant ou invalide. |
| 403 | Forbidden | Le jeton d’autorisation ne dispose pas des autorisations suffisantes pour cette requête. |
| 404 | Not Found | La ressource demandée n’existe pas. |
| 422 | Unprocessable Entity | Le payload et/ou les paramètres de la requête sont bien formés mais invalides par ailleurs, ce qui empêche l’exécution de la requête (largement interchangeable avec 400 Bad Request). |
| 429 | Too Many Requests | La requête a dépassé la limite de débit de notre API pour ce compte. Consultez la section Limitation du débit du guide de démarrage pour plus de détails. |
| 5xx | Server Errors | Une erreur inattendue a été signalée par notre serveur. Les clients doivent attendre au moins 30 secondes avant de relancer l’événement, et toute nouvelle tentative automatisée doit être limitée et inclure un intervalle aléatoire, en plus d’appliquer un back-off exponentiel lors des requêtes successives. |

### Authentification et autorisation {#authentication-and-authorization}

L’API V4 s’appuie sur OAuth 2.0 et [Adobe Identity Management Server (IMS)](https://experienceleague.adobe.com/en/docs/commerce-admin/start/admin/ims/adobe-ims-integration-overview) pour authentifier un utilisateur (AuthN) et générer des jetons d’accès en son nom. Un jeton d’accès doit être fourni avec chaque requête API via l’en-tête HTTP Authorization (c’est-à-dire une authentification par jeton Bearer).

<Note>

Les [scopes de jeton](https://developer.adobe.com/developer-console/docs/guides/authentication/UserAuthentication/ims#scopes) générés par IMS sont statiques, et l’autorisation (AuthZ), qui détermine ce que l’utilisateur est autorisé à faire (et quelles opérations l’API peut effectuer au nom de cet utilisateur), dépend des rôles et autorisations accordés à l’utilisateur dans Frame.io. Consultez les sections Prise en main de la Developer Console et Configuration de l’authentification (sous Commencer à développer avec Postman) pour plus de détails sur la génération et la demande de jetons d’accès.

</Note>

### Versions et rétrocompatibilité {#versions-and-backward-compatibility}

L’API Frame.io V4 n’est *pas* rétrocompatible avec les versions antérieures des API Frame.io et, de manière générale, ne peut pas être utilisée pour accéder aux ressources des comptes hérités ou les mettre à jour, car les concepts et le modèle de données de V4 ont considérablement changé. C’est pourquoi les URI associées à l’API V4 comportent toutes un préfixe de chemin `/v4`. Toutefois, l’API V4 évolue encore rapidement et il est possible que de nouvelles fonctionnalités justifient occasionnellement des changements incompatibles. Plus fréquemment, Frame.io publiera de nouveaux *ajouts* à l’API que nous considérerons comme expérimentaux pendant un certain temps, ce qui nous permettra de recueillir les retours des clients et les métriques d’utilisation et d’y répondre. Conscients que la rétrocompatibilité est une préoccupation majeure pour les clients qui gèrent des intégrations de qualité production avec des exigences élevées de disponibilité, nous concevons l’API V4 pour prendre en charge un niveau de versionnage supplémentaire via un en-tête HTTP personnalisé, afin de permettre aux clients d’opter pour l’utilisation d’endpoints expérimentaux, d’éviter les changements incompatibles et de bénéficier de garanties de rétrocompatibilité au sein de l’espace de noms V4. Plus de détails suivront, mais pour l’instant, vous pouvez considérer que la version initiale de l’API V4 est stable et qu’il s’écoulera un certain temps avant que nous envisagions d’introduire des changements incompatibles.

### Limitation du débit {#rate-limiting}

Tous les appels à l’API V4 sont soumis à une limitation du débit, et chaque ressource et opération de l’API est configurée avec sa propre limite. Les limites vont de 10 requêtes par minute à 100 requêtes par seconde. Actuellement, chaque limite est appliquée *par utilisateur*, mais les politiques et les limites elles-mêmes sont susceptibles d’évoluer.

L’API V4 utilise un algorithme de limitation progressive du débit de type « [seau percé](https://wikipedia.org/wiki/Leaky_bucket) » (leaky bucket), dans lequel les limites se renouvellent progressivement au cours de la fenêtre de temps impartie. Autrement dit, il n’existe pas de seuil fixe après lequel les limites se renouvellent pour une ressource donnée (comme dans les stratégies à fenêtre « fixe » ou « glissante »). Les limites restantes se renouvellent plutôt en continu, à un rythme proportionnel à la limite et à la fenêtre de temps de la ressource. Les requêtes qui dépassent la limite de débit d’un endpoint donné échouent avec une erreur HTTP 429.

La stratégie que nous recommandons pour répondre aux erreurs 429 est généralement appelée « back-off exponentiel ».
En résumé :

- Lorsque vous recevez une erreur `429`, faites une pause (d’au moins une seconde) avant de relancer la requête
- Si vous recevez une nouvelle erreur `429`, augmentez de manière exponentielle, ou au moins doublez, le délai d’attente précédent jusqu’à ce que le fonctionnement normal reprenne

Pour déterminer les limites de débit qui s’appliquent à une requête donnée, les clients peuvent examiner les en-têtes HTTP suivants renvoyés dans la réponse :

| En-tête | Description de la valeur |
| --- | --- |
| `x-ratelimit-limit` | La limite de débit pour ce chemin de ressource, exprimée en nombre de requêtes. |
| `x-ratelimit-remaining` | Le nombre de requêtes restantes dans la fenêtre de temps actuelle. |
| `x-ratelimit-window` | La fenêtre de temps des limites de ce chemin de ressource, exprimée en millisecondes (ms). |

## Détails de l’API {#api-details}

La documentation de référence de l’API V4 est notre [guide de référence de l’API](/fr/platform/api-reference/account-permissions/account-user-roles-update), mais il est utile de comprendre la hiérarchie des ressources telle que modélisée par l’API V4 avant d’envoyer vos premières requêtes.

### Hiérarchie des ressources {#resource-hierarchy}

Un [Account](https://help.frame.io/en/collections/8779087-account-settings) est généralement associé à une organisation et représente la ressource fondamentale qui détermine le plan d’abonnement, la propriété du contenu, les rôles / autorisations des utilisateurs et l’organisation des Workspaces. C’est pourquoi le chemin d’URL de presque tous les endpoints de l’API V4 comporte un préfixe qui identifie l’Account dans lequel se trouve la ressource.

Les Workspaces (auparavant appelés Teams dans la version héritée de Frame.io) et les [Projects](https://help.frame.io/en/articles/9101006-project-settings) servent à organiser à la fois le contenu et les utilisateurs, y compris qui a accès à quel contenu.

La hiérarchie de base des ressources de contenu dans Frame.io est la suivante :

<CardGroup cols={2}>

<Card title="Hiérarchie des ressources" icon="sitemap" iconType="solid">

**Account → Workspace → Project → Folder → Folder / Version Stack / File**

</Card>

</CardGroup>

Chaque asset envoyé vers Frame.io est en fin de compte représenté par un [File](https://help.frame.io/en/articles/9436564-supported-file-types-on-frame-io), tandis que les [Folders](https://help.frame.io/en/articles/9101044-creating-folders) et les [Version Stacks](https://help.frame.io/en/articles/9101068-version-stacking) sont des ressources de stockage qui servent de conteneurs et constituent la base d’un modèle de stockage hiérarchique prenant en charge les assets versionnés. La plupart des utilisateurs connaissent déjà le concept de base d’un Folder dans Frame.io : il sert simplement de conteneur non ordonné d’autres ressources de stockage (modélisées comme ses `children`) et représente un nœud de l’arborescence des dossiers. Chaque Project possède un dossier racine unique (identifié par la clé `root_folder_id`), qui sert de racine à l’arborescence des dossiers dans laquelle se trouvent tous les assets du Project.

Un Version Stack est un conteneur ordonné de Files. Son ordre est strictement linéaire et détermine un numéro de version pour chacun de ses enfants, mais les clients peuvent réorganiser les Files au sein du version stack comme ils le souhaitent. Un File est toujours l’enfant de (contenu dans) exactement un Folder *ou* un Version Stack à un instant donné. De même, un Folder ou un Version Stack est toujours l’enfant d’exactement un Folder (à l’exception du dossier racine du Project).

Consultez le [guide de référence de l’API](https://developer.frame.io/platform/v4-experimental/api/current) pour plus de détails sur les opérations CRUD de base sur les Files et Folders stockés dans Frame.io. Actuellement, l’API V4 ne prend en charge les Version Stacks que lors du listage du contenu d’un Folder, mais des endpoints permettant de créer et de mettre à jour des Version Stacks seront bientôt disponibles.
