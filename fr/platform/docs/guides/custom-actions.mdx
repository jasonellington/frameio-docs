Les Actions Frame.io offrent un accès rapide aux opérations média courantes comme le téléchargement, le renommage et la duplication d’éléments, et permettent également d’intégrer des outils et services tiers directement dans l’interface utilisateur de [Frame.io](https://next.frame.io/).

## À propos des Actions {#about-actions}

Avec l’introduction des Custom Actions, les développeurs peuvent configurer et gérer leurs propres Actions dans Frame.io V4. S’appuyant sur le même système d’événements sous-jacent que les [Webhooks](https://developer.adobe.com/frameio/guides/Webhooks/), les Custom Actions constituent un mécanisme alternatif permettant aux développeurs de connecter leurs assets aux outils les plus importants pour les utilisateurs de leur compte Frame.io.

Les Actions peuvent être exécutées par tout utilisateur Member du Workspace Frame.io dans lequel l’Action est activée. Lors de l’exécution d’une Action, Frame.io envoie un payload à une URL que vous fournissez. L’application destinataire répond avec un code de statut HTTP pour accuser réception, ou avec un callback personnalisé pour afficher des champs de formulaire supplémentaires dans l’interface de Frame.io. L’application destinataire peut être votre propre programme ou service hébergé, voire un outil IPaaS low-code/no-code comme Workfront Fusion ou Zapier.

Utilisez les Custom Actions pour créer des intégrations directement dans [Frame.io](https://next.frame.io/) sous forme de composants d’interface programmables. Cela permet de créer des workflows déclenchables par les utilisateurs dans l’application, en s’appuyant sur le même routage d’événements sous-jacent que les webhooks. Vous pouvez créer des formulaires à une ou plusieurs étapes, déclenchés par l’utilisateur, qui reviennent dans Frame.io sous la forme d’un autre formulaire ou d’une réponse simple. Et lorsqu’un utilisateur clique sur une Custom Action sur un Asset, Frame.io envoie un payload à une URL que vous fournissez. L’application destinataire répond avec un code de statut HTTP pour accuser réception, ou avec un callback personnalisé qui peut afficher une interface supplémentaire dans Frame.io.

## Limites de débit {#rate-limits}

Les événements de Custom Actions sont comptabilisés dans les mêmes limites au niveau du compte que les événements de webhooks : **1 000 événements par minute** et **20 000 événements par heure**. Ces deux limites s’appliquent à leur volume combiné sur l’ensemble du compte, et non séparément à chaque Custom Action ou abonnement webhook.

Lorsque l’une de ces limites est atteinte, les événements de Custom Actions supplémentaires sont **abandonnés** : ils ne sont ni mis en file d’attente ni relancés automatiquement.

Il s’agit de limites de volume d’événements, et non de limites de requêtes API pour la gestion des Custom Actions. Consultez [Limites de débit des webhooks](/fr/platform/docs/guides/webhooks#webhook-rate-limits) pour plus de détails.

## Actions migrées {#migrated-actions}

Quelques points sont à garder à l’esprit lors de la migration vers un compte Frame.io V4 contenant des Custom Actions créées dans la version legacy de Frame.io.

### Statut des Actions {#action-status}

Lors de la migration du compte vers Frame.io V4, toutes les Custom Actions créées dans les versions antérieures auront le statut ‘null’ et seront automatiquement désactivées. Cela permet aux utilisateurs de mettre d’abord à jour leurs Actions pour utiliser l’API V4 avant de les activer, car toute Action non mise à jour échouera. Pour identifier les Actions dans cet état, rendez-vous sur la page des paramètres des Actions et consultez la colonne “Status” ou, si vous utilisez l’API, vérifiez le champ is_active.

### Ressources prises en charge : fichiers, dossiers et Version Stacks {#actionable-resources-files-folders-&-version-stacks}

Les types d’assets étant des ressources distinctes dans l’API Frame.io V4, certains comportements sont à prendre en compte lors de l’interprétation de l’ID de ressource reçu dans le payload de votre Action. Pour les fichiers individuels, le comportement est simple : l’ID correspond au fichier précis sur lequel l’Action a été exécutée. De même pour les dossiers, vous recevrez l’ID du dossier sur lequel l’Action a été exécutée ; toutefois, selon votre cas d’usage, plusieurs options s’offrent à vous pour définir le comportement de votre Action. Utilisez l’ID du dossier pour effectuer des appels ultérieurs à l’API Frame.io si vous souhaitez interagir avec la ressource dossier elle-même. Vous pouvez aussi récupérer les enfants de ce dossier afin d’effectuer un traitement supplémentaire sur les assets qu’il contient. Lorsqu’une Action est exécutée sur un Version Stack, votre payload contient l’ID du ‘Head Asset’, c’est-à-dire le fichier situé au sommet du Stack, celui qui est affiché dans l’interface de Frame.io.

Pour en savoir plus sur les différences entre l’API Frame.io Legacy et V4, consultez notre [Guide de migration](/fr/platform/docs/resources/migration).

## Configurer votre Custom Action {#configure-your-custom-action}

Lorsqu’un utilisateur déclenche une Custom Action, Frame.io envoie un payload à une URL que vous fournissez. L’application destinataire peut répondre avec un code de statut HTTP pour accuser réception, ou avec un callback personnalisé qui affiche une interface supplémentaire dans [Frame.io](https://next.frame.io/).

<Warning>

Les autorisations Account Admin sont requises pour créer des Custom Actions pour un Workspace. Si vous n’y avez pas accès, demandez à votre Admin de modifier vos autorisations.

</Warning>

### Configuration multi-assets {#multi-asset-configuration}

La prise en charge multi-assets dépend de la configuration et doit être explicitement activée depuis la fenêtre de configuration de l’Action [sur le Web](https://next.frame.io/settings/actions). Cela peut se faire lors de la création d’une nouvelle Action ou lors de la mise à jour d’une Action existante.

Lorsque la prise en charge multi-assets est activée, le format du payload change immédiatement. Le payload legacy et le payload multi-assets s’excluent mutuellement.

### Migrer depuis le payload legacy {#migrating-from-the-legacy-payload}

<Warning>

**Abandon prévu du payload legacy**

L’abandon du payload legacy est prévu, et nous encourageons vivement les utilisateurs à migrer leurs services pour traiter le nouveau payload.

En activant l’option de configuration et en mettant à jour le traitement de votre payload, une Action peut passer en toute transparence à la prise en charge d’un payload multi-assets.

1. Remplacez l’utilisation de l’objet singulier `resource` par la liste `resources`
2. Mettez à jour votre code pour itérer sur la liste `resources`
3. Activez l’option Multi-asset dans la configuration des Actions

</Warning>

| --- | --- |
| `account_id` | L’ID unique du compte de l’Action. |
| `action_id` | L’ID unique de l’Action. |

## Interactions, nouvelles tentatives et délais d’expiration {#interactions-retries-and-timeouts}

L’`interaction_id` est un identifiant unique permettant de suivre l’interaction au fil de son évolution. Si vous n’avez pas besoin de répondre à l’utilisateur, renvoyez un code de statut 200, et c’est terminé. Bien que facultatif, nous recommandons d’inclure des informations sur le résultat de l’action, comme un message de succès ou une alerte d’erreur. Les Custom Actions prennent en charge les message callbacks.

<Note>

Frame.io attend une réponse en moins de 10 secondes et effectue jusqu’à 5 nouvelles tentatives en attendant une réponse réussie. Idéalement, la réponse est immédiate et les actions asynchrones ont lieu après le déclenchement via une Custom Action.

</Note>

## Créer un Message Callback {#create-a-message-callback}

Dans votre réponse HTTP à l’événement webhook, vous pouvez renvoyer un objet JSON décrivant un message qui sera présenté à l’utilisateur à l’origine de l’action dans l’interface de Frame.io.

```json
{
  "title": "Success!",
  "description": "The thing worked! Nice."
}
```

Les messages vous permettent de fournir un retour à l’utilisateur directement dans l’interface de Frame.io. Si vous devez recueillir des informations supplémentaires auprès de l’utilisateur, utilisez plutôt les **Form Callbacks**.

## Créer un Form Callback {#create-a-form-callback}

Supposons que vous ayez besoin de plus d’informations avant de lancer votre processus. Par exemple, vous importez peut-être du contenu dans un système qui exige des détails supplémentaires. Vous pouvez décrire un formulaire dans votre réponse, que l’utilisateur remplit et vous renvoie. Voici un exemple :

```json
{
  "title": "Need some more info!",
  "description": "Getting ready to submit this file!",
  "fields": [
    {
      "type": "text",
      "label": "Title",
      "name": "title",
      "value": "MyVideo.mp4"
    },
    {
      "type": "select",
      "label": "Captions",
      "name": "captions",
      "options": [
        {
          "name": "Off",
          "value": "off"
        },
        {
          "name": "On",
          "value": "on"
        }
      ]
    }
  ]
}
```

Lorsque l’utilisateur soumet le formulaire, vous recevez un événement sur la même URL que le POST initial :

```json
POST /your/url
{
  "type": "your-specified-event-name",
  "interaction_id": "the-same-id-as-before",
  "action_id": "unique-id-for-this-custom-action",
  "data":{
    "title": "MyVideo.mp4",
    "captions": "off"
  }
}
```

Tous les champs personnalisés ajoutés à un formulaire apparaissent dans la section `data` du payload JSON envoyé par Frame.io. Utilisez l’`interaction_id` pour associer la requête initiale à ces nouvelles données de formulaire. Vous pouvez répondre avec un message ou enchaîner un autre formulaire. En enchaînant Actions, formulaires et messages, vous pouvez programmer des workflows en plusieurs étapes dans Frame.io avec la logique métier d’un système externe.

Une simple zone de texte sans paramètres supplémentaires.

Définit une liste de choix dans laquelle l’utilisateur peut sélectionner une option. Doit inclure une liste `options`, dont chaque élément doit comporter un `name` lisible par un humain et une `value` interprétable par une machine.

```json
  "type": "select",
  "label": "Captions",
  "name": "captions",
  "value": "off",
  "options": [
       {
         "name": "Off",
         "value": "off"
       },
       {
         "name": "On",
         "value": "on"
      }
   ]
}
```

Une simple case à cocher sans paramètres supplémentaires.

```json
{ 
   "type": "boolean", 
   "name": "enabled", 
   "label": "Enabled",
```

## Sécurité et vérification {#security-and-verification}

Par défaut, toutes les Custom Actions disposent d’une clé de signature générée lors de leur création. Ce comportement n’est pas configurable. Cette clé peut être utilisée pour vérifier que la requête provient bien de Frame.io. La requête `POST` inclut les éléments suivants :

| Nom | Description |
| --- | --- |
| `X-Frameio-Request-Timestamp` | L’heure à laquelle votre Custom Action a été déclenchée. |
| `X-Frameio-Signature` | La signature calculée. |

<CardGroup cols={2}>

<Card title="Vérification de l’horodatage" icon="clock" iconType="solid">

**L’horodatage** correspond à l’heure à laquelle la requête a été signée en quittant le réseau de Frame.io. Il peut servir à prévenir les attaques par rejeu. Nous recommandons de vérifier que cette heure se situe à moins de 5 minutes de l’heure locale.

</Card>

<Card title="Vérification de la signature" icon="shield" iconType="solid">

**La signature** est un hachage HMAC SHA-256 utilisant la clé de signature fournie lors de la création de la Custom Action.

</Card>

</CardGroup>

### Vérifier la signature {#verifying-the-signature}

<Steps>

<Step title="Extraire la signature">

Extrayez la signature des en-têtes HTTP.

</Step>

<Step title="Créer le message à signer">

Créez un message à signer en combinant la version, l’heure de livraison et le corps de la requête : `v0:timestamp:body`.

</Step>

<Step title="Calculer le HMAC SHA256">

Calculez la signature HMAC SHA256 à l’aide de votre secret de signature.

</Step>

<Step title="Comparer les signatures">

Comparez la signature que vous avez calculée avec celle fournie !

</Step>

</Steps>

<Note>

La signature fournie est préfixée par `v0=`. Actuellement, Frame.io ne dispose que de cette version pour signer les requêtes. Vous devrez ajouter ce préfixe à la signature que vous calculez.

</Note>

```python title="Python"
import hmac
import hashlib

def verify_signature(curr_time, req_time, signature, body, secret):
    """
    Verify webhook/custom action signature
    :Args:
        curr_time (float): Current epoch time
        req_time (float): Request epoch time
        signature (str): Signature provided by the frame.io API for the given request
        body (str): Custom Action body from the received POST
        secret (str): The secret for this Custom Action that you saved when you first created it
    """
    if int(curr_time) - int(req_time) < 500:
        message = 'v0:{}:{}'.format(req_time, body)
        calculated_signature = 'v0={}'.format(hmac.new(
            bytes(secret, 'latin-1'),
            msg=bytes(message, 'latin-1'),
            digestmod=hashlib.sha256).hexdigest())
        if calculated_signature == signature:
            return True
    return False
```
