## Introduction {#introduction}

L’API Frame.io V4 est une refonte de l’API Legacy, souvent appelée *endpoints V2* ou *API Frame.io V3*. Cette refonte tire pleinement parti des nouvelles capacités et fonctionnalités de Frame V4 tout en conservant toutes les fonctionnalités pertinentes de l’API Legacy. Ce guide présente les principales différences entre les API Legacy et V4 et fournit des instructions étape par étape pour vous aider à migrer en douceur.

## Liste de contrôle de la migration {#migration-checklist}

<Steps>

<Step title="Authentification">

Pour les <Tooltip tip="Comptes qui utilisaient l’API Legacy avec un jeton de développeur généré et qui ont été migrés automatiquement vers V4. Les comptes créés sur V4 ou migrés manuellement ne sont pas concernés">**comptes migrés automatiquement vers V4**</Tooltip> qui ne sont pas encore administrés via l’Adobe Admin Console, vous pouvez continuer à utiliser les jetons de développeur Legacy gérés sur le [site développeur de Frame.io](/fr/platform/welcome), mais vous devrez ajouter à vos requêtes API un en-tête ayant pour clé `x-frameio-legacy-token-auth` et pour valeur `true`. Sinon, suivez les étapes de la section [Authentification](#adobe-developer-console-managed-authentication) ci-dessous.

</Step>

<Step title="Mettre à jour les appels API existants">

Toutes les routes de l’API Legacy devront être mises en correspondance avec les nouvelles routes et les nouveaux payloads JSON de l’API V4. Un tableau de [correspondance](#endpoint-mappings-legacy-api-to-v4) assez complet est fourni ci-dessous pour vous aider dans ce processus.

</Step>

<Step title="Les tests sont vivement recommandés">

**Testez minutieusement.** Comme l’API comporte de nombreux changements, il est recommandé d’effectuer des tests avec un compte V4 pour vous assurer que la nouvelle API fonctionne comme prévu.

</Step>

<Step title="Mettre en place une connexion dédiée">

Mettez en place une méthode de connexion dédiée pour V4, car les URL d’authentification sont distinctes. L’URL d’authentification V4 est différente de celle de l’API Legacy : elle ne renverra pas dans sa réponse les comptes qui n’ont pas encore été mis à niveau vers V4 et doit être traitée comme une intégration distincte.

</Step>

</Steps>

<Note>

Si vous avez des questions sur un endpoint qui ne figure pas dans le tableau de correspondance ci-dessous, contactez notre équipe d’assistance à l’adresse [support@frame.io](mailto:support@frame.io).

</Note>

## Authentification gérée via l’Adobe Developer Console {#adobe-developer-console-managed-authentication}

Pour les comptes migrés vers V4 qui sont gérés via l’[Adobe Developer Console](https://developer.adobe.com/developer-console/), vous devrez utiliser l’API V4 avec OAuth 2.0. Suivez les étapes ci-dessous.

<Steps>

<Step title="Créer un projet Adobe">

**Créez un projet dans l’Adobe Developer Console** et ajoutez Frame.io en tant que produit.

</Step>

<Step title="Choisir le type d’authentification">

**Authentifiez-vous.** Consultez le [guide d’authentification](https://developer.adobe.com/frameio/guides/Authentication/) pour plus d’informations. Si votre compte V4 n’est pas encore géré via l’Adobe Admin Console, vous pouvez ignorer cette étape.

- **Authentification utilisateur** : se connecte à Frame à l’aide d’un Client ID et/ou d’un Client Secret, et nécessite qu’un utilisateur se connecte avec son nom d’utilisateur et son mot de passe.
- **Authentification serveur à serveur** : se connecte à Frame à l’aide d’un Client ID et d’un Client Secret, mais ne nécessite pas qu’un utilisateur se connecte via un navigateur.

</Step>

<Step title="Mettre en œuvre l’authentification Bearer">

**Authentification JWT Bearer** : pour chaque requête API, transmettez le jeton d’authentification via un en-tête ayant pour clé `Authorization` et pour valeur `Bearer <IMS_ACCESS_TOKEN>`.

</Step>

</Steps>

## Correspondance des endpoints (API Legacy vers V4) {#endpoint-mappings-legacy-api-to-v4}

<Note>

Si vous utilisez l’authentification par jeton de développeur legacy, vous devrez ajouter à vos requêtes API un en-tête ayant pour clé x-frameio-legacy-token-auth et pour valeur true.

</Note>

Remarques générales pour faciliter la migration :

<Steps>

<Step title="Payloads">

Les payloads de requête et de réponse peuvent être différents.

</Step>

<Step title="Teams → Workspaces">

Les « Teams » de l’API Legacy équivalent aux « Workspaces » de V4.

</Step>

<Step title="Assets">

Les « Assets » de l’API Legacy sont désormais répartis en « Files », « Folders » et « Version Stacks » dans V4.

</Step>

<Step title="Autorisations">

Les autorisations et les rôles sont différents dans V4, ce qui modifie la structure des endpoints. Dans V4, il existe des rôles utilisateur au niveau du workspace et au niveau du projet. Pour plus de détails, consultez [Gérer les autorisations des utilisateurs](/fr/platform/docs/guides/managing-user-permissions).

</Step>

</Steps>

### 8. Partages (liens de revue / présentations) {#8-shares-review-links-/-presentations}

Dans Frame V4, les liens de partage ne sont plus divisés entre liens de revue et liens de présentation. Dans V4, le lien de partage peut désormais être configuré avec différents styles pour correspondre à l’expérience de revue ou de présentation.

Remarque : l’interaction avec les liens de revue et les présentations legacy via l’API V4 n’est pas prise en charge.

| Méthode | Endpoint Legacy | Méthode | Endpoint V4 | Remarques |
| --- | --- | --- | --- | --- |
| **GET** | `/v2/projects/{project_id}/review_links` <br />([Lister les liens de revue d’un projet](/fr/platform/v2/api-reference/review-links/list)) | **GET** | `/v4/accounts/{account_id}/projects/{project_id}/shares` <br />([Lister les partages](https://developer.adobe.com/frameio/api/current/#tag/Shares/operation/shares.index)) | Liste les partages d’un projet (remarque : cela n’inclut pas les liens de revue et les présentations legacy) |

### 9. Webhooks {#9-webhooks}

Les webhooks que vous utilisiez dans V3 seront migrés et fonctionneront pour la plupart de la même manière. Lors de la migration, ils seront désactivés et devront être réactivés pour fonctionner. Certaines modifications seront nécessaires pour les événements d’assets, qui sont désormais répartis entre fichiers et dossiers. Il existe également de nouveaux événements propres à V4 à connaître : metadata.value.updated, les événements liés aux collections et les événements liés aux partages.

Avant de réactiver les webhooks migrés, consultez les [limites de débit des webhooks](/fr/platform/docs/guides/webhooks#webhook-rate-limits). Les événements de webhooks V4 et de Custom Actions partagent des limites de **1 000 événements par minute** et de **20 000 événements par heure**, par compte. Ces deux limites s’appliquent à leur volume combiné sur l’ensemble du compte.

### 10. Custom Actions {#10-custom-actions}

Les Custom Actions que vous utilisiez dans V3 seront migrées, mais nécessiteront quelques modifications au niveau des requêtes et du traitement des réponses. ## Étapes de la migration {#migration-steps}

<Steps>

<Step title="Adapter les endpoints V2 non pris en charge">

**Adaptez** tous les endpoints Legacy V2 non pris en charge.

</Step>

<Step title="Mettre à jour les URL de base">

**Mettez à jour les URL de base** de `api.frame.io/v2/...` vers `api.frame.io/v4/...`.

</Step>

<Step title="Mettre à jour les requêtes API">

**Mettez à jour les requêtes API** dans votre code pour qu’elles référencent le nouveau schéma des endpoints.

</Step>

<Step title="Mettre à jour les payloads JSON">

**Mettez à jour les payloads JSON** des schémas de requête/réponse pour vous assurer que vous produisez et consommez les bons champs.

</Step>

<Step title="Mettre à jour la terminologie">

Mettez à jour la terminologie : « teams » → « workspaces » ; « assets » → « files/folders » ; « review links » ou « presentation links » → « shares », dans votre code et dans votre front-end.

</Step>

<Step title="Tester les endpoints">

**Testez** tous les endpoints nouvellement mis à jour. Si vous obtenez une erreur 403, 404 ou 422, vérifiez les endpoints, la forme du payload de la requête, etc.

</Step>

<Step title="Analyser les réponses d’erreur">

**Analysez** les nouvelles réponses d’erreur détaillées en recherchant le problème dans la réponse JSON `{"errors": [...]}` si votre appel API échoue.

</Step>

<Step title="Déployer en production">

**Déployez** en production une fois la validation effectuée avec un compte V4 [Frame.io](http://frame.io/).

</Step>

</Steps>

## Gestion des erreurs et problèmes courants {#error-handling-&-common-issues}

<Note>

Certaines routes renvoient des erreurs avec des descriptions personnalisées qui peuvent légèrement différer des exemples ci-dessous.

</Note>

<CardGroup cols={2}>

<Card title="Erreurs client (4xx)" icon="triangle-exclamation" iconType="solid">

- **400** Bad Request : vérifiez l’exactitude du payload.
- **401** Unauthorized : jeton d’autorisation invalide ou manquant.
- **403** Forbidden : scope manquant ou l’utilisateur n’a pas accès.
- **404** Not Found : vérifiez l’endpoint, la version de l’API ou les ID.
- **422** Unprocessable Entity : validez les données de la requête
- **429** Too Many Requests : mettez en place des nouvelles tentatives avec backoff.

</Card>

<Card title="Erreurs serveur (5xx)" icon="server" iconType="solid">

- **500** Internal Server Error : réessayez après un court délai.

</Card>

</CardGroup>
