## 什么是 Camera to Cloud API？ {#what-is-the-camera-to-cloud-api}

Camera to Cloud（C2C）API 提供了一种安全的方法，可在录制完成后立即将媒体直接传输到 Frame.io，而无需用户额外输入。在 Frame.io，我们的目标是在录制停止或元数据输入完成后，立即让媒体可用于审阅和协作。

在开发过程中，我们认识到，为了给集成方和用户提供最佳体验，C2C API 需要作为一个独立的专用后端系统运行，与 Frame.io 的主生态系统分开。虽然这一架构决策乍看之下可能并不直观，但本文将通过探讨 C2C 背后的指导原则来解释我们的理由。

## 不止于摄像机素材 {#beyond-camera-footage}

虽然为了清晰易懂、便于识别而将其命名为 "Camera to Cloud"，但该 API 的功能并不局限于摄像机素材。C2C API 可以处理多种类型的数字内容。无论您的设备生成的是音频、视频、PDF 还是其他文件类型，Frame.io 都能容纳。该 API 能以最少的阻力简化任何数字资产从创建到云存储的传输过程。

## 只写，不读 {#write-but-don’t-read}

Frame.io 坚持严格的安全标准，而引入设备连接可能会带来潜在的安全考量。许多媒体采集设备缺乏密码或锁屏等传统安全功能，因为它们最初并不是为联网而设计的。如果为这些设备提供完整的 Frame.io API 访问权限，在无人看管时可能会产生安全漏洞。

此外，设备操作员通常只需要访问特定的元素，而不是整个项目。他们的职责可能仅限于创建特定的媒体资产，而不是管理整个项目。

这引出了我们的核心设计原则：录制设备的主要用途是创建媒体，而不是审阅或评论来自其他来源的内容。最佳的安全方法是开发一个专门限定于其基本功能（将数据上传到云端）的 API。通过完全取消读取功能，我们有效地防止了对敏感项目信息的未授权访问。

## 为界面有限的设备而设计 {#designing-for-devices-with-limited-interfaces}

Frame.io 现有的 API 在设计时假定它们将与具有图形用户界面的应用程序对接。这些应用程序可以向用户显示选项，用户做出选择后再将其发送到服务器。

然而，C2C 生态系统包括 GUI 功能有限甚至没有 GUI 的物理设备，这些设备可能也没有用户输入机制。这就需要一种截然不同的用户交互方式。

在设计 C2C 时，我们需要打造一个能够在界面功能有限的设备上有效运行的系统。这意味着要开发一种不需要在设备本身上进行用户输入的交互模型，因为在许多情况下，这种输入可能根本无法实现。

这一限制排除了使用我们现有 API 架构的可能性，因为现有架构依赖于基于网页的身份验证流程，以及由用户选择目标文件夹。我们不仅需要简化设备可以执行的操作，还需要简化围绕这些操作的整个用户体验。

## 适应间歇性连接 {#accommodating-intermittent-connectivity}

除了界面限制之外，C2C 生态系统中的许多设备还在网络连接不可预测的环境中运行。我们在设计 API 时尽量减少与后端的通信，减少运行期间所需的调用次数，从而为在 WiFi 或蜂窝网络服务有限的偏远地区工作的专业人士提供可靠的体验。

## 简化集成 {#simplifying-integration}

我们的首要任务是让集成尽可能简单。我们开发了一个专注的 API，只包含一组最少的端点，对服务器协商的要求有限，并且其范围被严格限定在与我们目标一致的领域内。我们知道，对于某些集成方来说，这可能是他们第一次实现第三方网络调用。无论您是寻求高效实施的资深开发者，还是刚接触 REST API 的新手，我们都力求让这一体验易于上手、简单直接。
